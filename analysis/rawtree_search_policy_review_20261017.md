# RawTree 탐색 정책·파라미터 코드 검토 — 2026-10-17

## 범위와 결론

평가 요청 수 절감은 목표가 아니다. 기존 번들 선별 → 개별 청크 평가 → 원문 전달을 유지하며, 탐색 순서와 후보 손실을 검토했다. 운영 코드와 YAML은 이번 검토에서 변경하지 않았다. Browser 전면 전환도 아직 구현되지 않았다. 현재 원문 파이프라인 버전은 `raw-curl-browser-docling/4`다.

추천 비교 대상은 **RawTree 내부의 결정적인 배치 best-first 탐색**이다. 모든 검색 루트를 먼저 처리한 뒤, 이미 평가한 링크들을 전역 대기열에 보관하고 깊이와 전체 처리 예산 안에서 높은 점수부터 선택한다. 별도 모델, 생성 요약, MCTS rollout은 필요 없다. 후보를 넣는 단계에서 부모별 top 2를 영구 적용하면 이 변경의 목적을 달성할 수 없다.

검증 자료:

- `analysis/probe_rawtree_search_policy.py`: 실제 RawTree와 기존 LDS를 가짜 문서·점수로 실행. 외부 요청 없음.
- `analysis/probe_rawtree_search_policy.json`: 9개 동작 검증 조건 모두 통과.
- Best-first 부분은 순차 heap 스케줄러의 모의 검증이며, 운영 RawTree에 배치 스케줄러를 통합한 테스트가 아니다. 정답률·실제 서버 성능 개선은 검증하지 않았다.

## 코드로 확인한 제약

### 1. 평가한 링크를 top 2 단계에서 영구적으로 버린다

`searchgym/rawtree.py`의 `preview()`는 전체 `n.link_scores`를 저장하지만 반환은 `[:cfg.jev_branch]`뿐이다. `while level`은 그 반환값만 합친다. 다음 층에서 선택되지 않은 후보도 다음 반복에 남지 않는다.

실제 RawTree에 A의 링크 점수 0.9/0.8/0.7, B의 점수 0.003/0.002를 넣었다. branch=2, 다음 층 폭=4에서는 A의 0.7 대신 B의 두 저점 링크를 방문했다. branch=3에서는 A의 세 번째 링크를 방문했다. 두 부모의 top 2가 같은 URL이면 후보 수가 줄어도 세 번째 링크로 보충하지 않는다. 중복 모의 입력에서는 방문 예산 6 중 4개만 사용했다.

이는 탐색 스케줄러의 선택 결과이지, A의 0.7 링크가 실제 정답 근거라는 뜻은 아니다.

### 2. 폭·깊이·예산은 독립적이지 않다

현재 수준별 탐색에서 루트 E, 폭 W, 깊이 D일 때 방문 상한은 `min(B, E + (D-1)*W)` 이하이다. 실제로는 분기 수·중복·실패·후보 부족이 추가로 제한한다.

루트 10, 부모당 2개, 최대 깊이 5, 예산 50인 충분한 이진 트리에서 실제 RawTree 실행 결과:

| 폭 | 방문 수 | 최대 도달 깊이 |
|---|---:|---:|
| 4 | 26 | 5 |
| 10 | 50 | 5 |
| 20 | 50 | 3 |

따라서 폭 20은 동일 예산에서 탐색을 단순 강화하는 설정이 아니다. 루트 10개와 깊이 2의 20개, 깊이 3의 20개가 예산을 모두 쓴다.

### 3. 기존 LDS는 RawTree의 교체용 옵션이 아니다

`searchgym/agent.py`는 `jev_strategy=raw`일 때만 `LocalDecision`과 `RawTree`를 생성한다. `lds`로 바꾸면 `Jev`와 `JevTree`의 별도 경로를 사용하며 생성형 reader도 다시 사용한다. `test.py`의 API 키 요구, `runner.py`의 준비·캐시 처리도 raw 여부에 의존한다.

또 `searchgym/lds.py`의 기존 스케줄러는 루트마다 첫 선택 경로를 우선한다. 완전한 트리에서 루트 10 × 깊이 5 = 50이므로 예산 50을 모두 discrepancy 0에서 소진했다. 실제 모의 실행 결과 두 번째 선택 방문은 0회, 대기 중 대안은 40개였다. LDS를 비교하려면 스케줄러를 RawTree와 분리해 이식하고, 대안 탐색에 예산이 남는지 설계해야 한다. 현재의 첫 비교 대상으로는 권하지 않는다.

### 4. 검색 간 방문 제외가 쿼리 재평가를 막는다

`RawTree`는 문항당 한 번 생성된다. `self.visited`는 여러 검색에 걸쳐 남지만 `nodes`, `rows`, `page_chunks`는 매 검색마다 새로 생성된다. 같은 검색 결과를 다른 쿼리로 다시 주면 모의 실행의 두 번째 검색은 entries=0, nodes=0이 됐다.

이전 도구 메시지가 메인 기록에서 사라진다는 뜻은 아니다. 이전에 가져왔지만 청킹 대상으로 선택되지 않은 문서를 새 쿼리로 재평가할 수 없다는 제약이다. 같은 원문에 대해 질문을 좁혀 가는 정책에서는 중요하다.

제안: 문항 단위 원문 캐시와 검색 단위 방문 집합을 분리한다. 새 쿼리에서는 캐시 원문으로 새 점수를 계산하며 동일 검색 안에서는 URL 순환을 막는다. 캐시 재사용 페이지도 검색당 논리적 처리 예산 안에 포함하고 실제 HTTP fetch 수는 별도로 기록한다. 네트워크 재시도 정책까지 이 변경에 섞지 않는다.

### 5. 오류 처리도 스케줄러와 연결된다

`_gather_owned()`는 실패 시 형제 작업을 정리하지만, 평가 예외 하나가 전체 검색을 중단시킨다. Best-first를 넣어도 그대로면 이미 확보한 페이지의 청킹·반환 전에 실패할 수 있다.

페이지별 실패 상태를 기록하고 완료된 다른 페이지로 최종 선별을 수행하는 경계를 마련해야 한다. 점수가 없는 페이지를 임의의 0점으로 바꾸거나, 부분 응답의 누락 key를 추측해서 보충해서는 안 된다. 처음부터 d3 준비에 실패한 경우와 일부 페이지 처리 실패도 구분한다.

## 제안하는 구현 경계

1. `jev_strategy=raw`는 유지한다. 별도 `jev_traversal=beam|best_first`로 RawTree 안의 스케줄러만 선택한다. 기본값을 정해 과거 설정 로드도 가능하게 한다.
2. `preview()`의 fetch·페이지/링크 평가를 재사용하되 전체 평가된 링크 후보를 반환한다. `TreeNode`에 이미 `depth`, `parent`, `root_id`, `link_scores`, `document`가 있으므로 새로운 노드 프레임워크는 필요 없다.
3. `while level` 대신 `heapq` 대기열과 고정 크기 배치를 사용한다. 배치 시작 때 후보를 예약하고, 배치 완료 후 정해진 순서로 자식 후보를 넣는다. 네트워크 응답 순서로 방문 순서가 바뀌지 않게 한다.
4. 대기 중인 후보와 실제로 선택한 URL을 분리한다. 같은 URL의 여러 유입 경로 중 현재 관측된 최선 후보를 선택하며, 중복으로 빠진 슬롯은 대기열에서 다음 후보로 채운다. 깊이 제한과 예산은 예약 전에 검사한다.
5. 이미 평가된 링크의 원점수를 우선순위로 사용한다. 경로 점수 곱, 확률로의 해석, 깊이 감쇠, 도메인별 가중치는 첫 구현에 넣지 않는다. 점수는 보정된 경로 성공 확률이 아니다.
6. 순회가 끝난 뒤 `quota_select(rows, ...)`부터 번들·청크 평가·원문 반환은 재사용한다.
7. Browser 전환은 처음 받은 `n.document`를 청킹에도 재사용하도록 구현한다. `fast_fetches`/`browser_fetches`를 실제 호출 의미에 맞게 기록하고, curl용 상수가 남아 있지 않게 테스트한다.
8. `AgentConfig`, YAML 검증, 설정 저장, 캐시 버전, trace의 대기열/선택/종료 이유, 기존 depth별 집계에 새 정책을 반영한다. 새 필드는 config fingerprint에 자동 포함되지만 동작 변경 버전 갱신도 필요하다.

전역 점수 비교는 현재도 같은 층의 서로 다른 부모 사이에서 한다. Best-first는 이를 서로 다른 깊이까지 넓힌다. 모델 점수 편향이나 한 경로로의 쏠림은 검증 대상이며, 최적 탐색 보장은 없다.

## 파라미터 제안

아래 숫자는 첫 비교의 통제값/실험 후보이지 최적값이 아니다.

| 파라미터 | 현재 역할·값 | 제안 |
|---|---|---|
| max_searches / search_results | 메인 검색 10회 / 결과 10개 | 고정 |
| jev_entries | 검색 루트 최대 10개 | 10 유지; snippet/page 점수로 루트를 미리 탈락시키지 않음 |
| jev_depth | 루트를 1로 센 최대 깊이 5 | 5 유지 |
| jev_fetch_budget | 검색당 논리적 방문 50, 실패 포함 | 50 유지; 실제 네트워크 fetch와 분리 계측 |
| jev_branch | 부모별 상위 2개만 후보로 올림 | beam 대조군은 2; best-first에서는 영구 top-k 제한으로 사용하지 않음 |
| jev_frontier_width | 각 깊이에서 최대 10개 | beam 대조군만 사용; best-first에서 같은 이름으로 다른 의미를 주지 않음 |
| jev_expand_batch (신규) | 없음 | best-first 한 라운드 4페이지; 탐색 순서에 영향을 주므로 물리적 concurrency와 구분 |
| jev_link_floor (신규) | 없음 | 0과 0.01 비교. 0.01은 보수적인 시작 후보이며 browser 데이터에서 재확인. 0.05를 처음부터 기본으로 확정하지 않음 |
| jev_reads / direct_reads / query_reads | 6 = 2 + 4 | 첫 탐색 비교는 유지. 다음 독립 비교는 8 = 2 + 6 |
| jev_page_tokens | 탐색 점수·링크 추출에 쓸 앞 5,000토큰 | 5,000 유지. 뒤쪽 링크는 queue/top-k 변경으로 복구되지 않음 |
| MAX_LINKS | prefix에서 발견한 링크 중 페이지 순서 300개 | 그대로; 신규 조절 파라미터로 늘리지 않음 |
| jev_chunk_tokens | 약 512토큰 | 유지 |
| jev_bundle_tokens / overlap_chunks | 5,000토큰 / 2개 중첩 | 유지 |
| jev_floor | 번들 및 최종 청크에 공유하는 0.15 | 유지; 링크 중단값으로 재사용하지 않음 |
| jev_direct_chunks / query_chunks | 4 + 8개의 핵심 청크, 부족한 몫은 이월하지 않음 | 유지; 총량 확대보다 후보 손실을 먼저 확인 |
| jev_neighbor_chunks | 앞뒤 각 1개 | 유지 |
| jev_output_tokens | 검색당 최대 16,000 d3 토큰 | 유지. 메인 모델 토큰 기준과는 다름 |
| jev_concurrency | 공유 d3 HTTP 요청 4개 | 4 유지; 탐색 beam 폭으로 해석하지 않음 |
| run.workers | 문항 동시 실행 1개 | 1 유지 |
| JINA_MAX_CONCURRENT | fetch 세마포어 기본 50 | browser 실측 실패율을 보고 운영 용량 결정. 현재 루트 배치는 최대 10개라 한 문항에서 자동으로 50개 browser를 여는 것은 아님 |

`jev_reads`는 RawTree 선별에서 별도로 사용하는 상한이 아니라 direct/query 합계에 대한 검증 값이다. 6→8 변경 시 `jev_reads=8, direct=2, query=6`을 함께 바꿔야 한다. 현재 `jev_floor`는 서로 다른 두 단계에 결합돼 있으므로, 나중에 이 값만 튜닝해 한 단계의 효과라고 해석하면 안 된다.

번들에는 별도 top-k가 없다. 기준 이상 번들 전부와 목적별 최고 번들을 남기며, 그 안의 청크만 평가한다. 이 구조는 유지한다.

출력 16,000 × 검색 10회는 d3 기준으로만 160,000토큰이다. 메인 context 122,880과 동일 tokenizer가 아니고, 그 외 검색 결과·추론·응답도 들어간다. 따라서 검색당 출력량을 단순히 늘리는 것은 전체 대화 근거 손실과 연결된다.

## 실제 저장 결과에서 볼 수 있는 범위

최신 batch64 실행의 q57에서 두 검색 모두 최종 페이지 6개를 선택했지만 실제 반환 청크에 기여한 페이지는 각각 3개였다. 반환 핵심 그룹은 첫 검색 direct=3/query=8, 두 번째 direct=0/query=5였고, 출력은 9,310 / 5,533 d3 토큰이었다. 이는 페이지 6개 또는 청크 12개 상한이 항상 꽉 차는 것이 아님을 보여 준다. 8페이지로 늘리면 정답이 개선된다는 증거는 아니다.

첫 검색은 번들 25개 중 12개, 두 번째는 8개 중 6개가 세부 평가 대상으로 남았다. 최종 표본 1문항만으로 번들 임계값을 바꿀 근거는 없다.

## 비교 순서와 필요한 검증

1. Browser 원문 수집·재사용을 공통 기반으로 준비하고 기존 beam 정책을 대조군으로 남긴다. 같은 쿼리·원문에서의 비교와 자유롭게 쿼리가 달라지는 전체 실행을 구분한다.
2. Beam과 best-first를 같은 루트 10, 깊이 5, 예산 50, 페이지 2+4, 청크 4+8로 비교한다. best-first의 link floor는 0과 0.01을 비교해 중단 조건 효과를 분리한다.
3. 탐색 방식 선택 후 페이지 2+4와 2+6을 비교한다. 깊이, 출력 길이, 번들 임계값까지 동시에 바꾸지 않는다.
4. 추가 확인: 우수한 세 번째 링크 보존, 중복 후보 보충, 여러 깊이의 우선순위, 같은 페이지 새 쿼리 재평가, 깊이/총예산 경계, 네트워크 완료 순서와 무관한 선택, 실패 페이지가 있어도 완료 근거 전달, browser 본문 재사용.
5. 정답률뿐 아니라 반환된 유효 근거, 새 후보 발견, 이미 성공한 문항의 회귀, 방문·기여 페이지의 depth/root 분포, 문맥 잘림을 함께 본다. 평가 key 수를 줄이는 것을 성공 기준으로 삼지 않는다.

LDS/MCTS/A*를 동시에 도입할 필요는 없다. MCTS는 추가 reward/rollout 설계가 필요하고, A*는 현재 d3 점수로 비용 하한을 정의할 수 없어 최적성 보장을 가져올 수 없다. Best-first의 통합 범위가 가장 작고 현재의 평가·청크 파이프라인을 그대로 검증할 수 있다.
