# JevTree v65: 300문항 확대 판단

대상: `runs/test/20261003-1643_jevtree_gpt-oss-20b_browsecomp_jevtree_v65_10`.
10문항 모두 완료했고 실행/채점 오류는 0이다. IDs는 3, 7, 8, 13, 15, 21, 22, 26, 27, 32.
비교 실행의 원 질문·gold가 같은지 문항별로 검증했다. 집계 원본은
`analysis/jevtree_v65_matched_comparison.json`이다.

## 결론

베이스라인 초과 성능을 기대하며 현재 버전을 곧바로 300문항으로 확대할 근거는 약하다.
v65의 정답은 q8 하나로 v63과 동일하다. RAgent/search-o1 대비 단독 승리·패배는 각각 0/0,
DepthSearch v8 대비 0/1(q26)이다. frozen DepthSearch 대비는 q8에서 1승이 있으므로
모든 베이스라인보다 못한 것은 아니다. 전체 연구 목표가 주요 베이스라인을 넘는 것이라면
현재 관측은 우위를 보여주지 못한다.

이 10문항은 이미 개선 판단에 사용한 개발 표본이다. 20개의 독립 표본처럼 이전 실행과
합쳐 계산하면 안 된다. 10개로 300개의 성능을 단정할 수 없으므로, 추가 평가 예산을 쓴다면
현재 코드를 고정하고 아직 분석하지 않은 동일 문항 30개를 먼저 비교하는 쪽을 권한다.
단독 정답의 순증가와 비용을 보고 다음 확대를 결정한다. 임의의 작은 승수로 통계적
우월성을 확정하지 않으며, 이번 10개에 맞춰 계속 프롬프트를 고치는 것도 권하지 않는다.

## 같은 10문항 비교

| 방법 | 정답 | 정답 ID | fetch 시도 | 기반 LLM 호출 | 문항 평균 초 |
|---|---:|---|---:|---:|---:|
| RAgent frozen | 1 | 8 | 10 | 145 | 127.1 |
| search-o1 frozen | 1 | 8 | 804 | 762 | 1323.2 |
| DepthSearch frozen | 0 | 없음 | 176 | 438 | 755.7 |
| DepthSearch v8 | 2 | 8, 26 | 461 | 1057 | 1515.3 |
| JevTree v63 | 1 | 8 | 2559 | 488 | 3275.4 |
| JevTree v65 | 1 | 8 | 2856 | 536 | 3701.3 |

시간은 과거 실행과의 관측 비교이며 하드웨어·API 상태를 통제한 속도 실험이 아니다.
기반 LLM 호출 수에는 JEV 호출이 포함되지 않는다. v65는 search-o1보다 기반 LLM 호출이
약 30% 적고 입력 토큰도 약 12% 적다는 장점이 있지만, JEV 호출 2543회/입력 4326만 토큰이
별도로 추가된다. 가격 정보를 확인하지 않았으므로 금액으로 환산하지 않았다.

v63 대비 v65는 fetch +11.6%, 기반 LLM 호출 +9.8%, 기반 입력 +8.6%, JEV 입력 +27.4%다.
v65의 성공 페이지는 2095개, 독해는 400개, fetch 실패 335개, 중복 426개다.
성능 상승 없이 더 많은 탐색을 사용했다. 이 차이를 특정 변경 하나의 인과 효과로
해석할 수는 없다(복수 변경·모델 샘플링·검색 결과 차이).

300개를 단순 선형 환산하면 fetch 85,680회, JEV 입력 약 12.98억 토큰,
기반 LLM 입력 약 2.55억 토큰이다. 실제 문항 난도와 중단 시점에 따라 달라진다.

## 실제 궤적

### q8: 정답 후보를 빨리 확보했지만 끝내는 데 더 오래 걸림

v65의 두 번째 검색에서 Michael Radford → White Mischief 영화 → Box Office Mojo/IMDb
경로로 실제 정답 자료를 확보했다. 영화 페이지의 후보 식별/조건 검증 점수는 0.44/0.73,
Box Office Mojo는 0.49/0.80이었다. 후자는 depth 3에서 reader가 읽고 제목·출시일·107분
상영시간을 명시했다. 따라서 JEV 재귀 탐색이 유용한 사례라는 평가는 유지된다.

그러나 v65는 전체 검색 10회/fetch 350회/4640초를 사용했다. v63은 검색 5회/fetch 156회/
2292초였다. v65는 6~10번째 검색에서 James Fox의 종교·복귀 나이를 반복 조사했다.
RAgent와 search-o1도 맞혔으므로 추가 정답의 증거는 아니다.

근거: 최신 q00008/trace.jsonl 633행(reader: Box Office Mojo), 636행(IMDb), 638행(Radford),
q00008/response.json 검색 2, 5~10 및 최종 응답.

### q21: 유용한 경기에 도달했으나 관계를 잘못 연결

v65 여섯 번째 검색에서 Dexerto의 `t1-hammer-mad-lions-in-second-fastest-game-in-msi-history-2140880`
기사를 depth 1로 읽었다. 후보 식별/조건 검증 점수는 0.58/0.57.
원문은 MSI 2019 IG–SKT의 16:01 기록과 JackeyLove의 Draven이 Teddy의 Sona를 상대했다는
문장을 담고 있다. reader는 이를 질문의 비전형적인 듀오인 Draven+Sona로 묶고,
서로 다른 팀 소속 선수 둘을 조사 대상으로 제시했다. 이는 원문의 상대 관계와 질문의
같은 팀 선수 관계를 혼동한 것이다.

메인 7턴은 실제로 이 단서를 언급했지만 Caps/Perkz로 넘어가 나이를 검색했다.
최종 답은 Fnatic이었다. 좋은 페이지가 단순히 전달되지 않은 문제가 아니다.

비교: search-o1도 첫 검색에서 같은 Dexerto 기사를 읽고 2019 MSI/16:01 기록을 받았다.
그 첫 독해에는 Teddy/Sona 이름이 없었으므로 v65가 인물 단서를 더 남긴 차이는 있다.
하지만 페이지 접근 자체가 JEV만의 우위는 아니며, 최종 추가 정답으로 이어지지도 않았다.
이전에 검토한 DS v7은 이 문항을 맞혔지만 전체 77문항 완료 실행이므로 주 비교 표에서는
300개가 완료된 v8을 사용했다.

근거: 최신 q00021/trace.jsonl 402/404행(JEV가 본 원문), 503행(reader),
q00021/response.json 메인 7턴. search-o1 frozen q00021/response.json 첫 도구 반환.

### q22: 이전의 유망 후보 확보가 재현되지 않음

v63에서는 12th Fail을 읽고 메인에 전달했지만 후속 검증을 하지 않았다.
v65에서는 JEV에 전달한 페이지 본문, reader 출력, 메인 도구 반환에서 `12th Fail` 후보를
찾지 못했다. 이번에는 fetch 441회/reader 54회를 사용하고 The Greatest Beer Run Ever로
답했다. 그 영화의 Wikipedia는 식별 0.56/검증 0.83으로 선택됐다.

독해 자료는 실재 후보의 개봉·원작·감독·출연진을 설명한다. 하지만 핵심 경찰/사기 조건은
IMDb와 Yahoo 독해에서 확인되지 않았다고 명시되어 있고, Wikipedia reader는 사기라는
설명이 없다고 하면서도 도덕적 동기를 연결해 보충했다. 일부 공통 조건의 높은 검증 점수가
전체 후보의 적합성을 보장하지 않는 사례다. 점수 0.83을 정답 확률로 읽으면 안 된다.

근거: 최신 q00022/trace.jsonl 874행(IMDb), 878행(Wikipedia), 1208행(Yahoo), response.json.

### q26 및 나머지

q26의 첫 검색은 이전처럼 Ghana/French를 가정하지 않았지만, 이후 Zimbabwe/Morocco/
Angola/Uganda를 바꾸며 검색했다. Abdisalam 후보는 전달되지 않았고, v8이 이긴 문항을
회복하지 못했다. 원문에서 Somali/Ibrahim 문자열을 찾을 수 있는 경우도 있었지만 언어
메뉴·다른 선수 이름이어서 정답 후보 확보로 세지 않았다.

10문항의 검색어·최종 응답·reader 후보 출현을 확인했다. q3/q7/q27에서는 목표 식별자가
reader에 도달한 흔적을 찾지 못했다. q13의 Red Lake, q32의 Australian 등 단순 문자열
출현은 다른 인물/사이트 메뉴와 관련된 경우여서 추가 정답 가능성으로 부풀리지 않았다.
모든 페이지 원문 전체를 의미적으로 정독한 것은 아니며, 문자열 검색은 관련 구간을
찾는 수단으로만 사용하고 핵심 비교 문항의 앞뒤 추론과 원문을 직접 대조했다.

## 실행 상태와 변경 검증

- JEV 요청 실패는 0. reader는 저장된 프롬프트대로 자유 서술이며 JSON 검증 경로가 없다.
- 별도 질문 조건 추출은 q8/q26/q27/q32에서 각각 한 번 이상 실패했다. q8/q26은 정확한
  부분 문자열 검사, q27/q32는 JSON 문법 오류였다. q27은 두 번 실패해 원 질문 전체로
  대체했고 다른 세 문항은 재시도에 성공했다. 이 불안정성은 reader가 아니라 조건 추출이다.
- 내가 제안했던 변경의 성능 개선은 이번 결과에서 확인되지 않았다. 조건 추출·점수 분리가
  유효하다는 가정으로 추가 복잡성을 늘릴 근거도 현재 부족하다.
- 이번 작업에서는 분석 파일만 생성했으며 코드 수정이나 추가 유료 실행은 하지 않았다.
