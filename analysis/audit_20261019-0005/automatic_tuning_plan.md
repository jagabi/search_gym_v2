# 기존 d3 자동 탐색 구조 안의 튜닝 제안

2026-10-19. 제안만 작성했으며 운영 코드·설정은 변경하지 않았다.

## 고정하는 구조

메인 모델은 web_search의 질의를 정하고 반환된 원문 근거로 답한다. 각 검색 안의 페이지 평가, 링크 평가와 후속 확장, 페이지/번들/청크 선별은 d3가 맡는다. best_first를 유지한다. read_source, continue_search, 별도 메인 상태 갱신기, 메인에 의한 문서 재선별을 추가하지 않는다. 검색 최대 10회, d3 HTTP당 질문 1개 및 4개 웨이브 전체 완료 후 다음 웨이브를 유지한다.

## 현재 코드에서 실제 조절되는 것

- jev_entries: 검색 순서대로 최초 방문하는 결과 수다. 메인이 다시 선별하는 top-k가 아니다.
- jev_expand_batch: 내부에서 동시에 진행하는 페이지 작업 수다. d3 HTTP 웨이브 크기와 별개다.
- jev_fetch_budget: 검색 1회 전체의 방문 노드 수다. 실패/재사용 노드도 포함한다.
- jev_depth: 방문 깊이 상한이다. 해당 깊이에서는 본문을 평가하지만 자식 링크를 더 평가하지 않는다.
- jev_link_floor: 이미 평가한 링크의 확장 자격을 제한한다. 그 링크를 판정한 HTTP 비용을 되돌려 주지 않는다.
- jev_page_tokens: 페이지 미리보기와 링크 추출 범위다. 선택된 문서의 전체 본문 청킹 범위를 자르는 설정은 아니다.
- jev_direct_reads/jev_query_reads: 탐색 종료 후 실제 청킹/읽기할 페이지 수다. jev_reads는 이 합과 맞춰야 한다.
- jev_direct_chunks/jev_query_chunks: 선택된 페이지들을 합친 청크 후보에서 반환할 수다. 페이지마다 각각 적용되는 수가 아니다.
- jev_floor: 번들과 최종 청크에 함께 적용된다. 번들은 각 목표의 최고 점수 번들을 최소한 남긴다. 번들 하한만 따로 올리는 옵션은 현재 없다.
- jev_branch/jev_frontier_width: beam에만 적용된다. 현재 best_first에서 이 값을 바꿔도 확장 폭은 바뀌지 않는다.
- explorer_prompt: raw 경로에서 reader 모델을 부르지 않으므로 실제 d3 지침은 rawtree.py의 decision_question과 preview의 링크 질문이다.

## 저장 로그로 확인한 수치

원래 자동 탐색 p9의 링크 판정은 78,433회. 점수 중앙값 0.02352, 0.05 미만이 55,584개(70.9%). 하지만 실제 방문한 링크 2,227개 중 0.05 미만은 205개(9.2%)다. 0.01 미만은 21개(0.94%), 0.03 미만은 132개(5.9%). 그러므로 '하한 0.05로 올리면 비용 71% 절감'이라고 계산하면 틀리다. 현재 방문도 상위 링크 중심이며, 초기 링크 판정 비용은 그대로 든다. 점수는 정확한 성공 확률로 보정된 값도 아니다.

링크를 가진 부모의 후보 링크 수는 평균 42.19, 중앙값 36, p95 104였다. 한 부모에 링크가 많이 달리면 작은 방문 예산에서도 판정 시간이 커질 수 있다.

성공한 초기 검색 결과 원문 174개를 저장 로그에서 표본 추출해 동일한 로컬 d3 tokenizer/링크 추출기로 비교했다. 문항당 최대 20개, 앞선 검색 결과 6개에 해당하는 고유 원문을 사용했다. visited 집합은 비워서 길이 효과만 비교했다.

| 미리보기 | 후보 링크 합계 | 문서당 평균 | 5000 대비 감소 |
|---|---:|---:|---:|
| 5000 tokens | 4189 | 24.07 | — |
| 4000 tokens | 3630 | 20.86 | 13.3% |
| 3000 tokens | 2909 | 16.72 | 30.6% |

이는 첫 진입 문서 표본의 후보 링크 감소율이다. 전체 실행시간 절감률이나 자식 문서의 링크 밀도, 정답 보존율이 아니다. 뒤쪽 링크/소개를 잃을 수 있어 4000과 비교할 가치가 있다. 원문의 전체 본문은 선택된 뒤 기존대로 청킹한다.

depth 3은 무조건 개선이라는 뜻이 아니다. p9의 읽은 페이지 336개 중 depth 4~5도 75개였다. 그중 정답에 필수였던 페이지의 비율은 확인되지 않았다. 깊이 때문에 필요한 경로가 끊긴 사례가 나오면 depth 4를 비교한다. 동시에 전역 정책을 바꾸거나 메인에 확장 권한을 돌리지 않는다.

이 설정에서 방문은 문제당 최대 100개, 읽기는 검색당 최대 3개/문제당 최대 30회다. 깊이 3과 방문 수 10은 각각 상한이며 반드시 그만큼 사용하거나 그 깊이까지 도달한다는 뜻은 아니다. entries 6이면 초기 검색 결과가 충분한 검색에서 추가 링크 방문 슬롯은 최대 4개 남는다.

## 프롬프트 수정 범위

### 메인 검색/답변 지침

- 처음부터 추측한 인명·도시·연도 한 값으로 검색을 좁히지 않는다. 질문이 직접 준 드문 작품명·관계·조건을 우선 질의한다.
- 범위 조건을 경계값 하나의 완전일치 검색으로 바꾸지 않는다. 출판연도·통계 관측연도·측정 단위를 구별한다.
- 반환된 근거가 기존 추측을 반박하면 그 추측을 다음 질의의 확정 조건으로 사용하지 않는다. 같은 단서를 반복 확인하기보다 미확인 관계를 질의한다.
- 유력 원문에 접근하지 못하면 반환된 제목·저자·출판 정보로 다른 원문 경로를 검색한다. 별도의 읽기 도구는 제공하지 않는다.
- 최종 답은 실제로 지지되는 요청 사실과 출처로 제한한다. 핵심 조건의 반례를 꾸며서 해결하지 않고 추론 메모를 답변에 넣지 않는다.

### d3 링크 평가 지침

- 현재 질의의 미확인 사실을 밝힐 구체적인 목적지인지 평가한다. 원문, 공식 인물 소개, 작품의 출연진, 논문의 본문/부록처럼 관계를 이어줄 링크를 인정한다.
- 답의 완성형이 당장 나타나지 않는 중간 근거도 허용한다. 반례를 얻을 수 있는 링크도 유효하다.
- 제목/주변 텍스트에 질문 단어가 반복된다는 이유만으로 높은 점수를 주지 않는다. 무관한 탐색 메뉴와 질문 복제 페이지는 실제 사실 근거와 구별한다.
- 도메인/인명/문항별 분기나 URL 규칙을 추가하지 않는다. 현재 입력에 이미 있는 URL·anchor·주변 원문을 그대로 사용한다.

### d3 페이지/번들/청크 평가 지침

- 근거의 주체·시점·관계가 정확히 맞는지 평가한다. S56처럼 다른 사람의 페이지를 후보의 전기로 취급하지 않는다.
- 질문 문장을 재진술한 콘텐츠와 독립적으로 확인 가능한 사실을 구별한다.
- 질의 가설의 반박, 다음 식별 관계를 제공하는 부분 근거를 낮게만 평가하지 않는다. 기존 query_answer의 부분 근거 허용을 구체적인 기준으로 명료화한다.
- 인증/로그인/접근 화면에서 제목만 관련 있다고 읽을 가치가 높은 것으로 평가하지 않는다.

지침 변경도 실제 d3 점수 분포를 바꿀 수 있다. 프롬프트와 모든 수치를 한꺼번에 바꾼 결과만 보고 어느 변경이 좋아졌다고 결론내리지 않는다.

## 20분 목표와 검증 순서

4개 웨이브, 활용률 약 0.75~0.81, 링크 판정 평균 약 1.43초를 쓰면 링크 1000개에 약 7.4~7.9분, 1600개에 11.8~12.7분이다. 100페이지의 2종 페이지 판정은 약 1.3분, 30회 읽기의 번들/청크 판정은 과거 평균으로 약 5.5~6.1분이다. fetch·검색·메인·로컬 청킹에 수분이 더 들고 일부는 겹친다.

10회를 모두 사용하는 어려운 문제라면 대략 20분 전후~25분 정도가 가능한 첫 추정이며, 20분을 보장하는 설정은 아니다. 링크 수가 약 1000개 안팎으로 유지되는지, 깊은 관계를 놓치지 않는지 실측해야 한다. 55분/10문제인 progressive 결과를 이 자동 탐색 설정의 시간 예측에 사용하지 않는다. 시간 목표만 맞추려고 문제 타임아웃으로 자르지 않는다.

1. 현재 복구 설정을 대조군으로 기록한다. 이후 모든 실험은 메인 도구가 web_search만인지, 내부 자동 확장이 실제 발생하는지 확인한다.
2. 위 숫자 조합을 파라미터 후보 A로, 프롬프트는 그대로 두고 비교한다. 검색 수뿐 아니라 parent 수·link 요청 수·depth별 방문/읽기·첫 근거 반환 시간·정답 근거를 기록한다.
3. A에서 메인 검색 프롬프트만 바꾼 B를 비교한다. d3 프롬프트 변경은 다음 C에서 따로 비교한다.
4. 필요한 경우 한 축씩 비교한다: page_tokens 3000↔4000, fetch_budget 10↔12, depth 3↔4, link_floor 0.03↔0.05. 별도 호출형 파이프라인이나 메인 제어 도구는 도입하지 않는다.
5. 분기/페이지 top-k와 청크 top-k를 동시에 줄이지 않는다. 새 본문 후보 누락이면 entries/reads를, 깊이 제한 누락이면 depth를, 내부 링크 평가 폭증이면 prefix/방문 예산을 조절한다.
