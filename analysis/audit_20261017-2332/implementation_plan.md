# 20분 목표 탐색 개선 계획

## 유지할 조건

- baseline과 동일하게 max_searches=10. 10회를 목표 사용량으로 강제하지 않는다.
- 시간 초과로 잘라서 성능 목표를 달성하지 않는다. 정상적인 근거 확보와 최종 답변까지 걸리는 시간을 개선한다.
- d3는 HTTP당 질문 1개, 웨이브 4개, 전부 완료한 뒤 다음 웨이브. rolling 전송으로 바꾸지 않는다.
- Browser/Jina, Docling 청킹, 번들 선별 후 청크 판정 흐름을 유지한다.
- 인명·국가·문항별 규칙이나 인증 화면 문구 사전을 만들지 않는다. Reader의 지원 기능·메타데이터를 먼저 조사한다.
- 운영 코드 변경 전에 구현 상태와 재현 테스트를 확인한다. 구현 및 검증 결과는 [implementation_result.md](implementation_result.md)에 기록했다.

## 원래 문제와 적용 상태

1. p9 실행은 VERSION=9였으나 실제 traversal=best_first. progressive 초기 반환, read_source/continue_search, RawResearchState, progressive 최종 근거 재검토가 활성화되지 않았다. 현재 로컬 YAML은 progressive이므로 저장된 실행 설정과 현재 기본값을 구별한다.
2. 64회 검색 중 55회가 50페이지까지 탐색한 뒤 근거 반환. d3 101,222회 중 링크 78,433회. 요청 웨이브는 정상이나 작업량이 너무 컸다.
3. 598: 유력 PDF 대신 인증 화면이 반환됐지만 성공 문서로 취급. 주변 단서 반복 후 HDS 검색은 예산 소진으로 거절.
4. 746: Rockefeller 출생지 근거가 전달됐는데 Hamlin 가설 유지. 스스로 발견한 연대 모순을 후보 갱신에 반영하지 못함.
5. 1230: 교통 통계의 연도/측정 기준 혼합, 비슷한 검색 반복, 수치 조건 오류와 추측 메모가 최종 출력에 노출.
6. 516: 이름은 정답 처리됐지만 감독·작품 설명이 잘못됨. 정답 문자열과 근거 품질은 별도 평가 필요.
7. progressive 구현 자체도 부모 최대 4개 지정, research 선택 입력, 목표 변경 시 재평가, 유력 원문의 강제 새로고침 등의 점검이 필요. 활성화만으로 모든 문제가 해결됐다고 보지 않는다.

## 작업량 및 시간 모델

실측 평균: search 3.10초, fetch 5.94초, page 판정 1.266초, link 판정 1.431초, bundle 판정 1.714초, chunk 판정 0.531초, main 3.643초.

page/bundle/chunk는 목표 2종으로 각각 2회 판정, link는 1회. d3 처리시간 합을 4×0.81로 나누어 웨이브 효율을 반영한다. 읽기 1페이지당 bundle 4.71개와 후보 chunk 21.73개, 로컬 청킹 약 1.04초. fetch 4병렬 가정, 단계 사이 겹침은 제외.

| 검색 S | 추가 방문 행동 E | 방문 P=4(S+E) | 본문 읽기 R | 신규 부모 링크 평가 | 링크 합 | 예상 |
|---:|---:|---:|---:|---:|---:|---:|
| 4 | 6 | 40 | 30 | 6 | 600 | 13.4분 |
| 10 | 6 | 64 | 32 | 6 | 600 | 15.4분 |
| 10 | 6 | 64 | 40 | 6 | 600 | 17.2분 |
| 10 | 6 | 64 | 48 | 6 | 600 | 19.0분 |

확장 행동이 기존 평가 frontier를 소비하기만 하면 신규 부모 링크 평가는 발생하지 않는다. 위 모델은 매 행동에서 새 부모 1개를 평가한다고 가정한다. 부모당 평균 100링크 가정이며, 200링크이면 6개 부모에 대해 약 4.4분 증가한다. 문서 길이, fetch 지연, 서버 상태에 따른 미래 시간 보장은 아니다.

40페이지를 전역 고정 상한으로 두지 않는다. 정상 목표는 방문 약 40~64개, 본문 읽기 약 30~40개, 신규 부모 링크 평가 약 6회다. 초기 읽기는 행동당 2개(원질문 1 + 현재 목표 1), 세 번째 페이지는 별도 미확인 조건을 확인할 필요가 있을 때 추가한다. 무조건 3개를 읽으면 10검색 시 약 48페이지 읽기가 되어 여유가 작다.

## 구현 순서

### 1. 실행 정책 확정 및 검증

- YAML/CLI 합성 후 실제 설정을 한 번 출력하고 run config에 저장: traversal, 도구 목록, HTTP 웨이브, 페이지 단위, 최종 검증 여부.
- 새 실험 실행은 progressive를 명시한다. 명시한 기대 정책과 실제 정책이 다르면 모델 호출 전에 오류로 알려준다. legacy 비교 실행은 의도적으로 허용한다.
- 버전 번호와 활성 정책을 구분해 기록한다.
- 실제 Agent 경로에서 read_source/continue_search, 상태 주입, 최종 근거 검토가 연결됐는지 통합 검증한다.

### 2. 기본 작업량 변경

현재 지원 설정의 후보: max_searches=10, max_turns=24, search_results=10, jev_entries=4, jev_expand_batch=4, jev_fetch_budget=16(검색당), jev_depth=5. 초기 읽기 jev_reads=2, jev_direct_reads=1, jev_query_reads=1.

웨이브 4/packet 1/inflight 4 유지. chunk 512, bundle/page 5000, direct/query chunks 4/8, overlap 2, neighbor 1, output 16000, floor .15/link floor 0 유지. 초기 실험에서 임계값까지 동시에 변경하지 않는다. max_turns=24는 추가 읽기 등 도구 행동 여유이며 목표 호출 수는 더 적다.

- 부모 선택 상한을 페이지 방문 batch와 분리해 1로 둔다. 현행 jev_branch는 이 기능을 제공하지 않는다.
- 초기 방문에서 링크 평가가 발생하지 않도록 보장한다.
- 기존 frontier의 유망 링크를 먼저 소비하고, 아직 필요한 근거 경로가 있을 때만 새 부모를 확장한다.
- 자료형과 남은 조건을 근거로 세 번째 페이지 읽기 또는 명시적 read_source를 선택한다. 전체 방문/읽기/부모 판정을 기록하고 예상 작업량을 planner에 전달한다.
- 시간/누적 횟수만으로 답변을 강제하지 않는다. 종료는 요청한 사실과 식별 근거의 확보, 또는 현재 경로의 근거 부족을 명확히 정리하는 방식으로 한다.

### 3. 후보 갱신과 반복 탐색 개선

- candidate별 supported/contradicted/unknown과 출처를 실제 도구 인자와 상태에 연결한다. 지금처럼 선택 입력 누락이 조용히 계속되지 않게 설계한다.
- 처음에는 빈 후보 상태를 허용하고 이후에는 변경분과 next_gap을 전달한다. 매 행동마다 별도 요약 모델 호출을 추가하지 않는다.
- 같은 단서 재검색에는 새로 확인하려는 관계를 명시하게 한다. 문자열 유사도만으로 검색을 금지하지 않는다.
- 결정적 모순, 대안 후보, 아직 검색하지 않은 고유 단서를 다음 행동 선택에 반영한다. 문항별 정답 이름을 prompt에 넣지 않는다.
- 목표가 바뀔 때 필요한 query 판정만 재평가할 수 있는지 점검한다. 원질문 판정/문서/청킹 재사용은 모델·내용·질문·정책 버전이 같은 경우에만 적용한다.

### 4. 유력 원문 복구

- Jina가 제공하는 상태·자료형·렌더링·대기·재시도 옵션을 실제 설치 버전 기준으로 조사한다.
- 통신 성공, 원문 확보, 질문에 대한 유용성을 구별한다. 인증 화면을 논문 본문으로 저장한 사례를 재현한다.
- 캐시된 내용이 원문 미확보로 판단되면 명시적으로 다시 가져올 수 있는 경로를 제공한다. 같은 잘못된 캐시를 재사용하는 루프를 막는다.
- 지원되는 Reader 옵션으로 재시도하거나, 모델이 논문 제목·저자·기관 저장소 등 대체 출처를 검색하도록 한다. 무제한 재시도나 인증 우회는 하지 않는다.

### 5. 근거 기반 최종 답변

- 최종 출력은 실제 반환된 근거와 후보 상태로 검토한다. 불확실한 이전 추측을 사실로 승격하지 않는다.
- 이름만 맞는 경우에도 작품·감독·날짜·수치·연도·측정 기준이 근거와 일치하는지 확인한다.
- 추론 메모가 최종 text에 섞이는 응답 형식 문제를 별도 재현해 원인을 수정한다. 정상 답변 문자열을 임의 규칙으로 잘라내는 방식은 피한다.
- 답변의 각 설명을 뒷받침할 자료가 없으면 그 설명을 제외하거나 미확인으로 표시한다.

### 6. 검증과 비교

- 저장된 자료로 598 원문 미확보, 746 모순 및 대안 후보, 1230 반복 검색/숫자 조건, 516 설명 근거를 재현한다. 사실관계 처리의 검증이지 모델 정답을 강제하는 테스트가 아니다.
- 구조 테스트: 초기 링크 요청 0, 부모 최대 1, 추가 방문 최대 4, 4요청 barrier, 캐시 새로고침, 검색 10회 접근 가능, 실제 progressive 도구/상태/최종 검증.
- 서버 최소 실행으로 schema 수용과 도구 사용을 확인한 뒤 소수 문항, 마지막에 동일 diagnostic10으로 비교한다.
- 주요 지표: 정답률, 설명의 근거 일치, 전체 시간/최대 시간, 20분 초과 수, 첫 유효 근거 반환 시간, 단계별 판정량과 서비스 시간, 검색별 신규 근거, 반복 읽기/재평가, 원문 복구 성공.
- 속도만 좋아지고 정답이나 근거 전달이 나빠지면 성공으로 판정하지 않는다. 문제가 해결되기 전에 10개 전체를 반복 실행하지 않는다.
