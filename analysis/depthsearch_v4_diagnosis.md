## 3. 가장 큰 구조적 실패: 자식이 원 질문 전체를 다시 해결한다

### q00614: 다른 결투의 근거가 정답을 덮어씀, F1 0.8889 → 0.1538

1. 부모는 `Yami_Yugi_and_Mako_Tsunami's_Duel`이라는 정확한 출발 페이지를 읽었다.
2. 자식들은 Horn Imp / Giant Soldier of Stone / Silver Fang / Curse of Dragon의 ATK·DEF를 읽었다.
3. 카드 속성을 얻은 자식이 '전체 결투 정보가 없다'를 Missing으로 적고 다시 결투 페이지를 찾았다.
4. Curse of Dragon의 출연 목록에서 Episode 005로 내려갔다.
5. 그 페이지 원문은 `Featured Duel: Yami Yugi vs. Weevil Underwood`이고 Mako 문자열은 없다.
6. reader는 여기의 8개 몬스터를 근거로 반환했고, 메인과 최종 합성은 이를 Mako 결투 목록으로 채택했다.

부모 원문에는 Feral Imp 소환도 있지만 부모 reader는 카드 목록에 없다는 이유로 제외했다.
즉 최초 후보 목록부터 불완전했고, 잘못 확장된 하위 문서가 이를 더 크게 망가뜨렸다.

핵심은 URL을 만들었느냐보다 **이 자식에게 맡긴 일이 무엇인가**다.
카드 reader의 임무는 그 카드의 ATK/DEF 추출이면 끝나야 한다. 전체 결투 목록이 없다는 이유로
재귀를 계속하면 이미 확보한 대상 범위를 잃는다. 부모 사실의 재인용을 막는 것과 별개로,
사실 주장이 없는 국소 작업 지시(대상·필드·기간·사건)를 추출 입력에 전달할 필요가 있다.
현재 `_extraction_message`는 원 질문과 일반적인 추출 지시만 주며, 정확한 국소 목적은 전달하지 않는다.

제안: 같은 reader 안에서 `이 카드의 ATK/DEF`, `이 연도의 F30-39 1위`처럼 국소 임무를 명시하고,
국소 임무 완료와 원 질문 완료를 구분한다. 다른 사건/연도/대상 페이지는 내용이 풍부해도 비교 근거로
승격하지 않는다. 새로운 도구나 외부 실행 시스템은 필요 없다.

## 4. 원문을 확보해도 필요한 부분이 모델에 도달하지 않는다

### q00414: CSV의 정답 국가가 입력 절단 뒤에 있음

- CO2 CSV는 High-income countries의 과거 연도 부근에서 잘렸다.
- 항공 승객 CSV는 El Salvador의 1990년대 부근에서 잘렸다.
- 실제 추출 입력에는 Iran의 2020/2021 행이 없다.
- `filter=Country:India`, `filter=Entity:China`, `filter=Saudi Arabia` 같은 추측 파라미터로
  주소를 바꿔도 동일한 앞부분이 다시 들어왔다. 이 문항에서만 fetch.truncated 18회다.
- 최종 답은 Canada지만, 필요한 비교값을 확보한 결과가 아니다.

### q00699: PDF 공백은 줄었지만 본론까지 읽지는 못함

추출 입력은 PDF 1~28페이지에서 잘렸다. 필요한 Phyllostominae와 정답 학명은 입력에 없다.
같은 자료를 다른 URL로 다시 받아도 1~28페이지가 반복됐다. 메인의 이미 읽은 페이지 재사용 19회,
자식 재사용 2회가 있었으며, 최종 답은 다른 분류를 섞은 Carollia였다.

### q00495: 행과 열의 의미도 무너짐, F1 1 → 0.4

15회 원문 절단. 최종 답에서 Switzerland의 GDP와 하루 평균 소득이 모두 94,761.81로 적혔다.
추출한 daily-income 표에서 빈 값 다음 GDP 열이 소득 열로 옮겨지는 사례도 보인다.
`download=top_n=10&year=2022`라는 추측 URL이 실제 top-10 표라는 보장은 없다.

전체 fetch.truncated는 68회이며 q00414와 q00495가 그중 33회다.
보조 문서 도구를 없앤 판단과 별개로, 제가 v4에서 앞부분 절단을 그대로 둔 것은 해결되지 않은
원문 전달 문제다. 공백 정리나 '잘린 부분은 unknown'이라는 프롬프트만으로 필요한 행이 생기지는 않는다.

제안: 기존 reader 내부에서 헤더/페이지 경계를 보존한 질문 관련 구간을 선택하거나 나누어 읽는다.
검색 횟수나 별도 계산 도구를 늘리는 문제가 아니다. 전체 후보가 필요한 목록은 일부 구간만 읽고
완료로 표시해서는 안 된다. 어떤 구간을 읽었는지와 미확인 범위를 기록하고, 기존 읽기 예산에서
분배해야 한다. 구체 구현과 비교 조건은 설계가 필요하며 아직 적용하지 않았다.
URL 별칭의 중복은 전체 내용 기준으로 판별하는 편이 타당하다. 일반적으로 query string을 삭제하면
서로 다른 실제 자료까지 합쳐질 수 있으므로 그렇게 처리해서는 안 된다.

- q00144: Cocke로 결론 내렸지만 답변 표 자체에 1662·1663년 'No mention'이 있어 every December 조건과 모순된다.
- q00148: 2023년 8·9·12월만 비교하고 '해당 없음'을 선언하면서 다른 달은 미확인이라고 동시에 적었다.
- q00503: Booker shortlist 후보보다 유명 Nobel 수상자들을 먼저 하나씩 확인하다 후보를 놓쳤다.
- q00611: TRAPPIST-1 e 한 개만 확보했다. 후보 목록이 완성되지 않은 상태에서 2017 조건과 맞지 않는
  TESS/TOI 관련 검색으로 이동했다.
- q00849: Mary Cassatt 일부 작품만 남고 전체 대상 작가/작품 범위가 완성되지 않았다.

검색어를 짧게 만들라는 프롬프트만으로는 다음에 확인할 후보가 정해지지 않는다.
제안: 첫 반환에서 후보 목록을 찾는 일과, 알려진 후보의 특정 조건을 확인하는 일을 분리한다.
reader의 Missing/Next links도 원 질문 전체가 아니라 현재 하위 작업에서 아직 남은 필드를 기준으로 만든다.
별도 상태 관리 도구 대신 현재 반환 구조와 메인 추론에 반영할 사항이다.

## 6. 빈 응답 0이지만 q00577은 여전히 실행 실패

검색 0, 페치 0, reader 0. 메인의 첫 본문은 다음과 같은 도구 호출 JSON이었다.

```json
{"name":"functions.web_search","arguments":{"query":"DOE registered gasoline cars 2021 2022 state table"}}
```

이것을 실제 도구 호출로 인식하지 못해 최종 답변 단계로 넘어갔다. 최종 모델 응답이 두 번 모두
빈 문자열이자 기존 JSON을 usable_draft로 살려 `answered`로 저장했다.
따라서 empty_responses=0, run_errors=0, invalid_tool_calls=0으로 집계됐지만 사용 가능한 답이 아니다.

현재 함수에 저장된 본문을 넣는 오프라인 재현 결과:

- recover_tool_calls: False
- _clean_answer: JSON 그대로 유지
- _looks_like_action: False

지난 수정의 계획문/프로토콜 방지는 이 순수 JSON 형태를 놓쳤다. 테스트 통과가 이 실출력까지
처리한다는 보장은 아니었다. 등록된 도구 이름·JSON 구조·필수 인자를 검증해 복구하거나 명시적인
프로토콜 실패로 분리하고, 최종 초안 대체 경로에서도 도구 JSON을 답으로 인정하지 않아야 한다.

## 7. finalized는 검증 성공 지표가 아니다

29개 finalized, 1개 answered. finalized는 현재 수집한 도구 결과로 새 답변을 작성했다는 뜻이다.
원문 재검증·대상 일치 검증·후보 완전성 검증을 코드가 수행했다는 의미가 아니다.
q00678의 산술 수정처럼 도움이 되는 경우와 q00614의 잘못된 사건 목록을 그대로 강화하는 경우가 함께 있다.
q00037은 성공한 페이지 페치가 0개인데도 자세한 비교표와 부정 결론을 만들었다.
완료 상태를 성능 증거로 쓰면 안 된다.

reader complete 252개도 출력 추출 완료를 뜻한다. reader relevance는 partial 243개, not_found 9개다.
사이트 메타데이터만 있어도 partial로 나오는 사례가 있어 dead_dive_rate=4.1%는
'95.9%의 확장이 정답에 유용했다'는 의미가 아니다.

## 8. 비용과 다음 우선순위

- 노드 상한 12 도달은 3/30문항뿐이다. 상한을 늘리는 것이 첫 처방일 근거는 약하다.
- 깊이 3은 17문항에서 사용했고 46노드를 열었다. '재귀가 실행되지 않았다'는 이전 문제는 해결됐다.
- 재사용 노트 100회 중 메인 52회, 자식 48회다. 네트워크 절약은 되지만 같은 긴 근거를 다시
  컨텍스트에 추가하는 비용과 정체를 막지는 못한다.
- reader 입력 토큰은 extract 3,944,418 + expand 5,210,861 + recover 141,990 = 9,297,269다.
  탐색 단계 입력이 추출 단계보다 크다. 같은 원문·부모 추론·저장 노트의 반복이 비용 검토 대상이다.

권장 순서:

1. q00577의 실출력으로 프로토콜/초안 복구 오류를 재현하고 수정한다.
2. 국소 작업 지시와 대상 범위를 자식에게 전달하고, 국소 임무가 완료되면 확장을 멈춘다.
3. 기존 reader의 긴 원문 구간 전달과 내용 중복 판별을 수정한다. 별도 계산·문서 도구는 추가하지 않는다.
4. 후보 발견과 조건 검증을 구분하고, 비교 필드/사건/연도 불일치가 최종 답에 섞이지 않게 한다.
5. 같은 코드를 고정한 baseline과 새 문항/반복 실행으로 평가한다. 기존 30개는 이미 여러 차례
   개선에 사용한 개발 문항이므로 독립 평가처럼 취급하지 않는다.

핵심 연구 방향: 출처별로 맡긴 하위 문제를 해결하고 필요한 근거를 부모에게 반환하는 재귀 탐색.
성공 사례와 실패 사례 모두 이 방향의 필요성을 보여주지만, 평균 성능의 우월성은 아직 입증되지 않았다.
