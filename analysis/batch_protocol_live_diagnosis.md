# DS v10: 실서버 프로토콜 진단 및 반영

2026-09-25. 사용자 요청에 따라 현재 설정의 gpt-oss-20b 서버로 직접 실행했다.
모델 호출 27회, 입력 109,517 / 출력 28,732 토큰. 검색·fetch·judge 호출 0회.
기존 benchmark run과 채점 결과는 수정하지 않았다. 상세: `batch_protocol_live_audit.json`.

## 실측

| 검사 | 결과 |
|---|---|
| 두 URL의 복수 native 호출, 기본 옵션 2회 + parallel_tool_calls=true 2회 | 모두 첫 URL 한 호출만 반환 |
| 저장된 선택 입력 2개 + parallel_tool_calls=true | 모두 한 호출 |
| 초기 배열 형식 진단 | 두 URL 전달 성공; 실제 입력 하나는 배열 대신 문자열을 반환 |
| 최종 배열 프롬프트 형식 진단 2회 | 모두 한 native 호출 안에 두 URL 배열 반환 |
| 최종 배열 프롬프트의 실제 저장 입력 6개 | 배열 문법 6/6, 허용 URL/ID 선택 5/6, 모두 한 URL만 선택 |
| 기존 실패 문맥의 새 마무리 단계 6개 | 정상 일반 응답 6/6, 도구 호출 없음 |
| 그중 2개를 기존 마무리 방식으로 재실행 | 정상 1/2, 빈 일반 응답 1/2 |
| q00026 추출 지시 수정 전후 | 둘 다 Abdisalam Ibrahim 보존 실패. 수정안에 원문에 없는 이름/행 생성 |

복수 호출 문제의 내부 원인이 모델·템플릿·서버 파서 중 무엇인지는 이 검사로 분리되지 않는다.
현재 서버에서 복수 native 호출에 의존하면 안 된다는 실행 근거는 확보했다.
배열은 전달 가능성을 확인했으나 실제 선택 폭 개선은 확인하지 못했다. q00013의
관측되지 않은 Wikipedia 주소는 운영 코드에서 거절되며, 이 진단에서는 도구를 실행하지 않았다.
일반 응답 6/6은 문법/종료 성공이며 근거의 정확성이나 최종 정답률 평가가 아니다.

## 반영한 변경

1. DS 진입 노드만 `web_fetch(urls=[...])` 사용. 재귀 자식의 `web_fetch(url)` 유지.
   새 도구나 하위 작업용 필수 문자열 인자는 추가하지 않았다. URL 목록은 현재 메뉴와
   대조하고 유효한 항목만 모델 순서대로 읽는다. 중복·예산 초과 항목은 실행하지 않는다.
   배열 자리에 문자열이 오면 임의 변환하지 않고 기존 한도 안에서 오류 복구한다.
2. 마무리 전용 시스템 프롬프트. 원 질문·현재 출처 상태·읽은 결과만 제공하고 선택 단계의
   시스템 지시 및 assistant/tool 행동 대화는 다시 넣지 않는다. 도구 제거와 none 유지.
   출처별 원래 근거는 마무리 결과와 별도로 메인에 계속 전달한다.
3. 진입 프롬프트·마무리 프롬프트·배열 스키마를 run에 저장. DS 캐시만 agent/48로 변경.
   RAgent/search-o1 설정·캐시 버전·공유 LLM 래퍼는 그대로다.

실험한 추출 문구는 **반영하지 않았다**. `searchgym/explorer.py`는 기존 상태와 동일하다.
추출 성능이 좋아졌다고 볼 근거가 없고, 예시 행 생성이 나타났기 때문이다.
검색 10회/결과 10개, 깊이 3, 재귀 노드 12, 자식 2, 루트별 확장 6 등 숫자는 변경하지 않았다.
오프라인 회귀 검사 153개 통과. 형식·배열 항목 검증·재귀·근거 보존·메인 복귀를 포함한다.

## 범위와 결론

이번 진단은 배치 전달과 빈 마무리 응답의 구조적 문제를 다뤘다. 최종 정확도·실행 시간·
토큰 효율을 측정한 end-to-end 실험은 아니다. 저장 입력은 개발 사례이며, 특히 마무리는
기존 실패 사례를 선정했다. 복수 URL을 명시한 형식 검사는 실제 선택 폭 평가에서 제외한다.

실제 입력 6개 모두 여전히 한 URL을 고른 점과 긴 원문의 후보 누락은 미해결이다.
따라서 이 결과를 근거로 300문항 전체 실행이나 성능 급상승을 권하지 않는다.
재귀 구조를 축소하거나 무조건 여러 페이지를 열도록 바꾸지는 않았다.
