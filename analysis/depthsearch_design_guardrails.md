# DepthSearch: 성과 이력에 근거한 설계 기준

2026-09-23. 방법 코드 변경 전 설계 메모. 저장된 실행 및 진단 문서를 재검토했다.
`independent_clues_v6_diagnosis.md`의 검색당 단일 진입 제안은 아래 기준으로 수정한다.

## 지켜야 할 정체성

메인은 전역 검색을 계획한다. 하위 노드는 현재 출처를 읽고, 그 출처에서 발견한
관계와 링크를 따라 필요한 다음 문서를 재귀적으로 읽는다. 부모는 출처별 결과를
받아 자신의 탐색을 이어가거나 종료한다. 메인은 재귀 반환 뒤 다시 판단한다.

깊이 숫자나 전용 프롬프트의 존재보다 이 역할 분리와 정보 전달이 핵심이다.
검색 결과를 전부 자동 독해하는 방식, 메인이 대부분 snippet만 보고 끝나는 방식은
현재 목표로 삼은 DS 동작과 다르다.

## 관측된 성과와 한계

### DeepSearchQA

현재 records.jsonl 재집계, 동일 300문항:

| 방법 | 평균 F1 | 0점 | 부분점수 | 만점 |
|---|---:|---:|---:|---:|
| RAgent | .3919 | 135 | 102 | 63 |
| search-o1 | .4424 | 124 | 102 | 74 |
| 이전 DS | .4148 | 151 | 63 | 86 |
| ds_evidence_completion | .4550 | 127 | 87 | 86 |

evidence_completion의 최초 진단 문서는 실패 재실행 전 .4406이었다. .4550은
실패 재실행이 반영된 현재 집계다. 따라서 이 상승을 단일 프롬프트 변경의 효과로
분리해 주장하지 않는다. 만점 총수가 같아도 같은 문항의 성공이 보존됐다는 뜻은 아니다.

유지할 방향: 출처별 근거/행 보존, 부모 근거의 자식 추출 오염 방지, 후보별 빠진 조건
완성, 정상 초안 보존, 근거 있는 답 항목을 전체 조사 미완성 때문에 버리지 않기.

### BrowseComp

| 버전 | 정답 / 300 | 관측 |
|---|---:|---|
| 최초 DS | 30 | 검색 소진 뒤 읽기 집중, 무진전 재요청·URL 실패 |
| v3 | 37 | 메인 검색/하위 읽기 분리, 그러나 빈 답 48개 |
| v4 | 38 | 종료 경로 개선, 빈 답 2개; 선택·상태 갱신 실패는 잔존 |
| v5 | 미완주 | 진입 재선택·상태 갱신 반복으로 호출/latency 급증 |
| v6 | 28 | 보조 호출은 제거했으나 210문항에서 페이지 요청 자체가 사라짐 |

여러 변경과 생성·검색 변동이 섞인 단일 실행들이므로 점수 상승을 재귀의 순수 효과나
특정 구성요소의 확정적 기여로 간주하지 않는다. 개선과 함께 관측된 실행 형태를 보존한다.

q00326 v4: Kidlit411 인터뷰 → 작가 사이트 → bio/books/babycomeout 문서로 재귀하며
원제 Baby와 출판 정보를 출처별로 확보했다. 인터뷰에도 답이 있으므로 재귀가 없으면
반드시 실패했을 사례로 세지 않는다. 재귀가 실제 근거 확인에 참여한 사례다.

## 다음 구조의 기준

```text
메인: 검색 계획
  └ 검색 결과를 받는 fetch 전용 진입 노드
       ├ 선택한 문서: 자체 근거 추출
       │    └ 관련 링크의 자식 노드로 재귀
       ├ 반환 근거 검토 → 필요하면 같은 검색 결과의 다른 문서
       └ 종료: 출처별 확보 근거와 미확인 관계 반환
메인: 결과 통합 → 다음 검색 또는 답변
```

- 진입 노드를 별도의 점수 매기는 controller로 만들지 않는다. 기존 fetch/일반응답
  방식으로 읽기를 실행하는 노드로 다룬다. 구현 공통화 범위는 코드 수정 때 확인한다.
- 같은 검색 결과의 형제 문서를 읽으려고 새 web_search를 사용하도록 만들지 않는다.
  **검색당 문서 1개를 강제로 제한하지 않는다.**
- 문서에서 발견한 URL로 이어지는 탐색은 재귀 자식으로 처리한다. depth 1 승격을
  통한 자식 수/노드 예산 우회는 허용하지 않는다.
- 문서 깊이는 실제 원문부터 depth 1. 검색 결과의 진입 결정은 문서 깊이/확장 예산에
  포함하지 않는다. 검색 10회, 결과 10개, 기존 재귀 예산을 유지한다.
- 읽기 결과마다 별도 상태 갱신 LLM을 호출하지 않는다. 출처 노트는 코드로 누적한다.
- 같은 URL/동일 내용의 재독해와 이미 실패한 경로의 반복을 줄인다. 특히 동일 내용
  판정은 가능하면 추출 모델 호출 전에 수행한다. 의미상 새 정보의 유무와 단순 동일
  텍스트 판정은 구분한다.
- 현재 검색 결과의 진입 후보와 읽은 사실을 분리해 제공한다. 전체 미방문 URL·전체
  추론을 모든 노드에 반복 투입하지 않는다. 과거 후보를 영구 폐기할 필요는 없다.
- 마지막 검색의 읽기 작업이 반환된 후 도구 없는 최종 작성을 수행한다. 결과 반환
  직후 다시 메인을 호출한다는 순서는 생략하지 않는다.

형제 읽기의 자유를 남기므로 latency가 자동으로 낮아진다고 보장할 수 없다.
v5의 과도한 호출과 충분한 읽기는 별개이며, 호출 역할·중복 입력·실제 근거 증분을
함께 확인해야 한다. 이를 임의로 깊이나 수치만 낮춰 해결하지 않는다.

## 입력과 반환

- 추출은 원 질문과 현재 페이지의 근거를 중심으로 한다. 검색어의 임의 연도/이름은
  페이지 사실 또는 추출 범위로 승격하지 않는다.
- 부모의 작업 가설은 탐색 문맥으로 사용하되 현재 페이지가 입증한 사실과 분리한다.
- 선택적 `Check:`를 필수 기능으로 간주하지 않는다. v6의 146번 fetch에서 실제 사용은 0회였다.
- 부모에게 출처별 확인 사실, 그 사실로 연결된 후보/관계, 아직 확인되지 않은 항목을
  반환한다. 미확인을 모순으로 표현하지 않는다. 자식 근거를 부모가 재작성해야만
  살아남는 형태로 바꾸지 않는다.
- 범위·단위·연도·대상과 필요한 원문 행 보존은 유지한다. 노트가 짧아졌다는 이유만으로
  효율 개선이라고 판정하지 않는다.

## 보류할 것

- 최초 두 검색을 A/B로 고정하는 정책을 DS의 정체성으로 삼지 않는다. 관계가 다른
  두 경로를 만드는지는 별개 문제이며 현재 성과 근거가 부족하다.
- 전체 top-k 자동 fetch, 더 깊은 depth, 별도 verifier/controller, 계산 도구 추가는
  이번 실패를 해결하는 기본 처방으로 넣지 않는다.
- baseline 및 공유 모델·샘플링·검색량은 변경하지 않는다.

## 역행 여부를 판단하는 검증

점수만 보지 않고 같은 실패·성공 경로를 확인한다:

1. 유효한 검색 입구가 있는데 fetch를 전혀 안 하는가?
2. 같은 검색 결과의 다른 페이지를 읽기 위해 검색을 다시 소비하는가?
3. 재귀 자식이 얻은 출처 근거가 메인까지 남는가?
4. 검색어의 추측 범위가 원문의 관련 행을 삭제하는가?
5. 동일 원문을 반복 추출하거나 노트 저장을 위해 보조 LLM을 호출하는가?
6. 정상 종료/예산 종료 모두 확보한 답을 최종 출력까지 유지하는가?

저장 로그 재현은 오류 수정 확인용이며 전체 accuracy 상승의 증거로 쓰지 않는다.
새 실행은 사용자가 수행한다. 위 기준이 성능 비퇴행을 보장하는 것은 아니므로
고정된 평가 문항과 비용 지표를 함께 비교한다.
