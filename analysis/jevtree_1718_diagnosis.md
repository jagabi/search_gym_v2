## 로그 계측 문제

- SearchAgent/Jev가 문항 간 공유되는데 _jev_reading은 self.jev의 전역 누적 calls/input_tokens/failures 전후 차이를 문항 통계로 기록한다. 다른 문항의 동시 요청이 섞인다.
- q3 기록 553 JEV 요청 vs trace 구조상 130; 완료 6문항 기록 합계 4,752 vs 재구성 1,221. 재구성은 entry_scores 수 + 각 scored 페이지의 max(1, ceil(links/100))이며 이 문항들에서 jev.error는 0회다.
- jev_input_tokens와 failures도 같은 공유 카운터 차분을 사용하므로 문항별 비용/오류 통계로 신뢰할 수 없다. 정확한 입력 토큰은 현재 trace만으로 복원할 수 없다.
- tool.result.duration_ms는 검색 MCP 호출만 측정하고 뒤의 트리/독해를 포함하지 않는다. 실제 대기는 tool.call부터 tool.result까지 elapsed_ms 차이로 봐야 한다.

## 권장 수정 순서

1. 링크 확장에 별도 하한을 두고 로그인·가입·비밀번호 복구 등 명백한 비자료 링크를 제외한다. 부모 evidence가 낮다는 이유만으로 자식을 전부 막지는 않는다. 유용한 중간 페이지일 수 있으므로 링크 점수로 판단한다.
2. 성공 노드 예산과 별도로 검색당 총 fetch 시도 예산을 추가한다. 실패·중복 대체 fetch가 예산을 넘겨 대기시간을 늘리는 것을 제한한다.
3. JEV 요청별 사용량과 소요시간을 문항 trace에 기록하고, fetch 시작/끝도 기록한다. 공유 카운터 차분을 문항 통계에 쓰지 않는다.
4. 실제 Jina 계정의 허용 한도를 확인한 뒤 키/RPM을 설정한다. 제한값만 임의로 올리면 429 대기와 재시도가 늘 수 있다. 현재 프로세스는 .env 변경만으로 갱신되지 않는다.
5. reader의 Evidence/Inference/Leads 경계를 최종 답변까지 유지한다. 높은 JEV 관련성 점수로 전체 조건 검증을 대신하지 않는다.

코드나 실행 설정은 수정하지 않았으며 실행을 중지/재시작하지 않았다. 분석 JSON과 이 진단 문서만 추가했다.
