# DepthSearch v3: 다음 개선은 수치보다 실행 구조

분석일: 2026-09-16. 대상: `runs/test/20260915-2139_depthsearch_gpt-oss-20b_deepsearchqa_evidence-v3`의 완료된 30문항.
이번 분석은 저장된 trace/response/documents만 읽었다. 모델·검색·judge 재실행 및 평가 답안 변경은 없다.
`audit_depthsearch_v3.py`가 전체 문항의 도구 사용·오류·이전 실행 대비 변화를 집계한다.

## 1. 결과와 해석 범위

| 실행 | 전체 30문항 F1 | 입력 토큰 | LLM 호출 | 중앙 지연 시간 |
|---|---:|---:|---:|---:|
| 과거 RAgent | 0.3804 | 9,642,995 | 463 | 127.0초 |
| DepthSearch v1 | 0.4040 | 13,697,850 | 968 | 296.9초 |
| DepthSearch v2-fix | 0.3567 | 9,571,764 | 851 | 337.5초 |
| DepthSearch v3 | 0.4166 | 16,086,283 | 1,036 | 366.5초 |

v3는 v2 대비 +5.99%p, v1 대비 +1.25%p, 과거 RAgent 대비 +3.62%p.
v1 대비 7승·6패·17무이며, 문항별 차이의 paired bootstrap 95% 구간은 약 -11.76~+14.19%p이다.
이는 30개 고정 개발 문항의 관측 차이에 대한 불확실성으로, 모델 재샘플링과 라이브 웹 변화까지 추정한 구간은 아니다.
과거 RAgent는 공통 파서·복구 코드 버전도 다르다. 현재 결과를 동일 조건의 우월성이나 재귀만의 인과 효과로 주장할 수 없다.

v3 입력 토큰은 v2 대비 68.1%, v1 대비 17.4% 증가했다. 출력 토큰은 v2보다 감소했다.
검색은 208회, 전체 URL 페치 시도는 226회로 v2의 289회보다 줄었지만 비용 감소로 이어지지는 않았다.
전체 질문을 품은 문서 입력을 재전송하는 로컬 조회/추출 반복과 메인 이력을 따로 줄여야 한다.

## 2. 추가한 기능 중 실제로 작동하지 않은 것

### 재귀 깊이와 예산

- 확장 노드 54개, 모두 depth 2. depth 3은 0개.
- 문항당 노드 상한 12에 도달한 문항 0개. 최대 사용량 7개.
- depth 1 reader 103개 중 88개가 보이는 링크 12개 이상이다.
- depth 2 reader 54개 중 51개는 시작부터 확장 불가.
- 원인 후보가 아니라 코드에서 확인되는 제약: 링크 수 >=12이면 자식 슬롯 6개,
  root 할당 6개를 `remaining // children_left`로 나누면 첫 자식의 서브트리 예산이 1개다.
  자식 페이지 자체가 그 1개를 소비하므로 손자 페이지를 열 수 없다.
- 일반 문서도 메뉴·각주 때문에 쉽게 '인덱스'로 판정된다. 링크 수만으로 분류한 정책이 부정확하다.

이것은 앞선 구현의 설계 문제다. 노드 상한을 또 올리는 것으로 해결할 일이 아니다.
필요한 것은 한 번의 관측 후 재배분 가능한 예산과, 현재 문서에서 확인할 항목을 기준으로 한 확장 결정이다.

### 후보 근거표와 미방문 링크

- `research_state update`: 전체 30문항에서 1회, q00789의 Slovakia 관련 3개 셀.
- `inspect`: 0회. `follow`: 0회.
- 미방문 링크 14,026개가 저장돼도 실제 이어 읽기에는 사용되지 않았다.
- 기록된 unknown 셀을 대상으로 다음 행동을 정하는 실행기가 없고, 메인 모델이 자발적으로
  bookkeeping 도구를 호출하기를 기대하는 구조다. 따라서 프롬프트의 '미확인은 탈락이 아니다'가 실행 상태로 이어지지 않는다.

근거표 자동 생성/갱신은 reader 반환값 처리에 포함해야 한다. 별도 선택 도구에 맡기면 안 된다.
미방문 링크도 footer까지 대량 수집하는 큐 대신, 해결할 필드·출처·대상을 가진 작업으로 관리해야 한다.

### 문서 도구 사용성

- 문서 조회 이벤트 259회 중 오류 출력 44회(17.0%). 저장소 예산의 실제 증가량은 257회로,
  예산 거절 등의 이벤트 횟수와 다르다.
- 출력 24,000자 초과로 전체 결과를 버린 경우 19회.
- `find` 140회 중 45회가 0건. 여러 terms가 한 줄에 모두 있어야 하는 AND 검색을 모델이
  대체 키워드나 문서 전체 조건 검색처럼 사용하는 사례가 있다.
- action 누락 7회, document 누락 5회, 없는 테이블 접근 8회 등.
- sort 인자 사용 6회(모두 q00495; 이 중 잘못된 열 지정 2회). aggregate/intersect/calculate는 0회.

오류가 없다는 API 단위 테스트와 실제 모델이 도구를 사용할 수 있다는 것은 다른 검증이다.
doc ID, action, 테이블/열/행, 필터, cursor를 동시에 조합하게 하는 인터페이스 부담을 줄여야 한다.

## 3. 정답에 필요한 자료가 이미 있었던 실패

### q00414: CO2와 항공 승객 CSV

v3는 transport CO2와 air passengers의 전체 CSV를 모두 받아 두었다.
2020·2021년 각각 1억 톤 초과인 국가를 추리고, 두 해 승객 합계를 비교하는 저장 자료 재계산을 수행했다.
비어 있지 않은 3자리 국가 코드로 현재 CSV의 OWID 집계 행을 제외했으며, 별도 ISO 국가 목록 검증은 하지 않았다.

해당 조건의 13개 국가 모두 승객 자료가 있고, 최솟값은 Iran:

- CO2: 2020년 130,009,992톤, 2021년 142,880,000톤.
- 승객: 12,744,854 + 13,695,897 = 26,440,751명.
- 다음은 Saudi Arabia 50,372,598명.

그런데 실제 실행은 2021년 조회의 `action` 누락 후 '필요한 자료가 없다'고 답했다.
추가 검색 없이도 풀 수 있는 실행/데이터 결합 실패다. 결과는 `depthsearch_v3_source_replay.json`에 기록했다.
이 수작업 재계산은 향후 에이전트가 자율적으로 같은 계획을 세운다는 성능 보장은 아니다.

### q00699: RAP 보고서 PDF

저장 원문에는 Phyllostominae 구간과 필요한 종 목록이 있다. 21,655행 부근에서 해당 소절을 확인했다.
다만 추출 텍스트가 14,186,324자이고 그중 약 93%가 공백이다. 종 이름 일부도 글자 사이가 갈라져 있다.
`read` 결과 초과 오류를 반복하고, PDF 텍스트에 존재하지 않는 structured table을 조회하다 40턴 후 빈 답으로 끝났다.

해결 방향은 페이지/소절 단위 검색 결과에 짧은 주변 문맥을 함께 주고, layout 원본은 보존하면서
조회용 텍스트에서 불필요한 수평 공백을 정리하는 것이다. 큰 결과는 자동으로 나눠 다음 cursor를 반환해야 한다.
공백 제거만으로 잘못 분리된 학명을 정확히 복원할 수 있다고 가정해서는 안 된다.

### q00614: ATK/DEF와 기본값/일시적 강화값

원문에는 Giant Soldier of Stone의 기본 ATK/DEF = 1300/2000이 있고, 결투 서술에는 DEF 2000→2600이 있다.
최종 답은 2600을 ATK로 사용하고 Curse of Dragon을 누락했다. F1은 이름 매칭 때문에 0.8889이지만 정렬/속성 의미가 틀렸다.
더 많은 검색보다 값의 속성·상태·단위가 붙은 표와 그 위에서의 정렬이 필요하다.

## 5. 호출 안정성과 최종 답변

- 메인 invalid_tool_calls 23개: 알 수 없는 도구 이름 21개 + 잘못된 search 인자 2개.
- q00037, q00611은 vLLM 도구 헤더 처리 중 HTTP 500. PDF 경고와 별개.
- q00280, q00611, q00699의 최종 재시도는 `finish_reason=stop`, 빈 content, 도구 호출 없음.
- q00490은 `to=…`와 다음 fetch 계획을 포함한 초안을 최종 답으로 채택했다.
- q00577도 추론/추측을 포함한 초안이 답으로 남았다.

새로 관측한 malformed 이름마다 문자열 교정 규칙을 추가하는 방식은 한계가 있다.
단계별로 필요한 행동만 제시하고, 행동 제안과 실행을 분리하며, 실패 시 오류를 반복한 대화 대신
검증된 연구 상태에서 재구성하는 복구가 필요하다. constrained JSON 또는 단계별 지정 function의
실제 gpt-oss/vLLM 호환성은 별도 작은 실험으로 확인해야 하며, 작동한다고 가정하지 않는다.
응답은 facts/answer/unresolved 같은 명시적 반환 구조를 갖게 하고, answer 필드가 없으면 자연어
계획 문장을 답으로 승격시키지 않는다. 부분 정답도 그 구조 안에서 보존한다.

## 6. 성공 사례도 의미 검증이 필요

- q00495(F1 1): 저장 CSV의 실제 top-10 정렬 연산 사용. 전체 문서 접근+연산 도구의 유용성에 대한 구체적 사례다.
  다만 방법 변경이 여러 개라 F1 상승을 특정 한 기능의 인과 효과로 단정하지 않는다.
- q00678(F1 1): 필요한 연도 행을 저장 CSV에서 조회했지만 North Lincolnshire의
  13,031 - 10,151.58을 1,879.42로 잘못 적었다. 올바른 차이는 2,879.42.
- q00386(F1 1): $3,850 × 0.924를 €3,548.40로 계산했다. 올바른 값은 €3,557.40.
- q00789(F1 1): 근거표가 사용됐지만 후보 전체가 확인된 것은 아니다. quote가 원문에 존재하는
  것만으로 해당 값이 올바른 연도 열에 연결됐다는 것까지 검증되지 않는다.

계산은 실행기로 넘기고, 모델은 무엇을 비교하는지 정하도록 나누는 것이 중요하다.
F1 외에 답안 순서, 조건 충족 근거, 열/연도 일치율, 미확인 후보 수를 진단 지표로 보아야 한다.
이 지표는 공식 F1을 대체하거나 오답을 분모에서 빼는 용도로 쓰지 않는다.

## 7. 권하는 다음 구조: 질문의 미확인 항목이 재귀를 이끈다

1. **질문을 작은 실행 계획으로 바꾼다.** 후보 범위, 필수 속성, 시간/단위, 필요한 결합·정렬,
   최종 출력 형식을 명시한다. 같은 모델로 시작하며 모델 교체를 전제하지 않는다.
2. **reader의 로컬 작업을 지정한다.** '질문 전체를 이 페이지로 풀어라' 대신 '이 출처의
   2020/2021 transport CO2 행을 확보하라'를 전달한다. 추출에는 현재 원문과 로컬 목표만 주며,
   부모의 답/수치를 현재 페이지 근거에 섞지 않는다.
3. **reader 반환을 프로그램이 저장한다.** 출처/인용 위치가 붙은 관측값, 발견한 후보,
   읽을 만한 링크와 그 목적, 현재 자료의 범위를 반환한다. 별도 state 도구 호출 없이
   자동 병합한다. 인용 존재 검사와 주장 의미 검증을 구분한다.
4. **확장은 미확인 항목을 채우는 작업 단위로 선택한다.** 원문에 있는 링크 및 관측한
   동일 사이트 경로로 이동하는 정체성은 유지한다. 새 증거를 얻은 가지는 계속 내려가고,
   반복/무관한 가지는 중단해 형제 작업을 선택한다. 초기 예산을 영구 균등 분할하지 않는다.
5. **표 연산을 실행한다.** 검증된 열 의미 위에서 filter → group/sum → join/intersect → sort를
   수행한다. 모델이 수백 개 행을 기억하면서 암산/집합 연산하도록 두지 않는다.
6. **종료를 점검한다.** 전체 목록/최대·최소 요청에서 미확인 후보가 결론을 바꿀 수 있는지,
   잘못된 연도·속성·규격을 비교했는지 검사한다. 확인하지 못한 부분은 unresolved로 보존한다.

이것은 새 도구를 더 나열하는 것이 아니라 도구 사용·상태 갱신을 실행 순서에 넣는 변경이다.
DepthSearch의 기여 방향은 '페이지 근거와 미해결 조건을 전달하는 재귀 탐색'으로 설명할 수 있다.
관련 연구 대비 신규성은 별도 문헌 검토가 필요하다. 이 분석만으로 논문 채택 가능성을 보장하지 않는다.

## 8. 투자 순서와 검증 방법

### 먼저: 저장 자료만으로 재현 가능한 실패 제거

- q00414 유형: 전체 데이터는 있으나 필터/연도/결합을 실행하지 못한 실패.
- q00699 유형: 실제 소절이 있으나 읽기 인터페이스가 접근을 막은 실패.
- q00614 유형: 속성/순위 혼동. 올바른 근거를 전달한 이후 계산은 결정적으로 수행.
- 일반화된 synthetic 사례로 동작을 검증하고, 실제 저장 자료는 개발용 재현에 사용한다.
  특정 정답/문항 ID를 런타임 정책에 넣지 않는다.

### 다음: 자동 후보 상태 + 목적이 있는 재귀

확인할 지표: 자동 생성된 조건 셀 수, 실제 새 근거를 낸 확장 수, 미확인 후보 감소,
같은 쿼리 가설의 반복, depth 3 도달 가능 여부. depth 3을 많이 쓰는 것 자체가 목표는 아니다.
새 구조에서도 도움이 안 되는 문서는 한 단계에서 끝나야 한다.

### 그 후: 모델 역량/특수 접근의 한계 분리

q00385는 표지 이미지, q00390은 해안 거리와 폭풍 궤적의 공간 연산을 요구한다.
텍스트 reader나 노드 증가만으로 이 능력이 생기지 않는다. 별도의 이미지/공간 처리 경로가 필요하다.
강한 모델을 검토한다면 먼저 같은 저장 근거에서 계획·추출·종합 중 어느 단계가 약한지 비교한다.
전체 reader를 교체하기 전에 짧은 계획/검증 단계만 교체하는 대안의 비용·효과를 측정한다.

### 평가

검색 상한 10회·결과 10개는 유지한다(5는 search-o1 자동 페치 수).
개발 자료에서 고친 뒤, 미사용 평가 문항과 같은 코드의 baseline으로 확인한다.
반복 실험은 실질적인 차이가 생긴 후 소수 문항부터 하고, 매번 무작정 전체 30개를 다시 돌리지 않는다.
소스 고정 replay는 원인 분리용이며 end-to-end 라이브 웹 점수를 대신하지 않는다.

## 9. 이번 턴에 적용한 범위

- 누락된 fontTools 4.65.0을 기존 search_gym 환경에 설치하고 requirements에 등록했다.
- 잘못된 PDF 응답은 파서에 넣기 전 파일 헤더로 거절해 기존 Jina fallback 경로로 보낸다.
- 이에 대한 회귀 검사를 포함해 오프라인 테스트 67개 통과.

- 검색/재귀/토큰 설정값과 주요 탐색 알고리즘은 이번 분석 중 변경하지 않았다.
- 위 7절의 구조 재설계는 제안이며 아직 구현하지 않았다. 진단 결과와 구현 완료를 혼동하지 않는다.
