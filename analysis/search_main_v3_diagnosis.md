## 2. invalid 2,045건의 실체

`controller_invalid`는 질문 실패 수가 아니라 내부 호출 실패 횟수다.

| 내부 단계 | 전체 호출 | 정상 | invalid |
|---|---:|---:|---:|
| fetch 선택 | 2,860 | fetch 1,178 + 생략 74 | 1,608 |
| 읽은 뒤 상태 JSON 갱신 | 986 | 549 | 437 |
| 합계 | 3,846 | 1,801 | 2,045 |

선택 invalid 1,608건 중 목록 밖 URL 1,605, 잘못된 인자 JSON 2, 출력 길이 종료 1이다.
목록 밖 URL 1,605건의 구분:

- 검색 엔진 쿼리 URL: 653
- 그 밖의 미등록 URL: 538 (추측한 Wikipedia 경로, 사이트 내부 검색 등 포함)
- 이미 읽은 URL 재선택: 384
- 이미 실패한 URL 재선택: 27
- 대소문자 또는 끝 슬래시만 다른 URL: 3

즉 주원인은 도구 호출 형식이 아니라 행동 범위 이탈이다. tool call은 대부분
정상 파싱되었지만, 모델이 관측된 미방문 출처 대신 새 검색 URL/주소를 제출했다.
위 분류는 현재 근거 본문뿐 아니라 working_state의 전체 출처 목록과도 대조했다.
입력에는 읽은 출처도 들어 있으나 선택 가능 목록에서는 제외되어 있어, 이미 읽은
URL을 다시 고른 384건도 실행되지 않았다.
현재 코드는 이 호출을 거절하고 같은 선택 단계에 피드백을 주지 않은 채 메인으로
복귀한다. 빈 응답을 추측해 복원하거나 URL 검사만 느슨하게 만드는 것으로 해결할
문제가 아니다. 검색 엔진 URL을 열면 검색 횟수 통제가 깨지므로 허용해서는 안 된다.

상태 갱신 invalid 437건은 빈 본문 397, 비어 있지 않은 비정상 출력 28,
길이 제한 종료 12다. 선택을 tool calling으로 바꾼 뒤에도 이 JSON 호출은 별도로
남아 있었다. 이 단계의 빈 본문이 곧바로 질문의 빈 최종 답을 뜻하지는 않는다.

## 3. 빈 최종 답 48개는 종료 경로에 집중

- 48개 모두 검색 10회 소진 후 발생했다.
- 48개 모두 저장된 잠정 답이 비어 있었다.
- 47개는 최종 작성 두 번 모두 `raw_text=""`, `finish_reason="stop"`이었다.
- 나머지 q00532는 첫 최종 작성이 비었고, 두 번째는 답 대신 검색 계획을 반환했다.
- 46개는 마지막 메인 응답부터 빈 본문이었다. q00052는 도구 호출 형태의 원문이
  정리 후 비었고, 나머지 하나는 마지막 메인 호출이 length로 종료했다.
- 새 DS의 `judge_errors=48`은 전부 `empty_response`다. 채점 서버 장애가 아니다.

| 새 DS 메인 호출 조건 | 전체 호출 | 빈 본문 + stop |
|---|---:|---:|
| 도구 있음 | 2,950 | 3 (0.10%) |
| 도구 없음 | 259 | 127 (49.03%) |

본문 빈 메인 130회는 reasoning이 있는 경우도 포함한다. 최종 작성 trace에는
reasoning을 저장하지 않아 최종 작성 자체의 reasoning 유무까지는 확정할 수 없다.
최종 작성의 빈 본문은 정리 함수가 짧은 정답을 지운 결과가 아니다.

현재 DS는 도구가 없을 때 `tool_choice="none"`을 명시한다. baseline 최종화 경로는
이 필드를 생략한다. 하지만 두 경로는 질문 난이도·이력·프롬프트도 다르므로 위
차이만으로 이 필드나 vLLM 파서 하나를 원인으로 확정할 수 없다. 실제 응답은
도구 제거 후에도 검색을 계획하다 본문 없이 멈추는 양상을 보인다. 모델/서버의
채널 처리와 종료 프롬프트를 구분하려면 동일 저장 입력으로 작은 재현이 필요하다.
Reader의 무도구 추출은 같은 DS에서도 1,383세션 모두 complete이므로 모든 무도구
호출이 일괄적으로 고장났다고 설명해서도 안 된다.

빈 48개 중 baseline 중 하나라도 맞힌 것은 8개다. 빈 답을 모두 복구해도 모두
정답이 된다는 근거는 없으며, 단순 정답 보너스로 48개를 계산할 수 없다.

## 5. 40턴 및 depth 1 예산

`agent.max_turns=40`은 메인 대화 루프의 안전 상한이다. controller·reader·최종
작성 호출을 모두 합쳐 40번이라는 뜻이 아니다. reader 탐색은 별도로 최대 6턴이다.
이전 DS는 69문항이 메인 40턴까지 도달했고, 명시적 max_turns 탈출 이벤트는
63문항이었다. 새 DS는 최대 15턴, 평균 10.7턴, 40턴 도달 0문항이다.
따라서 이번 빈 답을 40턴 상한으로 설명하거나, 이를 올려 해결할 수는 없다.

현재 예산 처리:

| 행동 | 문항 확장 노드 12 차감 | 부모의 직접 자식 2개 차감 |
|---|---|---|
| 검색 결과에서 진입 페이지 fetch (depth 1) | 아니오 | 아니오 |
| 진입 페이지에서 링크를 열어 depth 2로 이동 | 예 | depth 1 reader의 한 자리 |
| depth 2에서 링크를 열어 depth 3로 이동 | 예 | 해당 depth 2 reader의 한 자리 |

진입 페이지당 6개는 그 아래 서브트리 확장 수 제한이다. 진입 페이지 수가 6개라는
뜻이 아니다. depth 2+ fetch가 실패하면 노드 예산을 반환한다.
q00157은 진입 fetch 8회, 방문 URL 8개인데 `budget.used=0`, expansion_nodes=0이다.
q00290은 진입 fetch 9회, 확장 노드는 2개다. depth 1을 자식 2개로 제한한 것은 아니다.

다만 현재 구현에는 **검색당 진입 fetch 최대 1회**라는 별도 구조 제한이 있다.
선택기는 한 번 호출하고, 선택된 페이지의 재귀를 마치면 바로 메인으로 돌아간다.
같은 검색 결과 목록에서 다른 형제 페이지를 추가로 고르는 fetch 루프는 없다.
따라서 기존 reader와 도구 호출 형식은 같지만, 여러 번 fetch한 뒤 일반 응답으로
종료하는 대화 루프까지 동일하게 구현한 상태는 아니다. 이것은 child=2와 무관하며,
추가 진입을 위해 다시 검색해야 하는 불필요한 결합을 만들 수 있다.

## 6. 사례와 수정 우선순위

- **q00510**: 이전 DS 오답 → 새 DS 정답(Rosenfeld). 새 실행은 두 번째 메인 턴에
  American Pancake의 직접 단서 페이지를 실제로 열었다. 진입 시점 개선이 작동한
  사례다. 이후 검색 반복도 남아 있으므로 모든 행동이 효율적이었다는 뜻은 아니다.
- **q00334**: 여전히 오답. 선택 단계가 검색 엔진 URL 7개와 미등록 폰트 URL 1개를
  제출해 거절됐다. 진입 단계가 새로운 검색 역할로 돌아선 구체적 사례다.
- **q01237**: 이전 DS 정답(Ek Tha Tiger) → 새 DS 오답(The Avengers). 새 실행은
  'period drama'를 특정 영화 제목 Jane Austen's Period Drama로 좁힌 뒤 그 경로의
  자료를 읽고 미국 영화 흥행 순위로 진행했다. 초기 후보의 다른 조건을 검증하지
  못한 문제는 독해 진입만 바꿔 해결되지 않았다.
- **q00898**: 이전 DS 정답 → 새 DS 빈 답. 새 실행에서 실제로 선택한 출처와 질의가
  이전 실행과 다르다. 이전 저장 검색 배치 probe 성공이 전체 실행 성공을 보장하지 않는다.

우선순위는 (1) 저장된 종료 입력으로 빈 본문 경로 재현, (2) fetch 전용 단계의
입력을 실제 선택 가능한 페이지 중심으로 좁히고 범위 이탈을 방지, (3) depth 1의
추가 진입을 새 search와 분리할지 결정하는 순서다. 상태 JSON 호출은 안정성 및
추가 비용 대비 효과도 별도로 재검토할 대상이다. 검색 예산·결과 수·40턴·재귀
깊이를 일괄적으로 늘리는 것이 이번 실패의 직접적인 해결책은 아니다.
