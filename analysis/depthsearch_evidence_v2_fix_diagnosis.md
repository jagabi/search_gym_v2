분석일: 2026-09-15. 모델·검색·judge를 새로 실행하지 않고 저장된 결과와 trace를 분석했다.

## 분석 대상과 범위

- 최신: `runs/test/20260915-1602_depthsearch_gpt-oss-20b_deepsearchqa_evidence-v2-fix`
- 직전: `runs/test/20260915-1431_depthsearch_gpt-oss-20b_deepsearchqa_evidence-v1`
- RAgent: `runs/test/20260912-2055_ragent_gpt-oss-20b_deepsearchqa_f1`

- v1은 재개 실행이며, 버전별 프롬프트와 동작이 함께 바뀌었다. 인과 효과나 독립 반복 실험으로 해석하지 않는다.
- 아래 제안은 개선 가설이다. 새 성능 수치는 측정하지 않았다.

## 예산과 관측

- 메인 fetch는 이미 무제한이다. 단, 메인 40턴, 하위 확장 4노드, reader별 자식 2개, 깊이 3은 제한된다.
- 메인 컨텍스트 소진 0문항. 메인 40턴 도달 1문항(q00490).
- reader 210세션의 총 호출 수: 1회 156개, 2회 12개, 3회 26개, 4회 16개. 추출을 먼저 하는 이 실행에서 탐색 4턴을 모두 사용한 사례는 없었다.
- reader 추출 210회: 출력 평균 2,067토큰, 중앙값 1,653.5, 출력 상한 도달 2회. 탐색 106회: 출력 평균 362토큰, 중앙값 211. 탐색 출력 상한 도달 0회.
- 메인 출력이 토큰 상한으로 잘린 사례는 0회.
- **원문 fetch 단계 절단 40회, 12문항.** reader 자체의 문서 절단 지표만 보면 앞 단계의 손실이 가려진다.
- 가지 중단 99회: 모델의 `no_useful_next_link` 79회, 동일 본문 20회. 모든 중단이 잘못된 것은 아니다.
- 도구 이름 오류: 메인 16회/5문항, reader 1회. `invalid_tool_calls=4`는 인자 오류만 세므로 이 문제의 크기를 충분히 보여주지 않는다.
- unknown 도구 이름 중 `web_search]` 11회. q00074 혼자 메인 이름 오류 12회를 겪었다.

## 핵심 병목

### 1. 원문 접근 범위

q00414: CO2 CSV 입력은 알파벳 순 앞부분에서 잘려 Iran 행이 한 개도 들어오지 않았다. 항공 승객 CSV는 El Salvador 중간에서 끝난다. 실제 정답 후보의 수치를 보기 전에 Canada를 선택했다.

q00678: 가스 사용량 CSV 입력은 2005~2006 구간에서 끝나며 2012/2023 행은 없다. `?download=1`, `#page=200` 등 URL을 바꿔 같은 앞부분을 여러 번 읽는다. 이 문항에서만 fetch 절단 10회다.

q00699: RAP 보고서 PDF의 여러 요청은 `Markdown Content:` 뒤가 비어 있었다. reader는 그래도 완료된 노트를 생성했다. reader 출력이 비어 있지 않다는 지표가 원문 획득 성공을 뜻하지 않는다.

q00385: 표지 사진의 동물 유무를 확인해야 하지만 텍스트 경로만 있다. q00849는 fetch 4건이 모두 오류였고 reader 세션이 0이다.

제안: 원문을 보관하고 내부 문서 ID를 부여한다. HTML은 섹션/페이지, PDF는 페이지/검색, CSV·XLSX는 행·열/시트 단위로 재접근한다. 전체 데이터는 컨텍스트 밖에서 처리하고 필요한 행과 헤더만 reader에 전달한다. 실패 시 형식에 맞는 다른 읽기 경로를 사용한다. 이것은 웹 링크를 따라 도달한 문서를 읽는 DepthSearch 기능 안에 둘 수 있다.

### 2. 후보와 미완료 경로를 보존하지 못함

q00148: 75개 경매 항목이 있는 색인에 도달했지만 일부 월만 읽고 전체 2023년의 조건을 부정했다. 하위 예산도 3/4 사용에 그쳤다. reader별 자식 2개 제한과 이후 경로 관리가 총 노드 예산과 별개로 작용한다.

q00802: California 페이지에서 다른 주의 동일한 통계 링크들을 노트에 적고도 `Expand: no`로 종료했다. 전체 주의 교집합이 필요한데 해당 페이지에서 California의 사실만 확인하는 데 치우쳤다.

q00503은 Nobel/Booker 후보 목록을 완성하지 못하고 한 명만 반환했다. q00884는 Richard Stone을 후보로 검증하지 못한 채 다른 인물의 논문 수를 추정했다.

제안: 후보 집합, 조건별 확인 상태, 미방문 링크를 지속 상태로 보관한다. 지역 reader는 관련 링크와 대상 필드를 제안하고, 문항 전체의 미완료 항목을 아는 조정자가 다음 확장에 예산을 배분한다. 세션이 끝나도 미방문 경로는 사라지지 않아야 한다. `Expand: no` 한 줄로 관련 후보 링크까지 버리지 않는다.

### 3. 요약된 표도 틀릴 수 있음

q00712의 NCES 다중 헤더 표에서 연도, 등록학생 수, 표준오차, 졸업생 수가 잘못 연결된다. HTML과 XLSX에서 얻은 노트끼리도 같은 항목의 값이 충돌한다. 표 형식 출력을 요청하는 것만으로 열 정합성이 보장되지 않는다.

q00548은 2015년 여성 기록이 없는데 나머지 4개 연도만 비교해 2017을 최대로 골랐다. 누락이 최댓값을 바꿀 수 있다는 판단이 작동하지 않았다.

제안: 표 헤더 경로와 원본 행 ID를 유지한다. 정렬, 교집합, 차이 계산, 단위 변환은 제한된 연산 도구에서 수행한다. 후보 누락·기간 불일치·충돌은 최종 결론의 미해결 조건으로 남긴다. 추출기는 사실과 경로를 제공하고 전역 순위 결정은 별도 단계에서 한다.

### 4. 답변과 행동의 상태 혼동

q00495의 최종 응답은 “이제 mean income 표를 fetch하자”이고, q00611은 “TRAPPIST-1 f, g, h 페이지를 확인하자”이다. 둘 다 `answered` 처리되었다. 단일 문장에 맞춘 `_looks_like_action`으로는 복합 문장/문단형 행동 출력을 잡지 못한다.

q00074는 정식 `tool_calls` 내부의 도구 이름에 `]` 등이 붙었다. 기존 복구는 본문으로 흘러나온 호출만 다루므로 이 유형을 해결하지 못한다.

제안: 제공된 도구로 유일하게 매핑되는 명백한 헤더 잔재를 정규화하고, 잘못된 헤더를 다음 대화에 계속 재주입하지 않는다. 최종 답변을 명시적인 상태/도구로 분리하거나, 비도구 텍스트가 나오면 근거에 기반한 최종 작성 단계로 전환한다. 단순 정규식 패치를 계속 늘리는 방법은 불충분하다.

### 5. 원문 내용과 채점의 관계

q00144는 질문을 닮은 Facebook `fb-answers` 페이지를 최종 출처로 삼았다. 이런 답변 재게시/SEO 문서는 원전 확인을 방해하고 평가 오염도 일으킬 수 있다. 모든 방법에 같은 기준으로 필터를 적용할 필요가 있다.

q00614는 정답에 포함된 이름들을 반환해 F1=1이지만 요구된 순서와 실제 출력 순서가 다르다. F1 외에 순서·조건 충족 진단이 필요하다.

q00450은 주의가 필요하다. 저장된 2023년 출석 원문에서 Expected−Present를 계산하면 Simon Warley가 9회로 가장 많고, 해당 인물의 ward는 Tankerton이다. gold는 West Bay이다. 따라서 이 사례를 곧바로 계산 오류라 부르면 안 된다. 전체 위원회 출석과 특정 Council 회의의 범위, 날짜 선택, 원 데이터 변경 또는 gold 정의를 확인해야 한다. 이번 분석에서는 gold를 바꾸거나 이 문항을 점수에서 제외하지 않았다.

## 개발 순서와 확인 실험

1. 프로토콜과 종료 상태를 안정화한다. 기존 trace를 입력으로 재현하여 복구율과 오분류를 확인한다.
2. 파일/표/문서 재접근 계층을 만든다. 이미 찾은 URL에서 원하는 행·페이지를 얻는지 먼저 검증한다. 탐색을 다시 하지 않는 read-only 재평가는 병목 분리용이며 최종 시스템 성능으로 보고하지 않는다.
3. 후보·조건·미방문 링크 상태를 도입한다. 추출의 원문 격리는 유지하면서 전역 누락 항목을 탐색 목표에 전달한다.
4. 개선된 읽기/탐색 정책에서 노드 4→8→12와 색인 분기 확대를 비교한다. 토큰·시간 대비 새 근거/새 후보가 늘었는지 함께 본다.
5. 표의 교집합·정렬·단위 변환을 검증 가능한 연산으로 옮긴다. 필요하다면 데이터 해석/최종 검증에만 더 강한 모델을 쓰는 조건을 따로 둔다.
6. 버전과 예산을 고정한 독립 반복 및 미사용 test로 최종 성능을 확인한다. 버전별 최고 결과 선택은 개발용 분석으로만 사용한다.

프롬프트·도구·제어 로직을 함께 개선하는 방법 비교가 목적이다. 재귀 단독 효과의 입증을 개발의 전제조건으로 두지 않는다. 방법의 핵심은 페이지에서 발견한 자료와 링크를 reader가 직접 탐색하고, 출처별 근거와 미완료 항목을 상위로 전달하며, 필요한 가지에 추가 읽기를 배정하는 것이다.
