## 1. Jina 실제 요청 대상은 현재 저장 로그만으로 확정할 수 없다 (정정)

71개 search의 `lds/*/structure.json` 모두 다음 설정을 기록했다.

```json
{"jina_base_url":"https://r.jina.ai","jina_rpm":"auto","jina_max_concurrent":50}
```

앞서 이를 근거로 공개 Jina로 실행했다고 단정했으나 철회한다. 사용자는 실행 중 로컬 Jina Docker에서 요청 로그가 계속 발생했다고 확인했다. 코드 확인 결과 위 설정은 실제 HTTP 요청을 보내는 서버가 보고한 값이 아니라, `searchgym/lds.py`에서 메인 프로세스의 환경변수와 기본값으로 작성한 값이다. 원격 MCP 연결 시 fetch 서버는 별도 환경을 사용하며, stdio 서버 역시 별도 프로세스에서 환경을 읽는다. 따라서 메인 환경 기록을 실제 서버 설정으로 간주할 수 없다. 원격 MCP를 썼다는 것도 아직 확인되지 않았다.

현재 저장된 fetch 로그에는 실제 Reader 엔드포인트가 없어 이 불일치를 확정적으로 해소할 수 없다. Docker 로그의 요청 URL/시각을 이번 실행과 대조하거나 fetch 서버의 유효 설정을 확보해야 한다. 로컬 사용 관측을 무시하고 공개 API RPM이 병목이라고 설명하면 안 된다. 아래 시간은 요청 대상과 무관하게 관측한 클라이언트 fetch 구간이다.

fetch_start/end 구간의 겹침을 제거한 시간은 각 문항 latency의 88.2~96.8%다. 개별 fetch 시간의 가중평균은 약 24.46초다. 이것은 클라이언트에서 기록한 fetch 전체 시간으로, pacing·재시도·서버 대기 등이 포함될 수 있다. 순수 Jina 서버 처리 시간으로 인용하면 안 된다.

페이지 JEV 구간의 겹침을 제거한 시간은 문항당 약 10~47초다. 이 수치는 entry 평가 등을 전부 포함한 전체 JEV 서비스 시간은 아니다.

## 4. 개선 순서 제안 — 이번 진단에서는 구현/추가 모델 호출하지 않음

1. **실제 fetch 서버 설정 확인 및 기록.** 메인 프로세스의 structure 설정만으로 검증하지 말고 실제 요청을 보내는 서버의 주소·RPM·동시 요청 한도를 확인해야 한다. 현재 실행이 공개 Jina를 썼다는 전제는 철회한다.
2. **저장된 문서로 JEV와 reader를 각각 재검증.** 위 세 사례를 포함해 원문·JEV 점수·reader 출력·후속 쿼리를 나란히 본다. 특히 '검색 주제와 관련 있음'과 '검색한 관계를 실제로 답함'을 JEV query_answer가 구별하는지 검증한다. 새 fetch 없이 비교할 수 있다. 프롬프트 수정만으로 해결된다고 전제하지 않는다.
3. **reader는 자유서술 유지하되 단정의 원문 근거를 확인.** 516의 inspired-by/director-of, 598의 Appendix/body, 1230의 하한/상한 같은 왜곡을 재현 사례로 삼는다. 베이스라인과 reader 통제가 중요하므로 reader 변경은 별도 실험으로 분리하고, 이번 JEV-only 개선과 섞지 않는다.
4. **구조 변경 후보는 미사용 reader 예산 이월.** direct 2/query 4의 우선 할당은 유지하되 남는 자리를 적격 문서에 빌려주는 방식이다. 총 6개 상한은 그대로다. 현재의 엄격한 미이월 구현을 개선할 후보이며 아직 적용하지 않았다.
5. **그 다음 depth ablation.** 같은 문항/환경에서 d3 또는 d4와 d6의 비용·정답을 비교한다. d5~6의 전달 수율이 낮다는 근거는 있지만 단순 축소로 정확도가 좋아질 것이라 단정하지 않는다. 조기종료와 후보 개수 정책은 이번 진단에서 변경하지 않는다.
