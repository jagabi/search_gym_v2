## 무엇을 실제로 바꿨나

reader는 사실을 재작성하는 대신 현재 원문에 부여한 `[P#]`를 선택했다. 코드가 번호를
검증하고 정확한 원문 문단을 반환했다. 모델의 Evidence 설명/Connections는 제거하고
Coverage/Missing/Next links는 탐색 가설로 표시했다. 자식 근거는 부모가 다시 쓰지 않고
자동 병합했다. 기존 8192-token 원문 보존 상한과 재귀 정책을 유지했다. 추가 모델 단계는 없다.
일관된 형식으로 explorer prompt도 바꿨으므로 코드만의 효과를 분리한 실험은 아니다.

- 원문 선택 기록 113회: 모델 추출 105회 + 알려진 접근 화면의 모델 생략 8회.
- 빈 선택 60회(위 접근 화면 8회 포함), 잘못된 ID 0회, 반환 절단 2회.
- 재귀 반환 38회(v12는 7회), 그중 partial 22 / not_found 16.
- 선택 루트 fetch 118회 중 성공 85 / 실패 33. 검색 배치 20개에서는 선택한 루트가 모두 접근 실패.

따라서 재귀가 사라진 구현 오류나 문단 번호 파싱 실패가 이번 정체의 설명은 아니다.
그렇다고 빈 선택을 모두 오판으로 세면 안 된다. 실제로 접근 화면·무관한 페이지가 많았다.

## 확인한 손실

### q01073: 복사할 근거를 선택하기 전에 후보를 버림

원문 P65에는 `Caldera and Puerto Viejo`가 있었다. 이는 전체 정답을 증명하지 않지만
습지 인근 마을의 후속 조사 단서다. reader는 원문이 질문의 모든 거리·방향 조건을
확정하지 못한다며 `Evidence: none`을 반환했다. 이후 검색은 Huasco와 주변 해변으로
좁아졌고 최종 답도 Huasco였다. 원문 복사 코드는 올바르게 작동했지만 복사할 선택이 없었다.

### q00265: 소스에 실제 있는 블로그 이름과 질문에 맞는 블로그는 다름

Nose in a Book의 제목과 일부 페이지를 읽었다. 메인은 그 후보를 반복 검색했고 최종적으로
블로거의 개인적 공감까지 확인된 것처럼 서술했다. 원문 보존이 후보의 적합성 검증을
자동으로 해결하지 않았다. 검색 방향과 최종 근거 연결의 손실을 별도로 다뤄야 한다.

### 문단 번호가 유효해도 선택 내용은 부실할 수 있음

q00510의 인터뷰에서는 답변 대신 인터뷰어의 질문 문장을 선택한 부분도 있었다.
8회 저장 페이지 probe의 출력 토큰 절반 감소(20,501→9,962)와 ID 형식 성공은
실제 정확도·전체 토큰 효율로 이어지지 않았다.

## 복귀한 상태와 다음 가설

- `configs/depthsearch.yaml`: v12 계열 메인/reader 프롬프트 복귀, `extractive_evidence: false`.
- 문단 선택 구현과 테스트·스냅샷은 보존. 괄호 URL 등록 보존 수정은 유지.
- DS-only cache `agent/54-ds-link-registry`; baseline `agent/35` 변경 없음.
- 복귀 후 오프라인 165개 검사 통과. baseline 재실행 없음.

다음 가설은 reader의 **근거를 남길지 판단하는 역할**과 **재귀 경로를 선택하는 역할**을
분리하는 것이다. 예컨대 원문 반환은 모델의 relevance 판단에 의존하지 않고, 모델은
링크 탐색에 집중하게 할 수 있다. 그러나 원문 전달량·컨텍스트·절단 비용이 늘 수 있으므로
아직 구현되거나 성능을 확인한 개선안으로 취급하지 않는다. 전체 결과 자동 fetch나 검색
예산 증가와도 구분한다. `_assistant_message`는 reasoning_content를 과거 대화에 넣지
않으므로, 단순히 메인 CoT 이력을 지우자는 처방은 현재 구조를 설명하지 못한다.
