# BrowseComp 300문항 비교 진단 — 2026-09-21

## 결론

현재 DS의 핵심 문제는 재귀 깊이 부족이 아니라, **후보 발견 → 필요한 페이지 진입 → 후보를 유지/기각 → 답 제출**을 연결하는 메인 탐색 정책이다. 검색을 모두 소진한 뒤 fetch로 복구하는 경향, 잘못된 후보에 대한 고착, 유력한 후보를 찾은 뒤에도 끝나지 않는 검증이 함께 나타난다. 여기에 평가 DNS 오류와 최종 응답 실패가 섞였다.

RAgent보다 낮은 2문항 차이를 확정적인 열세로 해석하기는 어렵다. search-o1 대비 13문항 차이는 운영 오류를 분리해도 방향이 유지된다. 재귀가 유용하게 작동한 개별 사례는 있으나, 이번 실행으로 전체 성능 우위를 주장할 수 없다.

실행 코드·프롬프트·설정·저장된 점수는 수정하지 않았다. 라이브 모델/검색/평가 호출 없이 저장된 기록만 분석했다.

## 1. 비교 범위와 점수

동일한 300개 ID의 질문과 gold answer 일치를 검사했다. 각 카테고리 30문항, 총 10개 카테고리인 표본이며 BrowseComp 전체 1,266문항 결과는 아니다. 세 실행 모두 gpt-oss-20b, 검색 10회, 결과 수 설정 10, 메인 최대 40턴이다. 실제 평균 사용량은 다르다.

| 항목 | RAgent | search-o1 | DepthSearch |
|---|---:|---:|---:|
| 정답 | 32/300 | 43/300 | 30/300 |
| 정확도 | 10.67% | 14.33% | 10.00% |
| 빈 응답 | 1 | 1 | 10 |
| 빈 응답 외 평가 오류 | 0 | 0 | 6 |
| 메인 40턴 도달 | 0 | 0 | 69 |
| 평균 검색 횟수 | 9.71 | 8.78 | 9.67 |

| 지연 시간 중앙값 | 102.7초 | 1,282.9초 | 609.2초 |

페이지 처리 세션 수는 문서 근거 추출/탐색 세션 수이며 고유 URL 수나 LLM 호출 수와 같지 않다. RAgent는 페이지 원문을 메인에 직접 전달하므로 이 세션 수가 0이다. 검색 결과 수 설정 10은 매번 유효 결과 10개를 확보했다는 뜻이 아니다.

## 2. 오류를 먼저 구분해야 한다

DS의 평가 DNS 오류 6개:

`q01173, q01177, q01181, q01200, q01202, q01185`

기록된 오류는 `ConnectError('[Errno 11001] getaddrinfo failed')`이다. q01185는 답에 gold인 Canada가 들어 있지만 평가 실패로 0이다. 정답으로 자동 변경하면 안 되며, 저장된 답을 대상으로 평가만 다시 해야 한다. 나머지 5개도 평가 실패가 사라진다고 정답이 되는 것은 아니다.

DS 빈 응답 10개:

`q00128, q00459, q00514, q00596, q00620, q00882, q00908, q00930, q01048, q01107`

전부 메인 40턴 소진 뒤 최종 응답 복구가 실패했다. 9개는 두 번의 최종 생성 모두 기록된 raw text 자체가 빈 문자열이고, q01048은 첫 응답이 사용할 수 없는 텍스트, 두 번째가 빈 문자열이다. 따라서 이번 빈 답변들을 `_clean_answer()`가 정상적인 짧은 답을 지운 현상으로 설명할 수 없다. API가 왜 빈 본문을 반환했는지까지 이 로그만으로 확정할 수는 없다.

검색 도구 실패는 DS의 7문항에서 총 63회다. 이 로그에는 주로 `Error executing tool web_search`만 기록되어 있어, 평가 오류와 동일한 DNS 원인이라고 단정할 수 없다.

세 방법 중 어느 하나라도 평가 오류(빈 답변 포함), 실행 오류, 검색 실패가 있는 문항을 제외한 공통 278문항에서는 RAgent 29개, search-o1 38개, DS 29개 정답이다. 이 사후 부분집합은 원점수를 대체하지 않는다. 여기서 DS–search-o1의 discordant pair는 8 대 17, p=0.108이다. **운영 문제만으로 전체 차이를 설명할 수 없지만, 방법의 확정적인 열세라고 단정하기에도 근거가 제한적이다.**

## 3. 가장 큰 패턴: 검색과 재귀가 잘 교차하지 않는다

| DS의 첫 메인 fetch 시점 | 문항 수 | 정답 수 | 정확도 |
|---|---:|---:|---:|
| 검색 0–3회 후 | 23 | 11 | 47.8% |
| 검색 4–9회 후 | 103 | 12 | 11.7% |
| 검색 10회 소진 후 | 160 | 7 | 4.4% |
| 메인 fetch 없음 | 14 | 0 | 0% |

이 표는 **인과 효과가 아니다**. 쉬운 문제에서 좋은 링크를 일찍 발견했기 때문에 fetch도 빨랐을 수 있다. 따라서 첫 fetch를 무조건 몇 번째 턴에 강제하는 처방은 뒷받침하지 않는다.

다만 실행 형태는 명확하다.

- 메인 fetch 4,220회 중 4,000회(94.8%)가 검색 10회 소진 뒤 발생했다.
- 메인 fetch 중 1,881회(44.6%)가 도구 오류였고, 768회는 이미 저장한 노트를 반환했다. 오류와 캐시 반환은 성격이 다른 지표다.
- 69문항이 최대 40턴에 도달했고 전부 0점이었다. 같은 69문항을 RAgent는 6개, search-o1은 8개 맞혔다.
- 재귀 확장 노드 12개를 모두 사용한 것은 11문항뿐이다. 이들도 모두 0점이지만, 어려운 문제가 예산을 많이 썼다는 선택 효과가 있다.

**현재의 잦은 실패 경로는 `검색 소진 → 추측 URL/실패 URL/기존 노트 반복 → 40턴 → 최종 복구`다.** 재귀 예산만 늘리면 이 경로가 개선된다고 볼 근거는 없다.

코드상 검색 소진 후 검색 도구 제거는 동작하고 있다. 그러나 `max_fetches: 0`은 메인 fetch 무제한이고, 매 턴 안내도 그 사실을 알린다. 재귀 자식 노드 한도는 메인이 새 depth-1 페이지를 계속 열거나 기존 노트를 재요청하는 것을 막지 않는다.

## 4. 같은 문항의 실패 경로

### A. 검색 결과에 후보와 정확한 링크가 있는데 사용하지 못함 — q00326

정답 Baby. RAgent와 search-o1 정답, DS 오답.

- DS 5번째 검색에 Fran Manushkin 인터뷰와 실제 URL이 등장했다.
- 8번째 검색에는 Encyclopedia.com의 `Manushkin's first book, Baby`라는 snippet까지 있었다.
- 그런데 메인은 10번 검색을 소진한 뒤 `Fran_Manuskin`이라는 오타가 있는 Wikipedia URL을 시도했다.
- 인터뷰 URL도 검색 결과의 `...spotlight-Fran-Manushkin.html`을 그대로 복사하지 않고 소문자 `...spotlight-fran-manushkin.html`로 바꿔 호출했다. 반환은 404였다.
- Encyclopedia.com 링크는 열지 않았다. 최종 답은 작가와 책을 확인하지 못했다는 응답이다.

search-o1은 검색 결과의 정확한 대소문자 URL을 자동으로 열었고, 노트에는 `BABY → BABY, COME OUT!`이 전달되었다. RAgent도 소문자 URL 404는 겪었지만, 이후 후보 이름 검색과 Wikipedia 등으로 진행하여 정답을 냈다.

이 사례에서 search-o1의 이점은 단순한 페이지 수 외에도 **발견된 URL을 정확하게 실행하는 경로**다. DS도 전체 결과 자동 fetch 없이 URL 보존과 선택을 개선할 여지가 있다.

### B. 답 후보를 찾고도 확인 작업을 끝내지 못함 — q00510

정답 Rosenfeld. RAgent 정답, search-o1과 DS 오답.

- DS 6번째 검색은 질문의 독특한 표현 `double-time piano`, `serious crooning`, `blistering blues guitar`가 일치하는 American Pancake의 Rosenfeld 기사였다.
- 이후 Genius/Last.fm 검색 결과에도 이름과 1998년 11월 출생 단서가 있었다.
- 메인은 39턴에도 후보를 Rosenfeld라고 판단했지만, 부수적인 발매일 등을 더 확인하려고 실패한 사이트와 추측 URL을 계속 열었다.
- 40턴 뒤 실제 최종 답변은 `Need source for "Do It For Me" release date and features. ... Open.`이라는 작업 계획이었다.

본문 fetch에서 Rosenfeld 문자열이 나타난 것 중에는 URL, 접근 차단 화면, 동명이인 사이트도 있다. 단순 문자열 출현을 유효한 원문 근거로 세면 안 된다. 여기서 확실한 근거는 검색 snippet과 메인의 후보 인식, 그리고 답 제출 실패다.

코드상 `_salvage()`는 도구 없이 답을 요구했지만 `_looks_like_action()`이 이 표현을 잡지 못해 정상 최종 답으로 받아들였다. 또한 최대 턴 소진 경로에서는 정상 초안 검토와 달리 기존 assistant 메시지를 제거해 답을 다시 구성한다. **정상 완료 초안 보존은 개선됐지만, 턴 소진 직전의 후보·근거 연결 보존은 아직 취약하다.**

### C. 잘못된 후보의 조건을 계속 채움 — q00975

정답 March 1910, Francis Lodowic Bartels. 두 baseline 정답, DS 오답.

- DS는 William McLachlan Dewar를 후보로 정하고 본인과 학교 페이지를 읽었다.
- 메인 추론에 Dewar의 출신 학교가 후보 학교와 다르다는 문제가 명시되어 있었다. 대사 경력도 확인하지 못했다.
- 그럼에도 후보를 교체하지 않고 Dewar의 출생일 April 1905를 답했다. 검색은 8회만 사용하여 2회가 남았다.
- RAgent는 `headmaster`와 `ambassador` 조합으로 다른 후보에 도달했고, search-o1은 Bartels의 학력·교장·대사 경력이 함께 담긴 페이지를 읽었다.

DS가 해야 했던 행동은 Dewar에 관한 추가 사실 수집보다 **후보 정체성의 재검토**였다. 단서에 맞지 않는 후보에서 올바른 생년월일을 추출해도 문제의 답은 아니다.

이는 재귀가 반드시 잘못된 정보를 만든다는 증거가 아니다. 반환된 정보를 받은 메인이 후보 채택/기각에 제대로 사용하지 못한 사례다.

### D. 모든 baseline 정답을 탐색 성공으로 볼 수는 없음 — q00865

정답 red. 두 baseline 정답, DS는 색상을 확인하지 못했다고 답했다.

DS 쿼리는 긴 조건 묶음과 검증하지 않은 잡지·연도 추측에 머물렀으며, 검색 소진 뒤 추측한 잡지 URL을 열다 실패했다. 개선해야 할 탐색 실패가 맞다.

그러나 baseline의 마지막 추론을 보면 둘 다 색상을 입증한 출처 없이 여러 색상을 생각하다 red를 선택했다. search-o1도 후보 정체성이 확립되지 않은 채 색을 추측했다. **이 문항의 점수 차이는 자동 fetch가 답을 찾아줬다는 사례로 쓰면 안 된다.**

벤치마크 점수는 그대로 인정하되, 개선 목표는 임의의 색 추측 모방보다 근거가 있는 유력한 후보를 불필요하게 폐기하지 않는 응답 정책이어야 한다.

## 5. 재귀의 장점이 남아 있는 사례

q01237은 DS만 정답 Ek Tha Tiger를 냈고, 두 baseline은 Hollywood의 The Avengers를 답했다.

DS는 Bollywood 흥행 자료, Lagaan, 중국의 2000년 올림픽 페이지를 읽었고, 재귀에서 2001 Gujarat earthquake 페이지를 추가로 읽었다. 최종 답은 중국 금메달 28개 → 다음 해 지진 → Lagaan의 산업 → 2012년 Bollywood 흥행작이라는 연결을 유지했다. 일부 경로는 관측된 사이트의 URL 추론을 사용했으므로 전부 원문 하이퍼링크 클릭이었다고 표현하면 안 된다.

이 사례는 재귀 확장이 관련 단서 연결에 참여했다는 관찰이다. 재귀를 제거했으면 반드시 틀렸을 것이라는 인과 주장은 할 수 없다. 또 DS 단독 정답 7개 중 q00746처럼 정답 단어는 맞았지만 정체성 연결 근거가 약한 사례도 있어, 7개 모두를 재귀 성공 사례로 세지 않는다.

## 7. 추가로 발견한 검색 통제 문제

메인 tool call에서 Google/Bing/DuckDuckGo/Yahoo의 `q` 또는 `p` 쿼리 URL을 fetch한 기록을 별도로 셌다. maps 등의 단순 조회는 제외했다.

- DS: 123문항, 316회. 이 중 308회는 검색 10회 소진 뒤다.
- RAgent: 1회, 도구 오류.
- search-o1: 명시적 메인 fetch에는 0회. 자동으로 fetch한 모든 URL까지 포함한 수치는 아니다.

DS의 316회 중 69회는 도구 오류다. 나머지도 CAPTCHA/차단 페이지일 수 있어 247회의 유효 검색 성공으로 계산할 수는 없다.

**`web_search 호출 10회`는 지켜졌지만, `외부 검색 기회 10회`까지 통제되었다고 할 수 없다.** 기존 점수를 소급 수정하지 말고, 다음 버전에서는 검색 엔진 query endpoint를 일반 문서 fetch와 구분해 동일 검색 예산으로 처리하거나 차단하는 명시적인 정책이 필요하다. 이는 기존 원문 링크를 따라가는 재귀의 자유를 없애는 것과 다른 문제다.

## 8. 개선 우선순위 — 새 도구/검색량 증가 없이

### 1순위: 발견된 출처를 실제로 읽는 연결

- 메인이 본 정확한 URL을 보존하고 선택할 수 있게 한다. 원문 URL을 다시 작성하다 대소문자·철자를 바꾸는 실패를 줄인다.
- 검색에서 유력한 후보/출처를 확보했다면 다음 검색이 그 페이지의 내용을 대체하지 않도록 한다. 고정된 첫 fetch 시점 대신 입구의 유용성을 기준으로 한다.
- 404 이후에는 이미 확보한 다른 후보 출처를 확인한다. 실패 URL 변형만 반복하지 않는다.

이는 search-o1의 모든 결과 자동 fetch를 복제하지 않고, 그 방법이 가진 정확한 출처 전달의 일부 이점을 가져오는 방향이다. 공유 fetch 파서나 baseline 프롬프트를 변경할 필요가 없는 DS 제어 계층 후보이다.

### 2순위: 후보 검증과 후보 발견을 구분

- 이름 식별 문제의 단서를 모두 동등한 체크리스트로 보지 않는다. 흔한 생년대보다 독특한 직업 조합/문구가 후보 발견에 더 유용할 수 있다.
- 후보와 충돌하는 핵심 단서가 나오면 후보 이름을 잠시 검색어에서 빼고 다른 후보를 찾는다.
- 모르는 조건과 직접 충돌하는 조건을 구분한다. 모든 미확인 조건을 답 포기의 이유로 만들지 않고, 직접 모순은 단순 미확인으로 넘기지 않는다.
- 충분히 구별되는 근거와 실제 요청한 답 필드가 확보되면, 주변 단서의 미확인 범위를 밝혀 답을 제출할 수 있게 한다.

이 원칙은 답을 지어내라는 지시가 아니다. q00510에서는 불필요한 검증 지속을 줄이고, q00975에서는 틀린 후보의 채택을 막는 방향이어야 한다. 현재 프롬프트에도 유사한 문장이 이미 있으므로 문장 추가만으로 해결됐다고 간주하지 않는다.

### 3순위: 검색 소진 뒤 진행 상태 관리와 답 보존

- 캐시 노트 재요청, 같은 실패 URL 재시도, 관련 없는 사이트 이동은 새 근거 확보와 구분한다.
- 알려진 유용한 미방문 출처는 계속 읽되, 후보/근거 상태가 변하지 않으면 현재 가장 지지되는 답으로 마무리한다.
- 최대 턴에서 정상 초안이 없더라도 후보와 근거 연결을 최종 작성에 넘길 수 있게 한다. 원문 사실과 후보 해석은 구분한다.
- 작업 계획을 정상 답으로 받아들이는 검사를 보완한다. 단순 정규식 추가만으로 전체 문제를 해결했다고 보지 않는다.

검색 10회와 결과 수 10은 그대로 둔다. 재귀 깊이/노드 한도를 먼저 올리는 접근은 권하지 않는다. 현 로그의 병목은 예산이 부족한 유익한 확장보다 진전 없는 메인 fetch와 답 제출 실패에 더 명확하게 나타난다.

### 보조적인 구현 결함

q00510의 Last.fm 차단 화면 노트에는 `**Status:** not_found – ...`가 있지만 메타데이터는 partial로 붙는다. `_parse_final()`은 상태명만 있는 마지막 줄을 인식하므로 설명을 붙인 not_found를 놓치고 partial로 기본 처리한다. 이 사례에서는 별도의 확장 중단도 작동했으므로 직접적인 점수 손실 원인으로 단정하지 않는다. 다만 상태를 탐색 제어에 쓸 때 수정할 필요가 있다.

## 9. 해석의 한계와 다음 확인

1. 평가 DNS 실패는 저장된 답을 다시 채점하여 탐색과 평가를 분리한다. 평가 복구와 전체 에이전트 재실행을 같은 것으로 취급하지 않는다.
2. 빈 응답 복구 실험은 최초 결과와 추가 시도 비용을 보존한다. 복구 성공이 방법 개선 자체를 입증하지는 않는다.
3. 이번 BrowseComp 사례를 사용해 수정한 버전은 이 표본에 대해 개발 영향을 받은 버전이다. 새 결과를 기존 고정 버전의 결과와 구분하고, 아직 보지 않은 평가 표본에서 일반화를 확인한다.
4. 정답 문자열 출현은 URL/차단 화면/동명이인에도 생긴다. 저장된 본문과 질문의 정체성 연결을 확인해야 한다. 검색 결과에 벤치마크를 닮은 문구를 반복하는 저품질 페이지도 있어 snippet 자체를 무조건 확정 근거로 취급하지 않는다.
