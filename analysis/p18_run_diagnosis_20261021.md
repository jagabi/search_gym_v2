## Depth는 들어가지만 근거 읽기로 거의 이어지지 않는다

하위 depth 방문이 있는 검색은 6/78(7.7%)→8/76(10.5%).
p18에서 실제 읽기 81회 중 79회(97.5%)가 depth 1이다.
depth 3은 516번의 검색 한 번에서만 나왔다. 목적지는 Benedict Cumberbatch와
Bernard Rose 페이지였고 둘 다 읽지 않았다. 정답 배우를 찾아 들어간 경로가 아니다.
326번의 정답 Manushkin 원문도 검색 9의 depth 1에서 확보했다.
따라서 새 정답을 깊이 탐색의 성과로 해석할 수 없다.

확장 funnel: 초기 preview 309개에서 RETURN 222 / READ 83 / EXPAND 4.
재판정까지 거친 최종 확장 부모 제안은 11개이며 전부 선택됐다.
개별 링크 542개 판단→자식 후보 21개→방문 18개.
부모 beam이 유용한 제안을 대량 탈락시킨 모습은 없다.
높은 EXPAND 때문에 형제 READ를 미룬 `read_deferred`는 단 한 번이다.
즉 이번 데이터에서 그 순서 수정이 적용될 기회 자체가 적었다.

종료: branches_closed 60, read_budget 10, frontier_exhausted 4, page_budget 2.

닫힌 페이지에 정답이 있었다거나 depth를 강제하면 좋아진다고 결론낼 수는 없다.

## 느려진 원인

RawTree 검색 시간 합은 2,494.3→4,594.2초로 2,099.9초 증가했다.
전체 문항 시간 합 증가 2,023.4초의 대부분이 검색 내부에서 발생했다.
메인모델 출력 대기만으로 설명되는 지연은 아니다.

d3 HTTP 서비스 시간은 p17 평균 약 765ms / 중앙값 609ms에서
p18 평균 1,624ms / 중앙값 829ms로 늘었다. p18 앞 5문항은 평균 850ms /
중앙값 632ms, 뒤 5문항은 평균 2,043ms / 중앙값 1,156ms다.
같은 실행 중에도 뒤쪽이 크게 느려졌다.

516번 두 번째 검색의 링크 평가에서는 같은 wave 요청 3개가 각각 약 94.5초 걸렸다.
8번째 검색의 링크 평가에도 약 25.7초 요청들이 있었다. wave 전체 완료를 기다리는
구조이므로 한 느린 wave가 다음 판단들을 지연시킨다. 병렬 요청 3개의 94.5초를
세 배로 더해 wall time이라고 계산해서는 안 된다.

이는 성공 HTTP 응답의 지연이며 d3 오류 응답은 0건이다. 입력 증가, 서버 부하,
큐잉·네트워크·서빙 상태 중 무엇이 원인인지는 클라이언트 로그만으로 분리할 수 없다.
따라서 '코드 변경만으로 64.6% 느려졌다' 또는 '전부 서버 문제다' 둘 다 증거가 부족하다.
다만 목적지 대응표가 입력을 늘리고, 쓸모없는 확장에 링크 요청을 쓰는 비용은 실제다.

## 문항별 실패와 실제 개선

**57: 정답 점수와 원문 grounding을 분리해야 한다.** 정확한 award 명칭과 grant 번호가
검색 7의 PMC7227421 검색 snippet에 있었다. 이 PMC 원문은 이번에도 5회 모두
`Expected status code 200 but got 203`으로 실패했다. 선택 청크들에서 정확한
award 명칭은 확인되지 않았다. 다른 NANETS 문서에 관련 grant 표기는 있었지만
대상 논문의 정확한 funding 근거와 동일하다고 볼 수 없다. 이번 정답은 reader가
원문 접근 문제를 해결한 증거가 아니다. 출력의 인용 줄 번호도 원문 검증을 대신하지 않는다.

**326: 실제 개선 사례다.** 검색 9에서 Encyclopedia.com의 Fran Manushkin 원문을 읽어
Baby와 Baby, Come Out!의 관계를 반환했고 검색 10에서는 작가 소개 원문도 읽었다.
p17에는 이 출처 자체가 없었다. p18이 도착한 출처를 읽어 전달한 것은 확인되지만,
프롬프트·스케줄러 중 어느 하나가 원인이라고 분리해서 주장할 수 없다.

**516: 정답 후보를 놓친 검색 경로와 빈 출력이 겹쳤다.** 처음 단서의 감독을
안정적으로 연결하지 못한 채 중국 띠·1979년·Carl Franklin으로 검색을 분산했다.
Kinsey와 The Constant Gardener까지 도달했으나 Peter King/Nzioki는 검사한
원문 청크·반환 근거에 나타나지 않는다. depth 3의 두 배우/감독 페이지도 정답 경로가 아니었다.
검색 10을 마친 뒤 일반 응답과 추가 최종화 2회 모두 text가 비어 있었다.

**598: 대상 PDF를 찾았지만 접근 실패했고 이후 검색은 돌아갔다.** 검색 3에서
RRS_10_2013_a1en.pdf를 발견했으나 Reader의 browser navigation 15초 timeout으로
실패했다(클라이언트 관측 약 23.2초). p17의 503과 이번 오류가 다르다.
PDF 확장자만으로 변환 실패라고 단정할 수 없다. 이후 일반 HDS/Appendix 문서와
Statistical Research Center를 반복 검색했고, 정확한 학술지 원문 근거를 확보하지 못했다.
p17의 이 문항 정답 역시 실패한 PDF를 인용한 결과였으므로, 정상적인 원문 독해 능력을
잃었다고 해석하면 안 된다. 이번에는 최종화 2회까지 빈 출력이다.

**746: Hamlin 가설이 그대로 고착됐다.** 'Maine 출생 부통령'을 Hannibal Hamlin으로
좁힌 뒤 Iowa 출생 조력자 검색을 이어 갔다. 올바른 다른 후보를 검증하는 검색은 없다.
Hamlin 도서관 페이지의 일반 부통령 메뉴에 Nelson Rockefeller 링크가 있었지만
이는 정답 관계를 확인한 근거가 아니며, 해당 출처는 확장하지 않았다. 10검색 동안 depth 1.
읽은 다른 긴 추모문에서 Rockefeller 단어가 나온 것도 정답 인물 발견으로 세지 않았다.

**1196: 정답 도시를 관찰했지만 가설로 이어가지 않았다.** 검색 2부터 결과 제목에
Thiruvananthapuram이 있었고, 검색 8에서는 Facebook 원문 청크로 도시 이름과
Padmanabhaswamy Temple의 관계까지 반환했다. 그러나 다음 검색은 다시 일반적인
도시 이름·3.25% 인구증가율이었다. 이름을 얻은 뒤 나머지 단서를 검증하지 않았고,
최종화 2회도 빈 출력이다. 정답 근거가 전혀 없었다고 할 수 없지만 전체 조건을
충분히 입증한 것도 아니다. 메인모델 활용 문제와 불완전한 근거를 함께 봐야 한다.

**1230: 관측을 잘못 결합하고 답 대신 행동 문장을 출력했다.** Moscow의 210시간
자료를 받은 뒤 Saint Petersburg의 극장, Moscow Cinema, Moscow Idaho의 Nu Art
극장 등 서로 다른 장소를 오갔다. 마지막 결과는
`Need to search but cannot use web_search? We can.`이었다. 빈 문자열과는 구별되지만
질문에 대한 답변은 아니다. Regal Cinema 근거를 확보한 흔적은 검사한 반환 청크에 없다.

네 빈 답변은 최종화 응답에서 raw_text와 text가 모두 빈 문자열이고 finish_reason은 stop이다.
후처리가 정상 최종 답변을 삭제했다는 증거는 없다. reasoning만 있고 final text가 없는
출력 행태는 확인되지만 서빙 파서 오류인지 모델 출력 선택인지는 서버 원시 기록이 더 필요하다.
여기서 메인모델을 교체·재실행하거나 출력 프로토콜을 변경하지 않았다.

## 판단과 다음 우선순위

파일럿 통과가 본 10문항 개선으로 이어졌다고 볼 수 없다. 가장 중요한 문제는
필요한 관계에 맞춘 경로 선택이며, 확장 폭을 키우거나 depth 3을 강제하는 처방은
현재 로그로 뒷받침되지 않는다. 원문 읽기 예산 두 번은 그대로다.

다음 수정 후보는 한꺼번에 도입하기보다 저장된 실제 노드로 따로 검증해야 한다.
우선 (1) 최초 가설에 맞는 사실과 새로운 후보를 연결하는 사실의 d3 판단을 분리해서
살펴보고, (2) 516번의 Kinsey→정답과 무관한 인물 확장을 왜 높게 평가했는지
해당 상태·키를 비교하고, (3) 이미 반환한 후보명과 누락된 관계를 활용하도록
기존 메인 프롬프트를 조정할 여지가 있는지 검토하는 순서다.
메인 추론모델은 통제변인으로 두고 새 도구·상태 모델·우회 reader를 추가할 근거는 없다.

현재 분석에서 접근 제한 완화, 추가 reader, PDF 우회, 자동 재실행은 하지 않았다.
