## 가장 큰 낭비: 1230번의 한 검색

- 검색어: `"202 hours" TomTom traffic index 2019`.
- 영화관 문제에서 요양시설 관련 PDF 두 URL을 선택했다.
- 두 URL의 fetch 본문은 SHA-256까지 동일하다: `03d4225b4beaca50084a0aafc636e150e83748c9484e3c51a3b7e7bacff29403`.
- 본문은 각각 2,251,387자, 2,681청크, 298번들이다.
- 페이지 direct/query 점수는 각각 0.00889/0.00276, 0.00779/0.00264였다.
- 검색 하나에 783초, d3 요청 1,284회, 입력 약 644만 토큰을 사용했다. 반환 청크는 0개다.
- 내용 해시 기반 청킹 캐시는 적중했지만, d3 번들 평가 결과는 재사용하지 않았다.

현재 `rawtree.py`의 문서 선별은 `quota_select(..., floor=0)`이며, `jev_link_floor`는 링크 확장에만 적용된다. `jev_floor`는 이미 모든 번들을 평가한 뒤 사용되므로, 이를 올려도 이 비용은 막지 못한다. 전체 선택 문서 121개 중 두 점수가 모두 0.05 미만인 14개가 번들 616개를 차지했다(전체 1,130개 중 54.5%). 이는 현재 선택을 사후 분류한 수치이며, 새 정책의 실제 절감률 예측은 아니다.

## 오답 경로

- **57**: 정답 논문의 PMC URL이 발견됐지만 fetch 422로 7회 실패했다. 다른 논문의 Vanderbilt 소속 정보는 반환됐지만 정답의 funding award는 반환되지 않았다. 문서 내부 탐색만 바꿔서는 접근 실패를 해결하지 못한다.
- **516**: 링크 판정 2,727회. Fifth Estate 본문의 Peter Nzioki 언급은 fetch됐으나 해당 이름은 반환 근거에서 발견되지 않았다. 대신 Bill Condon·유명 배우 쪽 근거가 반환됐고, 최종 답은 출생·부모·배역 조건을 충족하지 않는 Benedict Cumberbatch로 추측했다. 캐스트 본문에서 정답 후보를 고르고 전달하는 단계와 메인의 모순 검증을 함께 개선해야 한다.
- **598**: 정답 관련 Romanian Statistical Review PDF URL이 발견됐지만 fetch 400이었다. HDS를 다른 분야의 약어로 해석한 문서들이 반환됐고 Fuel을 추측했다.
- **746**: Maine 출생 부통령 단서에서 Hannibal Hamlin으로 기울었다. Rockefeller라는 문자열은 fetch에 있지만 내비게이션·족보 항목이므로 정답 근거 확보로 볼 수 없다. 1930년대 출생 인물의 경력과 19세기 인물의 시대 불일치를 검색 단계에서 반영하지 못했다.
- **1230**: 범위 단서 200~210시간을 205, 207, 202 등의 확정 숫자로 좁히는 검색이 이어졌다. 다른 연도의 교통표와 무관한 대형 문서에 비용을 썼다.

## 사용자 제안: 청킹 후 문서 내부 탐색

중간 청크만 보고 위/아래를 결정하는 정확한 이분탐색은 성립하지 않는다. 자연어 문서에는 답의 위치에 대한 단조성이 없고, 관련 증거가 여러 구간에 흩어질 수 있다. 적합한 모형은 **계층적 beam 탐색(coarse-to-fine retrieval)** 이다.

### 추천 실험안

1. Docling 청킹은 유지한다. 현재 `Chunk`에 index, text, tokens, headings가 이미 있다.
2. 연속된 청크/기존 번들을 계층으로 묶는다. 구조가 있으면 섹션 경계를 활용하고 큰 구간은 균등 분할한다.
3. 각 자식 구간을 제목·구간 위치·소량의 원문 발췌로 표현한다. 전체 자식 본문이나 모델이 생성한 전체 요약을 부모에게 넣지 않는다.
4. 4개 자식 구간을 d3로 평가하고, **레벨 전체에서 상위 2개**를 남긴다. 부모마다 2개를 남겨 지수적으로 늘리지 않는다.
5. 마지막에는 최대 4개 번들 원문을 읽고 기존 청크 평가·인접 청크 반환으로 이어간다. 원문에서 얻은 근거만 반환한다.
6. 가지 선택 점수는 답이 있을 가능성을 나타내며 사실 근거가 아니다. 양쪽 유효/전부 낮음/미리보기 정보 부족을 허용한다. 실패한 경로 뒤 차순위 탐색을 허용하더라도 추가 횟수·노드 수를 고정하고 전수평가로 복귀하지 않는다.

이는 문서 내부 선택 단계의 새 구현이다. 기존 Docling 라이브러리 설정을 켜기만 하면 제공되는 기능은 아니다. 메인의 도구나 탐색 책임은 바뀌지 않으며, d3가 계속 문서·구간·청크를 선택한다.

### 구간 표현의 한계와 대안

이번 PDF는 제목 경로 218종이 있었지만 같은 경로가 915개 청크에 반복된 구간도 있다. 제목만 사용하면 안 된다. 원문 앞·중간·뒤 표본은 저렴하지만 작은 중요 문장을 놓칠 수 있다.

대안으로 라이브러리 기반 BM25 인덱스를 청크에 만들고, 각 구간의 질의 관련 원문 몇 개를 미리보기로 쓰거나 전역 상위 청크를 별도 후보로 보존할 수 있다. 이는 로컬 전수 인덱싱 비용 O(N)이 들지만 모든 청크를 d3로 읽는 것은 아니다. 동의어·간접 단서에는 약하므로 BM25만으로 최종 탈락을 결정하는 것은 권하지 않는다. 현재 의존성에 추가해야 하는 선택지이며, 이번에는 설치하지 않았다.

요약 트리도 가능하지만 모든 하위 문서를 모델로 요약해서 구축하면 첫 질문의 비용이 크다. 문서를 반복 질의하고 인덱스를 재사용할 때 더 적합하다. MCTS는 평가 횟수와 보상 설계가 추가되므로 이번 목적의 첫 선택으로 권하지 않는다. d3 점수는 수학적으로 보장된 상한이 아니므로 branch-and-bound의 정확성 보장도 주장할 수 없다.

### 요청량 예시 — 측정 결과가 아닌 설계 계산

298번들 문서를 균형 4분할하면 약 5단계다. 내부 beam 폭 2, 마지막 번들 최대 4를 가정한다.

- 현재: 298번들 × 2목적 = **596회** 번들 판정.
- 제안: 최대 약 36개 구간 카드 × 2목적 = **72회** 경로 판정, 최종 4번들 × 2목적 = **8회** 본문 판정.
- 이후 청크 판정은 별도다. 최종 번들에 약 40개 고유 청크가 있다면 약 80회가 더 든다. 청크 수는 문서 구조와 겹침에 따라 달라진다.
- 구간 카드 생성과 청킹은 여전히 O(N) 로컬 작업이다. 탐색 횟수가 줄어도 문서 전체에 대한 정답 누락 방지나 일정한 wall time을 보장하지 않는다.

현재 d3 클라이언트는 임의 이름의 질문 key와 최대 64개 packet을 지원하지만 활성 설정은 **key 1개/HTTP, HTTP 4개/wave**다. 새 key를 여러 개 추가한다고 한 번에 공짜로 평가되는 것이 아니다. 이 전송 정책을 바꾸지 않고 구간 판정 자체의 수·입력을 줄이는 실험이다.

## 적용 우선순위와 검증

1. 문서 단계에서도 매우 낮은 점수로 읽기 할당량을 억지로 채우지 않게 한다. 현재 raw 경로에는 별도 page floor 설정이 없으므로 설정 배선이 필요하다. 짧은 prefix의 누락 가능성을 고려해 보수적인 후보 하한부터 재생 평가한다.
2. 동일 본문·동일 평가 질문·동일 모델/프롬프트/청킹 설정에서만 중복 독해 평가를 재사용한다. query가 바뀐 결과를 임의로 재사용하지 않는다.
3. 선택된 긴 문서에 위 4분할/beam 2/최종 4번들 탐색을 비교한다. 짧은 문서는 기존 번들 평가 경로를 유지한다.
4. 저장된 정답 근거 청크가 새 후보에 남는 비율, 최종 정답률, 번들/청크 HTTP 수, 입력 토큰, wall time을 각각 측정한다. 아직 새 정책의 d3 실험을 하지 않았으므로 속도·정확도 향상을 확정하지 않는다.
5. 문서 내부 개선과 별도로 516번의 모든 링크 사전평가, 57·598번의 접근 실패, 메인의 숫자 추측·시간 모순 처리는 별도 원인으로 남는다.

고정: main은 web_search와 최종 답변, d3는 내부 탐색·선별·독해, max_searches=10, strict wave=4. 문제 전체 타임아웃이나 메인의 read/continue 도구를 추가하지 않는다.
