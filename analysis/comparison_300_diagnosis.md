## 1. 분석 범위와 결론

- 세 실행의 300개 ID, 질문, gold 문자열이 모두 일치한다. 총 900개 response와 records를 비교했다.
- 카테고리와 single/set, 정답 항목 수는 데이터셋 메타데이터를 사용했다. 실패 유형 사례는 목적 표집이며, 사례 비율을 전체 실패율로 해석하지 않는다.
- 계산 및 일반 추론 오류는 동일한 기반 모델의 한계로 두며, 개선 대상에서 제외한다. 검색·페이지 선택, 근거 전달, 재귀의 작업 범위, 읽기 범위, 제어 흐름을 대상으로 한다.
- DepthSearch는 전체 F1에서 RAgent보다 높고 search-o1보다 낮다. 완전정답은 세 방법 중 가장 많지만 0점도 가장 많다.
- 가장 선명한 약점은 집합형 답의 recall이다. 단일 답에서는 search-o1과 비슷하나 집합형에서는 RAgent와 거의 같은 F1에 머문다.
- 전체 자동 fetch는 유망한 마지막 비교 후보이지만, 현재 기록만으로 우위를 보장할 수 없다. 이미 읽은 자료의 손실과 후보별 탐색 편중을 먼저 줄일 근거가 있다.

## 7. 코드와 전체 trace가 뒷받침하는 구조적 병목

- 현재 추출 입력은 원 질문과 현재 페이지뿐이다. [`_extraction_message`](C:/Users/yundo/Desktop/search_gym_v2/searchgym/explorer.py:907)는 부모 사실 오염을 막지만 “이번 페이지에서 맡은 작업”도 전달하지 않는다. `query`는 재귀 호출에서 그대로 내려가므로 자식의 구체 작업을 표현하지 못한다.
- 메인 fetch의 query는 [`_latest_query`](C:/Users/yundo/Desktop/search_gym_v2/searchgym/agent.py:825)를 사용한다. 직전 검색이 현재 fetch 대상과 다를 수 있다. 검색 문자열과 읽기 목표를 동일시하면 안 된다.
- [`fetch.reused`](C:/Users/yundo/Desktop/search_gym_v2/searchgym/agent.py:806)와 자식의 reuse는 URL별 저장 노트를 다시 준다. 다른 필드가 필요해도 이전 추출의 손실을 회복할 경로가 약하다. 캐시 삭제보다 원문 캐시와 작업별 노트 캐시의 구분이 적합하다.
- DS main fetch.reused 351회/141문항, child expand.reused 496회/170문항이다. 네트워크 재호출 847회라는 뜻은 아니다. 재사용은 비용을 아끼지만 정보 증가 없이 대화가 이어지는지 확인할 필요가 있다.
- DS 확장 예산 소진은 17/300. depth 3 사용 165개, depth 2까지만 68개, 확장 없음 67개. 각 F1은 .4869/.4348/.2169지만 문제 난도와 성공적인 진입 페이지 선택에 영향을 받으므로 재귀의 인과 효과로 해석할 수 없다.
- fetch.truncated는 R/O/D에서 70/242/120문항에 발생했다. RAgent/o1에도 공통인 문서 읽기 범위 제한이다. prefix만 제공하는 문제를 다른 페이지를 많이 읽는 것으로 우회할 수는 있지만 원본 보고서의 필요한 부분을 읽는 기능이 더 직접적이다.
- DS 검색 예산 이후 거절은 429회/157문항. RAgent 472회/172문항, o1 125회/101문항이다. fetch/node 예산 거절 이벤트는 세 실행 모두 0이었다. 사용 불가능한 도구를 철회하는 제어 개선은 공통 harness 정리로 취급해야 한다.
- o1은 선언상 web_search만 제공하지만 response에는 web_fetch 호출 57개가 있고 2개 인자 오류를 제외한 55개는 dispatch되었다. 따라서 현재 baseline을 엄밀한 search-only라고 설명하면 안 된다. 공통 dispatcher의 허용 목록 검증 문제이며, 이를 수정하면 새 실행이 필요하다.
- DS finalizing은 293문항에서 실행되고 최종 텍스트 변경은 284문항에서 관찰된다. 변경·축약 횟수 자체는 성능 손실 근거가 아니다. 사전 답변을 재채점하지 않았으므로 net gain/loss는 미확정이다. 일반 추론 교정 대신 추가 호출의 유효성과 확인된 근거의 보존만 ablation 대상으로 삼는다.

## 8. 우선순위: 전체 자동 fetch 없이 개선하기

### A. 짧은 작업 명세를 가진 재귀 — 최우선

기존 web_fetch와 내부 재귀에 `이번 페이지에서 찾을 항목`, `대상·연도·범위`, `반환할 원문 필드`를 전달한다. 예: “2018년 PPIC 지역별 issue 비율 표를 반환”. 원 질문은 맥락으로 유지하고, 부모의 주장·답 추측·누적 추론은 추출의 사실 입력으로 전달하지 않는다. 부모 근거는 이미 저장된 노트로 유지한다.

효과 가설: 전체 질문을 자식이 다시 해결하려는 탐색을 줄이고, 실제 누락된 필드에 맞는 링크 선택/추출을 수행한다. 목표는 계산 능력 향상이 아니라 일의 분배다. 추가 LLM planner 없이 기존 call 인자/reader 반환에 넣을 수 있다.

### B. 근거 본문과 reader 해설 분리 — 최우선

현재 자연어 Evidence/Missing은 원문, 누락, 모델 판단을 섞기 쉽다. 반환은 (1) 원문에서 복사한 관련 행·인용, (2) 원문에서 확인된 범위(시스템이 실제 절단 여부를 제공), (3) 아직 안 읽은 위치·다음 링크로 나눈다. 모델이 쓰는 “집계가 없다/결론이 없다”는 문장을 원자료가 없다는 뜻으로 취급하지 않는다.

특히 목록 질문에서는 몇 가지 예시로 압축하지 않고 관련 행과 헤더를 유지한다. 전체 본문을 다시 메인에 쏟아 넣을 필요는 없고, 필요한 섹션·열·행을 덜 변형해 전달한다. 추출을 범용 해설문 작성 작업으로 만들지 않는 것이 핵심이다. q00787 유형을 겨냥한다.

### C. 문서 재다운로드 없이 읽기 범위 갱신 — 높은 우선순위

원문을 한 번 확보한 뒤 필요한 섹션/PDF 페이지/CSV 행 범위를 선택해서 reader에 제공한다. 읽은 범위를 결과에 붙이고, 같은 URL을 다른 작업으로 다시 읽을 때 그 범위를 갱신한다. 새 원격 도구·계산 도구를 추가하지 않고 기존 fetch 내부에서 다룬다.

캐시는 URL별 원문과 (URL, 작업, 읽은 범위)별 노트로 분리하는 설계가 적합하다. 기존 노트에 필요한 항목이 있으면 그대로 재사용하고, 없을 때만 제한된 재독해를 허용한다. 호출 수가 늘 수 있으므로 무조건 재독해하지 않고 기존 반복 호출을 대체한다.

### D. 독립 대상 조사와 한 가지 재귀를 구분 — 높은 우선순위

4개 항공사를 물으면 각 항공사의 진입 자료를 먼저 확보하고, 한 항공사의 막힌 SEC 경로를 계속 시도하느라 다른 3개가 사라지지 않게 한다. 고정 “각 대상 N회” 할당보다 미조사 대상과 아직 채우지 못한 필드를 메인에 짧게 유지한다.

자식은 필요한 행/링크를 얻으면 부모로 복귀하고, 부모는 다른 미조사 대상 또는 같은 대상의 유망한 다음 링크를 선택한다. 10 search / 10 results는 유지한다. 탐색 순서를 바꾸는 제안이며 전체 자동 fetch가 아니다.

### E. 완전성 판단의 범위를 로컬 작업으로 제한

한 페이지가 전체 질문을 답하지 못하는 것은 정상이다. “이 페이지의 관련 행을 다 읽었는가”, “이 자식에게 맡긴 항목을 찾았는가”, “전체 후보가 다 검토됐는가”를 분리한다. source-backed 일부 답을 보존하고 누락 범위만 표시한다. 불확실한 후보를 무조건 나열해 recall을 올리자는 제안은 아니다.

현재 프롬프트에도 완전 목록 보존·누락은 제외가 아님 등의 문구가 있다. 같은 문구를 더 추가하는 것으로 해결됐다고 보지 않는다. 작업 단위, 반환 형식, 문서 범위, 부모에게 전달되는 데이터 자체를 바꾸고 검증해야 한다.

### F. 검색어를 짧게보다 “어떤 자료를 찾는지” 명시

첫 검색의 평균 단어 수는 R/O/D 약 9.99/9.84/9.23이며 중앙값은 모두 9다. 길이만으로 DS의 검색이 나쁘다고 할 근거는 부족하다. q00790처럼 같은 대상과 파일명 변형만 반복하는 것이 더 직접적인 문제다.

검색 목표를 후보 목록 찾기 / 특정 대상의 한 필드 찾기 / 막힌 원본의 대체 자료 찾기로 구분한다. 결과 제목·snippet이 이미 좋은 입구를 주면 fetch로 넘어가고, 같은 결과만 돌아오면 다른 미조사 대상 또는 자료 유형을 찾는다. 새 검색 횟수·result 수 증가는 없다.

### G. 공통 제어 오류와 finalizer는 별도 축

소진 도구 철회, 미제공 도구 dispatch 차단, 서버 protocol 오류는 세 방법에 공통 적용할 harness 항목이다. 이것으로 DS의 학술적 기여를 대신하지 않는다. DS만 매번 최종 답을 재작성하는 정책은 켜기/끄기를 독립 비교하되 근거 누락·추가 비용에 초점을 맞춘다.

## 9. 더 큰 아이디어와 마지막 수단

1. **중단·재개 가능한 재귀:** 첫 가지를 끝까지 내려가기 전에 자식이 “확보한 근거 + 남은 링크와 해당 필드”를 반환한다. 부모가 여러 가지 중 실제 공백을 채울 경로를 이어간다. 새로운 에이전트/상태 도구 대신 기존 재귀의 스케줄링을 바꾼다. 복잡도가 커지고 context 연속성이 깨질 위험이 있어 A–D 이후 실험할 후보다.
2. **자료 구조에 따라 재귀의 모양 변경:** 인물 식별→연도별 기록은 chain, 여러 기관 비교는 sibling, 목록의 상세 페이지 검증은 index→detail로 처리한다. 도메인 이름으로 router를 만들지 않고 질문이 요구하는 자료 의존성에 따라 처리한다.
3. **재귀의 결과를 결론 대신 재사용 가능한 자료 묶음으로 반환:** 후보별 행과 출처를 부모에게 전달하고 부모가 합친다. 각 자식의 출력이 어느 누락 항목을 채웠는지로 확장 가치를 평가한다. 정답을 알아야 하는 oracle 점수가 아니라 작업 진척 신호다.
4. **선택적인 폭 확대:** 현재 SERP의 아직 안 읽은 유망 문서와 페이지 내부 링크를 함께 비교해서 다음 하나를 선택한다. 매 검색 top-10 전부를 읽지 않으면서도 처음 고른 root에 묶이지 않도록 한다. 이미 노출된 URL 목록 활용이므로 검색 통제변수는 유지된다.
5. **search-o1 + recursive fetch:** 모든 검색 결과를 읽은 뒤 미충족 항목에 연결된 링크만 재귀한다. 기대 효과는 root 선택 실패 완화와 연결 문서 접근의 결합. 위험은 반복 페이지/reader 비용, 요약 손실의 확산, 첫 자동 reader가 예산을 독점하는 문제다. 10개 root 모두에 현행 재귀를 붙이는 방식은 특히 비추천한다. 마지막 비용-성능 비교 후보로 둔다.

마지막 후보가 이길 가능성은 있지만 현재 결과로 확신할 수 없다. q00073은 이미 선택적 재귀가 76회 자동 fetch보다 효율적이었고, q00787은 이미 읽은 목록이 전달되지 않은 문제가 있다. 모든 실패를 fetch 양으로 설명할 수 없다.

## 10. 논문 조사와 연결

- [DeepSearchQA](https://storage.googleapis.com/deepmind-media/DeepSearchQA/DeepSearchQA_benchmark_paper.pdf): F1을 주지표로 두고 집합 답의 완전성을 평가한다. DS의 높은 완전정답률은 강점이지만 F1 우위를 대신하지 못한다. 여기서는 집합형 recall 손실을 우선 과제로 해석한다.
- [Search-o1](https://arxiv.org/html/2501.05366v1): Reason-in-Documents는 현재 query와 앞선 reasoning에 맞는 근거 정제를 강조한다. top-k 자동 수집만이 논문의 핵심은 아니다. DS가 가져올 것은 현재 하위 작업과 읽기를 정렬하는 원리이며, 부모 사실 오염 방지를 포기할 필요는 없다. 현 저장 구현은 동일 harness로 재구성한 baseline이지 원 논문 전체 설정의 완전 재현이라고 단정하지 않는다.
- [BrowseComp-Plus](https://arxiv.org/abs/2508.06600): 고정 corpus와 근거 문서로 retrieval과 answering을 분리해 평가한다. 여기서는 이미 수집한 같은 페이지로 reader 전후를 비교하는 실험 설계에 참고할 수 있다. 저장되지 않은 문서의 반사실 검색 성능까지 재현할 수 있는 것은 아니다.
- [Diagnosing Search Behavior and Failure Modes in Long-Horizon Search Agents](https://arxiv.org/abs/2608.01913), 2026 preprint: 근거를 찾지 못한 실패와 찾고도 활용하지 못한 실패를 구분한다. 이 프로젝트에서는 이를 한 단계 더 나눠 원문 획득→reader 반환→최종 답 단계로 감사하면 된다. 타 논문의 상관관계를 이번 DS의 인과 효과로 옮겨오지 않는다.
- [AgentFold](https://arxiv.org/abs/2510.24699): 문맥을 여러 수준으로 보존·압축하는 접근이다. 이번에는 중요한 원문 근거를 반복 요약에서 보호한다는 설계 원리만 참고한다. 학습된 별도 모델의 성능을 프롬프트 수정만으로 기대할 근거는 없다.

## 11. 다음 실험 순서와 기여의 형태

1. **같은 저장 문서에서 reader만 비교:** 개발 문항의 원문을 고정하고 기존 노트 대비 하위 작업 명세 + 관련 원문행 보존이 누락을 줄이는지 본다. 외부 검색 없이도 비교 가능하지만 모델/판정 호출은 사용자가 실행할 때 한다.
2. **같은 모델·같은 검색 한도에서 end-to-end:** 기존 DS와 A+B를 비교한다. 그다음 C, 그다음 D/선택적 폭을 순서대로 추가한다. 모든 요소를 한 번에 바꾸어 원인을 잃지 않는다.
3. **재귀 기여 ablation:** 개선된 reader/메인 프롬프트는 유지하면서 재귀만 끈 조건을 비교한다. 전체방법 대 baseline 비교와 별개로 기여를 검증한다.
4. **비용 비교:** 실제 검색, 고유/중복 fetch, reader/LLM 호출, 토큰을 함께 제시한다. 원래 o1을 유지한 결과와 별도의 비용 맞춤 곡선을 구분하고, baseline을 약화해 우위를 만들지 않는다.
5. **평가 보호:** 이 300 test를 자세히 진단했으므로 같은 test를 반복 개선용으로 쓰면 독립 최종 평가라는 주장이 약해진다. 기존 validation에서 개발하고, 가능한 별도 holdout/추가 seed 및 모델로 최종 확인한다. 사례 검증과 반복실행은 F1을 보조해야 한다.

추가 진단 지표는 (a) 필요한 근거가 fetched body에 존재하는 비율, (b) 그 근거가 reader 반환에 보존되는 비율, (c) 자식이 새로 채운 필드 수, (d) 미조사 대상/범위, (e) 반복 호출에 따른 새 근거 유무다. gold를 사용하는 평가는 평가 단계에서만 수행한다.

추천 기여의 방향: “검색 결과에서 선택한 근거 페이지를 출발점으로, 미충족 하위 작업에 맞춰 연결 문서를 재귀 탐색하고, 페이지별 근거를 보존해 상위 작업으로 반환하는 방법.” 이것은 search-o1의 문서 정제와 접점이 있지만 자동 fetch에 단순히 호출을 더 붙이는 것과 구분된다. 신규성은 관련 browsing/hierarchical-agent 연구와 더 비교해야 하며, 이번 결과만으로 IEEE Access 게재 가능성이나 F1 폭증을 보장하지 않는다.

당장 선택: **전체 자동 fetch는 보류하고 A+B → C → D 순서로 검증. 모델 계산·추론 교정, 계산기 추가, 모델 교체, GEPA, 검색 한도 상향은 범위 밖.**
