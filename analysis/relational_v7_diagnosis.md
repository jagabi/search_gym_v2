# DS relational v7: 완료된 동일 77문항 진단

2026-09-24. 저장된 records/trace/response/explorer만 분석했다. 새 모델·검색·fetch·judge
호출이나 방법 코드 변경은 없다. 재현: `python analysis/audit_relational_v7.py`.
분석 시점 v7의 77개 완료 ID를 다른 실행과 대응시켰다. 비동기 완료 표본이며,
전체 300개에 대한 성능 추정이나 구성요소의 인과 효과 측정이 아니다.

## 결론

현재 v7은 읽기 실행을 회복했지만 그 비용에 상응하는 정답 증가가 없다.
invalid 수정이나 깊이 조절로 해결할 규모가 아니다. 추가 full run보다
관측 보존, 탐색 과제 전달, 페이지마다 중복되는 판단 구조를 먼저 수정할 근거가 있다.
DS의 재귀 자체를 폐기할 증거는 아니다. q00185에서는 재귀가 정답 페이지까지 도달했지만
최종 후보 선택에 반영되지 않았다.

| 방법 | 정답/77 | 중앙값 초 | LLM 호출 | fetch 시도 | 입력 토큰 |
|---|---:|---:|---:|---:|---:|
| RAgent | 8 | 94.3 | 1,109 | 65 | 8,454,971 |
| search-o1 | 7 | 1,226.0 | 5,517 | 5,592 | 66,671,952 |

v7 대 v4는 새 정답 4개/잃은 정답 5개, 대 v6는 4/4, 대 o1은 3/2다.
v7의 빈 최종 답과 run error는 0이지만 controller 예외 4회 및 도구 내부 실패는 존재한다.

## 1. 호출 증가의 주원인은 진입 페이지마다 반복하는 읽기 절차

| 응답을 받은 LLM 호출 역할 | v4 | v7 | v7 비중 |
|---|---:|---:|---:|
| 메인 + 최종 작성 | 826 | 800 | 10.6% |
| 진입 선택 | 728 | 3,044 | 40.3% |
| 별도 상태 갱신 | 277 | 0 | 0% |
| 페이지 추출 + 추출 복구 | 390 | 2,245 | 29.7% |
| 페이지 내 후속 탐색 판단 | 262 | 1,461 | 19.4% |
| 합계 | 2,483 | 7,550 | 100% |

v7 control.request는 3,048회이고 예외 4회를 제외한 response가 3,044회다.
기록의 llm_calls와 응답 이벤트 합계는 문항별로 일치한다.

- 검색 결과에서 고른 루트 요청: 333 → 2,390회(7.18배), 문항당 4.32 → 31.04회.
- depth 1 실제 새 추출: 277 → 1,709회. 전체 새 추출 2,224회 중 76.8%다.
- 읽기가 발생한 검색 배치 605개에서 루트 선택 중앙값 4개, 최대 6개.
- 682개 검색 배치 중 정상 일반 응답 종료 222, 읽기 턴 제한 종료 227,
  남은 미방문 후보 없음 126, invalid 종료 96, 나머지 11개.
- 전체 77문항 중 재귀 발생 70개. depth 2 추출 344회, depth 3 추출 171회.

v4의 실패한 선택까지 복원하고 형제 문서를 반복해서 읽으면서 요청량이 크게 증가했다.
루트를 재귀 확장 예산에 넣지 않는 설계는 의도된 것이지만, 그 결과 글로벌 12노드
제한은 총 읽기 비용의 상한이 아니다. 검색당 1루트 제한을 다시 넣자는 뜻은 아니다.

선택 호출의 관측 소요시간 합계는 30,557.9초, 추출은 45,727.9초다.
이는 문항 latency 합계 119,393.1초의 각각 25.6%, 38.3%다.
요청-응답 구간이므로 서버 대기시간도 포함한다. 탐색 판단 호출은 별도 요청 이벤트가
없어 정확한 개별 시간을 분리하지 않았다. 문항 시간 합계는 병렬 실행의 실제 벽시계 시간이 아니다.

페이지 추출 입력 24.38M 토큰 외에 후속 탐색 판단에서 20.74M 입력 토큰을 다시 사용했다.
탐색 입력은 원문과 저장한 own note 및 누적 자식 응답을 함께 포함한다.
메인에게 전달하는 검색+읽기 결과 중앙값도 3,670자 → 15,056.5자로 증가했다.

## 2. invalid만의 문제가 아니다

v7 선택 invalid 432건: 현재 메뉴 밖 주소 310, 검색 URL 74,
이미 선택한 루트 URL/ID 27, 다중 호출 5, 길이 제한 13, 빈 응답 1, 다른 도구 2.
여기서 '현재 메뉴 밖'은 관측된 분류이며 모두 환각 URL이라는 뜻이 아니다.
복구 329회. invalid 응답 자체는 전체 호출의 5.7%다.
이 호출을 모두 제거해도 현재의 3배 호출 격차는 해결되지 않는다.
탐색 판단 1,461회도 전부 제거할 수 없으며, 전부 없앤다는 과도한 가정조차 약 19% 절감이다.

fetch 실패율은 v7 598/3,097=19.3%, v4 94/472=19.9%로 비슷하다.
오류율 폭증보다 시도 자체가 늘어난 영향이 크다. 실제 서버 부하와 원격 사이트 조건은
통제한 실험이 아니므로 latency 차이 전부를 소프트웨어 구조 탓으로 단정하지 않는다.

## 3. 과제 분할이 입력에서 실제로 작동하지 않는다

agent._fetch의 relational 경로는 navigation_context를 원 질문의 관계를 찾으라는
일반 문장으로 만들고 query도 비운다. 루트의 reading_goal은 비어 있다.
_control은 현재 query를 보지만 working_state와 previous_sources를 제거한다.
자식 과제는 own note의 Next links 한 줄에서 URL과 설명이 맞을 때만 전달한다.
실제 expand.relation_task 518회 중 구체적인 문자열 과제 199회, 원 질문 fallback 319회(61.6%).
문자열 존재가 과제의 적절함을 보장하지도 않는다.

추출에서 부모 사실을 제거하는 것은 타당하다. 그러나 탐색 판단에서도 현재 후보,
이미 확인한 조건, 기각 근거가 사라지면 모든 페이지가 원 질문 전체를 다시 풀게 된다.
추출의 증거 격리와 탐색의 작업 문맥 전달을 분리해야 한다.

또한 매 선택 호출에서 selectable만 sources에 포함하여 프롬프트를 새로 만든다.
읽은/실패한 페이지의 원래 title/snippet은 이후 메뉴에서 사라지고, session.history에는
호출과 결과만 남는다. 접근 실패 응답에는 원래 검색 snippet의 식별 정보가 없을 수 있다.
실행 가능한 행동 목록을 줄이는 것과 과거 관측 자체를 지우는 것이 결합되어 있다.

snippet과 접근 상태를 분리 보존하고 대체 사본 탐색으로 연결해야 한다.

## 5. 차단 페이지도 정상 연구 노트로 커진다

49문항에서 원문 제목이 `18+ Access`인 페이지에 추출 호출 256회가 실행됐다.
이 수치는 정확한 제목 일치 기준이며, 전체 무관 페이지나 모든 차단 화면의 수는 아니다.
v4에도 같은 유형 102회가 있어 v7만의 현상은 아니다.
본문이 Loading 또는 연령 확인 안내뿐인데 Evidence/Coverage/Missing/Connections를
모두 작성하고 질문의 조건 전체를 되풀이하는 예가 있다. 일부는 partial로 표시된다.
이런 페이지는 한 줄 접근 상태와 관측된 원래 문서 식별 정보를 반환하면 충분하다.
단, 무관한 모든 페이지를 기계적으로 판별할 수 있다고 가정하거나 도메인 블랙리스트로
벤치마크에 맞추는 방식은 권하지 않는다.

## 다음 방향: 제한 수치를 바꾸기 전에 구조를 축소

1. **관측과 행동 목록 분리.** 이번 검색의 title/snippet/접근 결과는 세션 내내 보존하고,
   실행 가능 URL만 별도로 제한한다. 이전 전체 URL 메뉴를 재투입할 필요는 없다.
2. **추출 격리는 유지하고 탐색 과제 복원.** 현재 후보와 확인할 관계, 이미 확인/반박된
   조건을 탐색 단계에 전달한다. 부모 사실은 페이지 근거로 추출하지 않는다.
   별도 상태 갱신 모델을 추가하지 않고 기존 메인 출력/노드 반환을 사용한다.
3. **추출과 첫 확장 선택의 중복 제거.** 이미 추출 응답에서 Expand와 Next links를
   판단한 뒤 별도 호출로 처음부터 다시 고르게 하는 구조를 통합할 후보로 삼는다.
   출처별 노트는 먼저 보존하고 자식 반환 후의 부모 판단은 유지한다.
   native tool 출력과 노트 동시 반환을 실제 지원/검증하지 않은 채 가능하다고 단정하지 않는다.
4. **누락 조건 전체의 반복보다 식별 상태 변화 반환.** 후보가 새로 생김/반박됨/필요 조건이
   확인됨을 출처와 함께 부모가 알아볼 수 있게 하고 다음 행동을 바꾼다. 이것은 추가
   verifier 호출을 뜻하지 않는다. 단순 Missing 전체 목록을 매 페이지 반복하지 않는다.
5. 명백한 접근 화면은 짧게 종료한다. 무관 페이지와 가정 확인의 반복을 줄이지 않으면
   1회당 호출 절감만으로 v4 수준의 비용에 근접하기 어렵다.

검색 횟수/검색 결과 수, 깊이·자식·확장 노드 예산, baseline 코드는 이 분석에서 변경하지 않았다.
유망한 문서를 재귀로 읽는 DS 정체성을 유지하되, 무관한 진입 페이지를 많이 읽는 것을
재귀의 활용도나 성능 개선으로 간주하지 않는 것이 핵심이다. 개선 폭은 새 실행 전 예측 불가다.
