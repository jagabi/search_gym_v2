# 2026-10-17 RawTree v8 완료 4문항 진단

대상: `runs/test/20261017-1836_jevtree_gpt-oss-20b_browsecomp_raw_browser_p8_10`.
폴더명의 p8과 달리 실제 trace의 설정은 HTTP당 판단 1개, 묶음 4개, 이전 묶음 완료 후 다음 묶음이다.
실행 로그와 현재 코드의 분석이며, 새로운 웹 검색이나 모델 호출은 수행하지 않았다.

전송 혼잡은 이번 실행의 주원인이 아니다. 완료된 28,038개 평가의 실패는 0건이며 묶음 사이 중첩도 없었다.
주된 시간 비용은 매 검색에서 50페이지를 다 방문하고 그 페이지의 링크를 먼저 평가하는 탐색 구조다.
정답률 문제는 별개로, 메인 모델이 근거를 활용하지 않거나 가설을 사실로 취급하는 데서 드러난다.
청킹을 더 많이 하거나 요청 동시성을 다시 변경하는 것은 이 관찰에 맞는 첫 조치가 아니다.

페이지 방문은 재사용 및 실패도 포함하는 논리적 방문 수다. 실제 browser fetch는 각각 93/262/139/479회다.
4문항은 전체 정답률을 추정하기에 작은 표본이다.

## 시간 측정

`jev.attempt`에서 `jev.response`까지를 HTTP 서비스 시간으로 계산했다. 병렬 작업 시간을 단순히 더해 전체 소요 시간으로 부르지 않았다.

| 문항 | d3 요청이 하나 이상 진행 중이던 시간 | 그중 링크 요청이 진행 중이던 시간 | 메인 모델 호출 시간 |
|---|---:|---:|---:|
| q40 | 19.83분 | 17.18분 | 6.79초 |
| q57 | 30.17분 | 24.13분 | 30.07초 |
| q117 | 29.63분 | 27.34분 | 12.81초 |
| q326 | 99.89분 | 88.47분 | 57.58초 |

링크 시간은 d3 시간의 부분집합이며, fetch와도 겹칠 수 있다. 전체 187.57분 중 179.52분(95.7%) 동안 d3 작업이 진행 중이었다.
전체 요청 중 72.1%가 링크 평가이며, 요청별 서비스 시간을 합한 작업량에서는 약 81.4%다.
fetch 자체가 무료라는 뜻은 아니다. q57에는 fetch 실패 43건이 있으며 평가와 겹치지 않은 시간도 약 4분 있다.
그러나 fetch 단독 최장 시간은 이 네 문항에서 약 24.36초, d3 요청 최장은 약 6.65초다. 장시간 개별 요청이 멈춘 양상은 아니다.
청킹/번들링의 작업별 CPU 경과 시간 합계는 네 문항 각각 12.73/35.00/7.94/86.25초다. 병렬 중첩이 있으므로 wall time과 더할 수 없다.

q326의 링크 평가는 평균 1.408초다. 전체 d3 요청 서비스 시간 합계는 약 19,446초로, 네 슬롯을 쉬지 않고 사용해도 약 81분의 작업이다.
실제 묶음 슬롯 활용률은 약 81.1%로 평가 진행 시간 약 100분과 부합한다. 사용자가 요청한 묶음 완료 대기 때문에 생기는 빈 슬롯도 포함한다.
이것은 4개 배치가 깨졌다는 증거가 아니다. 요청 수 자체가 큰 상태에서 정상적으로 일한 결과다.
큐 대기 시간 대부분은 다른 평가가 진행되는 동안의 정상적인 대기다. 순수 큐 대기만 있던 시간은 q326 약 2.13초였다.

## 코드에서 확인한 탐색 문제

1. `searchgym/rawtree.py:305`의 `preview()`는 페이지 적합도 두 개와 모든 후보 링크를 하나의 논리적 평가 작업으로 묶는다. 해당 작업의 링크 평가가 끝나야 페이지 점수가 `rows`에 들어간다.
2. `rawtree.py:387`의 best-first는 페이지 예산이 끝나거나 frontier가 비어야 탐색을 종료한다. 답이 충분한지 확인하거나 중간 원문 근거를 메인에 반환하는 단계가 없다.
3. `rawtree.py:439`에서 비로소 문서 6개를 선정한다. 즉 50페이지를 방문하고 링크까지 평가한 뒤, 그중 6개를 청킹한다. 네 문항에서 총 126개 문서를 청킹했고, 최종 반환에 기여한 페이지 방문은 95개였다. 나머지가 전부 불필요하다고 단정할 수는 없지만 평가량과 실제 반환량의 차이가 크다.
4. 검색 결과가 있었던 21회 모두 50페이지를 소진했다. q57의 나머지 두 검색은 결과가 없어 frontier가 비었다.
5. 링크 생성 조건은 depth만 검사한다(`rawtree.py:326`). 이미 50페이지가 예약되어 추가 방문이 불가능해도 링크 평가를 계속한다. trace에서 50번째 노드가 예약된 뒤 새로 요청된 링크 평가만 q40 191개, q57 174개, q117 117개, q326 893개다. 합계 1,375개. 이미 진행 중이던 평가까지 포함한 수치는 아니다.
6. 현재 best-first에서 `jev_branch=2`, `jev_frontier_width=10`은 적용되지 않는다. 두 옵션은 beam 전용이다. best-first는 평가된 모든 적격 링크를 frontier에 넣고 방문 수만 50으로 제한한다.

링크 floor가 0이라 실제로 매우 낮은 점수도 방문한다. q57에서는 원래 의학 논문을 찾다가 Cloudflare의 CAPTCHA/Turnstile 개발 문서로 들어갔다.
예: private-access-tokens 진입 점수 0.000775, Turnstile 오류 코드 문서 0.001996. 해당 오류 코드 페이지에서는 다시 101개의 링크를 평가했다.
확률값처럼 표시되지만 이 점수를 실제 정답 확률로 해석해서는 안 된다.

방문한 비루트 노드 중 진입 점수 0.01 미만은 q57의 46개뿐이고, 이 중 최종 반환 기여 페이지는 0개다.
따라서 0.01은 시험할 만한 보수적인 floor다. 그러나 q326에는 0.01 미만 방문이 없어서 이 변경만으로 103분 문제를 해결하지 못한다.
q326에는 0.1 미만 진입이 123개 있었으나, 그중 2개는 반환에 기여했다. 0.1을 정답으로 정해 일괄 적용할 근거도 부족하다.
이는 관찰된 방문 집합의 통계이지, threshold를 바꿨을 때 발생할 새 탐색 경로의 성능 예측이 아니다.

정답은 Fran Manushkin의 첫 책 원제 `Baby`다.

따라서 정답 선택 실패의 직접 근거는 가설 고착과 명백한 반증 무시다.

현재 trace에서 Manushkin의 유의미한 전기나 책 근거가 평가/반환된 기록은 없다.

그 이름은 평가 prefix나 반환 원문에 들어오지 않았다. 이를 “정답 전기를 확보했는데 청킹이 버렸다”라고 해석하면 안 된다.
이전 실행과 이번 실행은 검색어 및 검색 결과가 달라, 이번 탐색 정책이 정답률을 떨어뜨렸다고 인과적으로 단정할 수도 없다.

현 system prompt에는 이미 추측과 사실을 구분하고 모순을 확인하라는 지침이 있다. 같은 지침을 추가하는 것만으로 해결된다고 보기 어렵다.
현재 RawTree는 원질문과 현재 query로 평가하고, 메인 모델의 후보·기확인 조건·반증 상태를 별도로 전달받지 않는다.
`agent.py:401`의 `ResearchState` 생성과 관련 제어는 depthsearch 조건에 묶여 있어 raw 경로에는 자동 적용되지 않는다.

## 권장 변경 순서

### 1. 결과를 버리지 않는 확정적인 낭비부터 제거

- 현재 1판단/HTTP, 4HTTP/묶음, 전부 완료 후 다음 묶음은 유지한다.
- 페이지 적합도 평가와 링크 확장 평가를 분리한다. 확장이 필요한 페이지에서만 링크를 평가한다.
- 최대 깊이뿐 아니라 방문 예산이 끝났을 때도 새 링크 평가를 만들지 않는다. 이미 필요한 페이지/청크 평가는 완료한다.
- fetch가 차단/오류 상태임을 제공하는 경우 그대로 보존한다. 제공자가 정상 본문이라고 반환하는 CAPTCHA를 거르는 기능은 별도 검토가 필요하다. 임의 도메인 블랙리스트를 늘리지 않는다.
- 비교 실험으로 `jev_link_floor=0.01`을 먼저 시험한다. 이것만으로 q326 해결을 약속하지 않는다.

### 2. 읽기 전에 끝까지 확장하는 순서를 바꾼다

초기 검색 결과 10개를 확보하고 페이지 적합도를 평가한 뒤, 상위 문서의 기존 coarse-to-fine 읽기를 먼저 수행한다.
근거와 미확인 조건을 확인한 뒤 필요한 frontier를 추가로 확장한다. 예를 들어 10개 추가 방문 단위로 중간 결과를 확인하고 총 50은 비상 상한으로 유지한다.
중간 확인은 모델에 근거와 부족한 조건을 판단하게 하며, 원문에 특정 단어가 있으면 중단하는 수작업 규칙을 만들지 않는다.
이는 새 제어 흐름 구현이 필요하다. 현재 `jev_fetch_budget` 하나를 바꾸는 것으로 progressive 탐색이 되는 것은 아니다.
현재 코드로 빠른 대조가 필요하면 방문 상한 50 대 20을 비교할 수 있지만, 20은 실험값이고 정답 보존을 보장하지 않는다.

### 3. 메인 판단을 독립적으로 검증한다

- q57 두 번째 결과, q117 두 번째 결과, q326 다섯 번째 검색 전후의 저장 근거를 동일하게 재생한다. 검색 결과 변화 없이 다음 행동이 근거에 맞는지 확인한다.
- 한 후보의 각 조건을 confirmed/contradicted/unknown으로 유지하고, 다음 행동은 미확인 조건 하나에 연결한다. 출처 원문은 계속 보존한다.
- 명백한 반증이 있는 후보를 계속 검색하거나 최종 답으로 채택하는지 측정한다. 실패하면 같은 근거를 더 강한 메인 모델에 제공하는 대조로 모델 능력과 제어 문제를 분리한다.
- 최종 검증은 찾지 못한 정답을 만들어내는 기능이 아니다. q326 같은 모순된 단정과 근거 없는 출처 설명을 막는 목적이다.
- 알려진 URL을 확인하는 전용 읽기/기존 문서 재열람 경로를 검토한다. 지금은 메인의 유일한 도구가 검색이라 작은 확인도 대규모 트리를 다시 연다.

### 4. 청킹 및 top-k는 원인이 확인된 것부터 조정

| 항목 | 현재 | 우선 권장 |
|---|---|---|
| HTTP | 1판단 × 4, 묶음 완료 대기 | 유지 |
| 초기 검색 결과 | 10 | 유지: 후보 회수율을 먼저 줄이지 않음 |
| 깊이 | 5 | 유지: 비용 조절은 방문/확장 시점부터 |
| 방문 상한 | 검색당 50 | 단계별 추가 방문, 50은 총 상한; 즉시 비교 실험은 20 대 50 |
| 링크 floor | 0 | 0.01 대조; 0.1은 별도 검증 |
| branch/frontier width | 2/10 | best-first에서는 무효; 이것을 조절해 해결하려 하지 않음 |
| 읽을 문서 | direct 2 + query 4 | 우선 유지, 읽는 시점을 앞당김 |
| bundle/chunk | 5,000/512, coarse-to-fine | 유지: 주된 시간 병목이 아님 |
| 핵심 청크 | direct 4 + query 8, 이웃 1 | 우선 유지; 정답 문장과 식별 메타데이터가 함께 오는지 점검 |
| 출력 상한 | 16,000 tokens | 우선 유지; 상한과 실제 출력량은 구별 |

Docling의 heading contextualization은 이미 켜져 있다. 청킹이 모든 조건의 연결을 보장하지는 않는다.
예를 들어 funding 문장은 살아 있어도 저자/소속/발행일이 다른 청크에 있으면 해당 논문을 확정하기 어렵다.
문서 제목 등 제공되는 메타데이터를 함께 유지하고, 부족한 식별 근거만 보충하는 방향이 맞다. 모든 번들을 모든 원자 청크로 확대 평가할 근거는 없다.
