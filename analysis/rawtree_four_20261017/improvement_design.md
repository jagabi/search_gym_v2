# RawTree 개선 설계안 — 2026-10-17

상태: 구현 전 제안. 근거는 같은 폴더의 review.md와 네 완료 문항의 trace다.
목표는 근거 있는 정답에 도달하는 시간 단축과 잘못된 후보의 지속 탐색 방지다. 평가를 덜 정확하게 만들거나 답변 실패를 빠른 종료로 감추는 것이 목표가 아니다.

## 1. 기본 구조

유지: 브라우저 Jina, 원문 기반 읽기, Docling, d3의 개별 판단, 전역 HTTP 4개 묶음 완료 대기.
변경: 모든 링크를 먼저 평가하고 50페이지를 소진한 뒤 읽는 단일 실행 흐름.

새 흐름:

1. 질문의 조건과 요청된 답의 형태를 메인 모델이 작업 상태로 기록한다. 원질문도 항상 보존한다.
2. 검색 결과 10개를 수집하고 브라우저 원문을 확보한다. 페이지 적합도를 먼저 평가한다.
3. 기존 direct 2 + goal 4의 최대 6문서에 coarse-to-fine 읽기를 적용해 첫 근거를 반환한다. 이 단계는 링크 전체 평가를 기다리지 않는다.
4. 메인은 근거와 후보 상태를 갱신하고, 답변 / 알려진 문서의 다른 조건 읽기 / 현재 탐색 이어가기 / 새 검색 중 하나를 선택한다.
5. 이어가기가 선택된 경우에만 유망한 부모 페이지의 링크를 평가하고, 소수의 후속 페이지를 연 뒤 다시 읽는다.
6. 최종 답은 원문 근거와 반증을 검토한 별도 답변 단계에서 작성한다.

메인이 매 링크나 청크를 제어하지 않는다. 의미 판단은 근거 묶음이 돌아온 경계에서 수행하며, d3는 페이지·링크·청크의 지역 판단을 담당한다.
첫 결과 반환 후 남은 확장을 백그라운드에서 계속하지 않는다. 진행 중인 HTTP 묶음은 정리하고, 다음 행동을 받기 전 새 확장 요청을 만들지 않는다.

## 2. 실제 코드 경계

| 구성요소 | 변경 |
|---|---|
| rawtree.py / LocalDecision | 1개 판단/HTTP, 전역 4개 묶음, FIFO와 취소 정리 유지. 단위·진단 로그 유지 |
| rawtree.py / preview | fetch + page scoring과 link scoring 분리 |
| rawtree.py / run_search | 일회성 함수에서 저장 가능한 탐색 세션으로 분리. open/read/continue 결과를 공통 반환 형식으로 제공 |
| rawtree.py / reading | 기존 bundle→chunk 선택 재사용. 동일 문서의 다른 goal에 대한 재열람 허용 |
| agent.py | raw 경로에도 작업 상태와 행동 예산 적용. 알려진 출처 읽기/탐색 이어가기 제공 |
| research_state.py | 출처 등록 재사용. 조건별 근거, 반증, unknown, 근거 종류 및 버전 추가. 기존 apply 그대로 접속하지 않음 |
| tools/__init__.py | Jina가 실제 제공하는 제목·상태·최종 URL 등 메타데이터 보존 검토 |
| raw_chunks.py | 현 Docling 방식 우선 유지. 라이브러리 옵션 없는 사이트별 재가공 규칙 추가 안 함 |
| config.py, configs/jevtree.yaml | 현재 정책과 새 정책 분리. 사용되지 않는 beam 전용 옵션을 실행 로그에 명시 |

제안 행동 API는 `web_search(query)`, `read_source(source_id, goal)`, `continue_search(search_id, goal)`다.
새 웹 검색은 기존 검색 횟수 예산에서 차감한다. 읽기/이어가기도 기존 페이지·깊이·턴 예산 및 질문 전체 자원 집계에 포함한다.
확인용 도구를 추가하면서 공짜 탐색 예산을 늘리지 않는다. max_turns=40에 중간 확인이 더 많이 들어가는 영향도 평가한다.
검색 한도의 소진은 기존 출처 검증과 최종화의 소진을 뜻하지 않는다. 소진된 도구는 실제 도구 목록에서 제거한다.

## 3. 탐색 세션과 지연 평가

세션에는 query, 현재 goal, 부모별 미평가 링크 목록, 평가된 frontier, 방문 기록, 읽은 근거, 예산과 goal 버전을 저장한다.
첫 패스에서 읽은 문서라도 유용한 링크를 가진 탐색 출발점일 수 있다. 반대로 본문이 정답을 주지 못하는 목차·기관 디렉터리도 좋은 출발점일 수 있다.
따라서 page-answer score 하나로 부모를 영구 폐기하지 않는다. 확장이 필요할 때 본문 근거용 후보와 탐색 경로용 후보를 구분해 부모를 선택한다.
초기 구현은 근거와 실제 링크가 있는 부모를 메인이 묶음 단위로 지목하고, 지목된 부모의 후보 링크는 기존 d3 방식으로 평가한다. 페이지 앞쪽 링크 몇 개만 고정 선택하지 않는다.
평가 대상이 아닌 부모와 낮은 순위 링크는 보류 상태로 남긴다. 필요할 때 다시 검토한다.

방문은 best-first로 하되, 소규모 방문 묶음 뒤 원문 근거를 메인에 돌려준다. 최초 이어가기 묶음은 기존 expand_batch=4를 출발값으로 사용한다.
페이지 작업 4개와 HTTP 묶음 4개는 별개의 한도다. 설정과 로그에서도 이름/단위를 구별한다.
방문 예산이 끝났거나 depth 한도에 도달하면 새로운 link scoring을 생성하지 않는다.

goal이 바뀌면 이전 목표의 점수를 새 목표의 순위로 사용하지 않는다. 원문과 청크는 재사용하고, 관련 점수는 goal 버전으로 구분해 필요한 부분만 다시 평가한다.
여러 검색의 서로 다른 목표 점수를 하나의 보편적 확률 순위로 섞지 않는다.
이 정책은 부분적으로 평가된 후보를 다루므로 엄밀한 전역 최선우선 순서를 보장하지 않는다. A*의 최적성 주장이나 점수 곱으로 만든 경로 정답 확률을 도입하지 않는다.

## 4. 후보 상태와 근거의 관계

질문의 조건은 코드의 도메인 규칙이 아니라 모델이 원질문에서 추출한다. 각 조건에는 원문 위치와 essential/identifying/auxiliary 같은 작업상 역할을 기록할 수 있으나, 이 분류 역시 모델 판단임을 남긴다.
후보별로 조건을 supported / contradicted / unknown으로 기록하고 출처와 청크 ID를 연결한다.
새로운 source가 없으면 가설을 supported로 승격하지 않는다. 가설을 사용하는 탐색 자체는 허용하되, 가설 표시는 유지한다.
예: q326의 whales/dolphins는 탐색 가설일 수 있지만 이후 읽기에 문제의 확정 조건으로 주입하지 않는다.
후보에 대한 모순이 있으면 다음 작업은 해당 모순을 해소할 근거 확인이나 다른 후보 탐색이어야 한다. 같은 후보를 정답으로 제출하려면 상태 갱신에서 모순 처리 이유가 필요하다.
오해한 근거로 잘못 탈락시킬 수도 있으므로 rejected는 되돌릴 수 있다. 새 근거가 나오면 재검토한다.

기존 ResearchState의 인용 문자열 존재 검사는 실제 문장이 있었다는 것만 확인한다. 그 문장이 그 인물의 출생지를 말하는지, 그 문헌의 funding인지까지 증명하지 않는다.
코드는 출처/청크 존재와 버전 같은 구조만 검증한다. 문장의 의미, 주체 연결, 모순 여부는 모델이 판단한다.
상태 갱신 파싱이나 인용 연결에 실패해도 원문은 폐기하지 않는다. 해당 해석을 미확인으로 남기고 제한된 복구를 수행한다.
검색 snippet, 실제 페이지 원문, 모델의 해석을 구별한다. snippet은 후보를 찾는 단서로 보존하지만 본문을 읽었다고 기록하지 않는다.

상태 기록은 기존 메인의 다음 행동 판단에 통합하는 것을 우선한다. 별도의 planner/critic/selector 모델 호출을 매 단계에 겹겹이 추가하지 않는다.
최종 검토만 한 차례 독립된 역할로 둔다. 동일 모델의 재검토는 독립된 검증자가 아니므로 효과를 실측한다.

## 5. 읽기 목적과 원문 반환

현재 direct-answer 목적은 원질문의 답을 명시하는 문장에 유리하다. 다중 조건 문제에서는 정답이 아닌 출생지·직업·날짜나 후보를 부정하는 문장도 필수 근거다.
goal 목적은 현재 부족한 관계를 확인하거나 반박하는 근거를 포함하도록 바꾼다. 단순한 키워드 일치나 현재 가설에 유리한 증거만 점수화하지 않는다.
원문 근거를 반환할 때 제목, URL/source ID, 청크 ID, 문서 버전과 함께 제공한다. 제공된 발행일/저자 메타데이터만 사용하고 없는 필드는 추측하지 않는다.
q57처럼 funding만 보이고 논문의 저자·연도가 빠져 있으면, 동일 문서에 대한 goal read로 필요한 부분만 추가한다.
현재 `agent._fetch`의 read 상태에 따른 반복 차단을 raw 재열람에 그대로 적용하지 않는다. 이미 fetch함, 특정 부분을 읽음, 필요한 조건까지 확인함은 서로 다른 상태다.

Docling 512-token 청크, 5k bundle, bundle 선별 후 세부 청크 평가를 유지한다. 모든 문서/번들을 세부 청킹 평가로 확장하지 않는다.
반환 청크는 같은 문서의 겹치는 범위를 병합하고, 원문상의 순서를 유지한다. 이미 반환된 동일 청크는 ID로 참조하고 요청하면 다시 노출할 수 있게 한다.
여러 청크가 같은 근거를 반복하는 경우와 서로 다른 조건을 확인하는 경우를 구별한다. 우선 동일 범위/동일 내용의 중복만 제거하고, 의미상 중복 판단을 위한 별도 모델은 나중에 필요성을 측정한다.
다른 출처의 같은 문장은 출처 관계를 보존한다. 단순 복제 페이지를 독립된 corroboration으로 세지 않는다.
문서별 강제 할당이나 도메인별 제한으로 중요한 긴 원문을 잘라내지는 않는다.
출력 한도에서 core를 제거할 경우 direct 쿼터를 먼저 예약해놓고 query-first 표시 순서 때문에 direct만 탈락하는 현재 잠재적 충돌을 해소한다. 표시 순서와 선정 우선순위를 분리한다.

## 6. 캐시와 브라우저

성공한 browser 원문은 현재처럼 질문 안에서 재사용한다. 동일 내용의 청킹/번들링 결과도 content hash + chunker/tokenizer 설정 버전으로 캐시한다.
점수 캐시는 model/prompt version, 정확한 state, target, objective를 포함하는 키로만 사용한다. query가 달라졌는데 URL이 같다는 이유로 재사용하지 않는다.
원질문에만 의존하는 direct 점수는 정확한 입력이 같을 때 재사용할 수 있다. 링크 번호가 visited에 따라 달라지는 state도 별개 입력이다.
서로 다른 문서 버전은 분리한다. 테스트 정답이나 문항 ID를 검색/랭킹 입력에 넣지 않는다.

브라우저 Jina는 유지한다. 성공 응답이어도 차단 화면이나 not-found 내용일 수 있다는 점을 관찰 가능하게 만든다.
제공자의 status/title/final URL 등을 보존하고, 제공자가 확실히 오류로 표시한 문서는 링크 확장하지 않는다.
서버가 정상 본문으로 전달한 차단 화면까지 해결하려면 설치된 Reader의 실제 기능과 출력 계약을 확인해야 한다. 지원 여부를 확인하지 않은 옵션을 가정하지 않는다.
현재 reader_failure가 있는 만큼 문자열 차단 규칙을 더 늘려 만능 해결책으로 삼지 않는다.
실패한 문서도 제목과 검색 snippet은 남겨 다른 사본을 찾을 수 있게 한다. 실패를 관련도 0으로 바꾸지 않는다.

## 7. 시작 파라미터

새 숫자를 잔뜩 추가하지 않는다. 우선 기존값을 새 실행 순서에서 사용한다.

| 파라미터 | 시작값/정책 | 의미 |
|---|---|---|
| HTTP packet / wave | 1 / 4 | 유지, 이전 wave 완료 필수 |
| 검색 결과 | 10 | 초기 후보 회수율 유지 |
| 최대 깊이 | 5 | 깊은 근거를 일괄 차단하지 않음 |
| 검색 세션 방문 상한 | 50 | 총 상한, 자동 소진하지 않음 |
| 이어가기 방문 묶음 | 4 | 매 묶음 후 읽기/다음 행동 판단; 실험 시작값 |
| 문서 읽기 쿼터 | direct 2 + goal 4 | 초기/증분 후보에서 최대치. 동일 문서 재처리 안 함 |
| bundle / chunk | 5,000 / 512 | 유지 |
| core 청크 / 이웃 | direct 4 + goal 8 / 1 | 유지, 중복 제거와 식별 근거 보완부터 |
| 출력 상한 | 16,000 | 유지; 실제 토큰량 관찰 |
| 링크 floor | 0 대 0.01 비교 | calibrated probability로 간주하지 않음 |

branch=2와 frontier_width=10은 beam에서만 동작한다. 새 모드의 부모 선택 한도로 몰래 재해석하지 않는다.
비교가 끝나기 전 0.1/0.15 같은 큰 link floor를 기본값으로 올리지 않는다.
문서 쿼터도 전부 채워야 한다는 의미로 쓰지 않는다. 읽을 새 후보나 해당 목표의 유효 근거가 부족하면 부족한 상태를 반환한다.

## 8. 답변 및 중단

답변하려면 후보의 식별 근거와 요청된 답 필드가 연결되어야 한다. 남은 명백한 모순이 있으면 해결되었다고 쓰지 않는다.
모든 주변 단서를 끝없이 재검증할 필요는 없지만, 다른 후보와 구분하는 핵심 조건은 빠뜨리지 않는다. 여러 문서에서 연결하는 정당한 추론을 허용하고, 한 문서의 정확한 문자열 일치만 요구하지 않는다.
더 찾을 수 없을 때 supported answer / unresolved / exhausted / infrastructure failure를 구별한다. 불확실한 응답을 정답 성공으로 집계하지 않는다.
최종 단계는 원질문, 근거 원문, 후보 상태와 반증을 받는다. 이전의 긴 추측을 근거로 재투입하지 않는다.
일반 답변 재작성 한 번이 q326의 정답을 복구한다고 기대하지 않는다. 우선 근거 없는 단정 방지 효과를 측정한다.

## 9. 구현 및 검증 순서

A. 의미를 바꾸지 않는 수정: 예산 종료 뒤 link scoring 방지, 제목/출처 보존, 정확한 캐시, 소진 도구 제거, 로그 개선.
B. preview/link/read를 분리하고 현 정책으로도 실행 가능하게 한다. 기존 HTTP 묶음 및 coarse-to-fine 테스트 유지.
C. 초기 근거 반환과 continue/read_source를 연결한다. 후보 상태를 최소 구성으로 접속한다.
D. 최종 검토와 반증 대응을 추가한다. 이 단계에서만 메인 모델 능력 차이를 비교한다.

각 단계는 별도 정책 버전으로 남긴다. 한 번에 모든 숫자와 모델을 바꾸지 않는다.

기능 검증:
- 대량 동시 요청에서도 4개 wave 경계, 오류/취소 후 다음 wave 정리.
- 페이지 상한 소진 후 신규 링크 평가 0건.
- 초기 반환에서 불필요한 링크 평가를 기다리지 않음.
- 세션 이어가기 시 원문/청크 재사용, goal 변경 시 오래된 점수 미사용.
- 한 번 읽은 문서의 다른 부분을 다시 읽을 수 있음.
- chunk/출처 연결과 출력 예산에서 core 보존, 원문 누락/중복 점검.
- 알려진 반증을 유지하고, 새로운 근거로 반증 상태를 되돌릴 수도 있음.

성능/정답 검증:
1. 저장된 페이지와 검색 결과로 기계적인 변화의 회수율·평가량을 비교한다. 기록에 없는 새 경로의 품질은 이 재생으로 알 수 없다.
2. q57 두 번째 반환, q117 두 번째 반환, q326 가설 전환 지점의 같은 근거로 메인의 다음 행동을 비교한다.
3. 항상 쓰던 10문항에서 새 정책 대조. 검색 결과 변동과 생성 변동을 기록하고 가능하면 동일 snapshot/설정으로 반복한다.
4. 그 10개만 보고 최적화하지 않도록 별도 미사용 문항에서도 확인한다.

지표는 정답률, 총 시간/p95, 첫 유효 근거까지 시간, 근거 확보 뒤 추가 시간, 링크 평가량, 실제 기여 페이지, 후보 탈락 뒤 재검색, 모순된 최종 답, 근거 없는 조기 종료다.
trace에는 phase, search/session ID, goal version, visited/read/expanded 수, HTTP wave, 현재 큐, 종료 이유를 남긴다.
불변 원문은 해시로 따로 저장하고 요청 로그는 해당 state를 참조하게 해 반복 대용량 로그도 줄일 수 있다. 이는 주된 추론 병목 해결과 분리된 관측성 개선이다.

## 10. 참고할 탐색 개념

[Fast Downward의 lazy best-first](https://www.fast-downward.org/latest/documentation/search/SearchAlgorithm/)는 평가를 필요할 때로 미루는 설계의 참고다.
[IRCoT, ACL 2023](https://aclanthology.org/2023.acl-long.557/)는 다단계 질문에서 검색과 추론을 번갈아 수행하는 접근의 참고다.
여기서는 개념을 가져오되 해당 플래너/논문 구현을 그대로 설치하는 방안을 제안하는 것이 아니다. 실제 정책의 정확도·지연 효과는 위 대조로 확인해야 한다.
