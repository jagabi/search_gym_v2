# p24: bounded multi-key d3 transport

The previous default split every decision into a separate HTTP request even when
the same page/chunk supplied multiple objectives. Independent source items also
issued separate requests. This changes transport and input layout, not tree/read
quotas or the underlying evidence questions.

## Request formation

- Defaults: at most 64 question keys per HTTP request, 4 HTTP requests per shared
  wave, at most 256 in-flight keys. The existing wave barrier remains.
- Independent judgments already runnable in the same event-loop boundary are
  grouped only within the same trace, usage accumulator, search and phase.
  There is no timer-based batching wait. Dependent read/rejudge/expand operations
  retain their existing awaits and depth barriers.
- A single source's direct/query/action keys remain together using the original
  state. Identical states with unique keys also retain the original state.
- Different source inputs use `shared` fields plus `items.item_N` original fields.
  Keys become `item_N__original_key`; each question explicitly binds its field
  references to that item overlaid on shared. Original paragraphs, headings,
  neighboring chunks, URLs and selected evidence are preserved, not summarized.
- Additional independent inputs fit within the existing `jev_bundle_tokens`
  source-state token budget (5000). This is a bound on combined serialized state,
  not a guarantee about the d3 server's complete prompt capacity. Existing large
  single-source inputs are not truncated to force a merge. Therefore packets need
  not fill 64 keys. Question instruction tokens are additional input.
- Responses are mapped by key, never answer iteration order. Missing/invalid keys
  preserve valid sibling scores and surface as explicit per-item errors. They are
  not assigned zero or retried as separate single-key service requests.
- Request traces include the composite request and original per-item contexts.
  HTTP counters now describe requests with potentially multiple decisions.
- Cancellation of one item keeps a shared request needed by another item alive;
  cancellation of all items or closing the client releases HTTP/key limits.

Affected independent phases include entry ranking, entry complement selection,
page preview, node actions, read selection, document/link regions, bundles,
atomic chunks and individual links. Cached decisions remain local.

## Offline verification

Fake HTTP tests exercise two objectives in one unchanged state; 33 source items
with two objectives in 64+2-key packets; per-link context/destination binding;
reversed responses; source-budget splitting without truncation; missing keys;
search/phase isolation; partial/all cancellation; packing errors; and the four
concurrent 64-key-request wave. Existing raw traversal, native-document and
final-answer regressions are also checked.

No live Jina/d3/search/main-model/judge experiment was run. Composite model inputs
may yield different scores despite preserving source data and question intent.
No claim of a measured runtime or accuracy improvement is made.

python test.py --method jevtree --model gpt-oss --benchmark browsecomp --path data/browsecomp/test.json --split test --limit 300 --tag raw_browser_p24_batch300 --expect-raw-traversal beam --no-cache
