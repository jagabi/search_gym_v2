# v65 지연 시간: fetch 대 reader

대상: `20261003-1643_jevtree_gpt-oss-20b_browsecomp_jevtree_v65_10`.
재현: `python analysis/jevtree_v65_latency.py`.
수치 원본: `analysis/jevtree_v65_latency.json`.

## 결과

10문항의 에이전트 실행 시간 합은 37,012.636초, 문항당 평균은 61.69분이다.
이는 workers=4 전체 배치의 경과 시간이 아니며 채점 시간도 포함하지 않는다.
각 문항 내부에서 겹치는 API 호출 구간은 합집합으로 계산하여 중복 합산하지 않았다.

| 구간 | 10문항 시간 합(초) | 문항당 평균(분) | 비율 |
|---|---:|---:|---:|
| 페이지 fetch 및 전처리 | 32667.68 | 54.45 | 88.26% |
| reader/요약 모델 대기 | 2873.26 | 4.79 | 7.76% |
| 메인 모델 및 최종 합성 | 991.47 | 1.65 | 2.68% |
| 검색 API(Serper) | 198.25 | 0.33 | 0.54% |
| JEV 평가 | 156.56 | 0.26 | 0.42% |
| 질문 조건 추출 모델 | 125.25 | 0.21 | 0.34% |
| 기타 경계 처리 | 0.16 | <0.01 | <0.01% |

reader는 400회, 개별 호출 평균 29.39초/중앙값 25.50초/p90 51.92초다.
개별 호출을 단순 합하면 11,755.39초지만, 최대 6개 독해를 병렬 실행하므로
실제 문항이 독해 단계에서 기다린 시간 합은 2,873.26초다. 단순 합으로 전체 지연의
32%가 reader라고 계산하면 병렬 시간을 중복 계산하는 오류다.

## 측정 방법과 한계

- main: `llm.request → llm.response`, 최종 합성은 `run.finalizing → run.final_response`.
- reader: `jevtree.selection → jevtree.search_end`. 개별 `reader_request → read` 구간도
  별도 집계해 병렬 중복을 확인했다. 이 구간에는 모델 서버 대기·생성·통신이 함께 포함된다.
- JEV: request_id로 연결한 `jev.request → jev.result` 구간의 합집합.
- 검색: `tool.result.duration_ms`는 코드상 최초 Serper 검색 도구 호출 시간이다.
- 페이지 구간: 검색 도구 호출 종료부터 `jevtree.selection`까지의 트리 탐색 시간에서
  JEV 구간을 차감했다. fetch 시작/끝을 쌍으로 남기지 않았으므로 잔여 시간을 사용했다.
  Jina/native 다운로드, 클라이언트 속도 제한 대기, 재시도, 본문 필터링, `/tokenize`,
  링크 추출 및 trace 직렬화가 포함된다. 따라서 88.26%를 순수 Jina 서버 처리 시간이라고
  말할 수는 없다. 다만 fetch 2856개 중 retrieval 라벨상 Jina/Jina fallback이 2850개다.
- 각 단계 합계와 전체 경과 시간을 대조했고, 단계 간 중복이 없는지 스크립트에서 검증했다.

## 속도 제한의 정황

처음 함께 실행되는 네 문항(q3/q7/q8/q13)의 문항 내 경과 시간을 대략 같은 시작으로
정렬해 Jina 완료 수를 계산하면 다음과 같다. trace에는 절대 시각이 없으므로 시작 시각
차이를 정확하게 보정한 전역 측정은 아니다. 넓은 구간의 처리율을 보는 보조 추정이다.

| 초기 네 문항의 경과 시간 구간 | 완료 수 | 분당 완료 |
|---|---:|---:|
| 60~600초 | 161 | 17.89 |
| 600~1200초 | 180 | 18.00 |
| 1200~1800초 | 176 | 17.60 |
| 60~1800초 전체 | 517 | 17.83 |

코드 `_jina_pacer()`는 JINA_RPM이 유효하면 그 값을 사용하고, 아니면 API 키 존재 여부에
따라 180 또는 18 RPM을 사용한다. 이번 관측은 18 RPM 전역 제한과 매우 잘 맞는다.
과거 실행 시 실제 환경 변수 값이나 계정의 현재 허용량은 로그로 확인할 수 없다.
180/18은 이 프로젝트의 기본값이며 Jina 계정의 실제 한도를 검증한 값이 아니다.

또한 로컬 MCP 서버를 만드는 `WebTools.__aenter__`의 환경 변수 전달 목록에 JINA_RPM이
없다. 설치된 MCP의 `get_default_environment()`에도 포함되지 않는다. 따라서 현재 로컬
stdio 구성에서는 부모 셸/.env에서 RPM을 설정하더라도 자식 서버로 전달되지 않을 수 있다.
키 전달 항목(JINA_API_KEY)은 존재한다. 원격 MCP를 쓴다면 원격 서버 환경을 따로 봐야 한다.

## 노드 수를 유지하는 개선 우선순위

1. 실제 Jina 키 적용 여부와 허용 RPM을 확인하고, 로컬 서버에 JINA_RPM 전달을 연결한다.
   계정 한도를 확인하지 않고 숫자만 올리면 429 및 재시도가 늘 수 있다.
2. 다음 실행에서는 fetch의 페이서 대기/HTTP/재시도/전처리 시간을 나눠 기록한다.
   현재 자료로 속도 제한이 유력하다는 것과 순수 네트워크 시간의 정확한 비중은 구분한다.
3. 전역 속도 제한이 해소되기 전에는 workers나 부모 노드 병렬성 확대만으로 그 제한을
   넘을 수 없다. JEV 사용과 트리 크기를 유지하면서 fetch 경로를 먼저 개선하는 것이 합리적이다.

현재 비율을 고정한 단순 계산으로 reader 구간을 절반으로 줄이면 전체 시간은 약 3.9%
줄어든다(1.04배 속도). fetch·전처리 구간을 절반으로 줄이면 약 44.1% 줄어든다(1.79배).
실제 병렬 부하·큐잉이 바뀌면 비율도 바뀌므로 성능 보장은 아니다.

이번 작업은 로그 분석만 했으며 실행 코드나 RPM 설정을 변경하지 않았다.
